# 차트 솔루션 개발 PRD (Product Requirements Document)

**문서 버전:** v1.8
**작성일:** 2026-06-10 (v1.8 갱신: 2026-06-29 — 모든 차트 타입의 원본값 튜플 모드, 저장 시 서버 SQL 재생성, DTO 검증 반영)

**관련 문서:** 화면설계서 v2.5 (Figma 작업용) · API 계약서 v1.6 · 노코드 SQL 생성규칙 v1.5 · 유사서비스 기능비교표 · Flyway V1__init.sql (v5.0)

## 1. 개요

웹페이지에 `<div>` 한 줄과 스크립트만 삽입하면 차트가 렌더링되는 사내 전용 임베드 차트 솔루션을 개발한다. 사용자가 노코드 빌더(기본) 또는 SQL(2차)로 차트를 정의하고 시각화 옵션을 지정하면, 토큰이 포함된 임베드 코드가 발급되어 사내 인원이 자신의 페이지에 차트를 끼워 넣어 사용한다. Metabase의 임베디드 분석 기능과 개념적으로 유사하나, 핵심 기능(네이티브 임베드, SSO)이 유료인 Metabase와 달리 사내 요구에 맞춰 자체 구축한다.

## 2. 배경 및 목적

상용 BI 도구(Metabase 등)는 차트 그리기는 무료지만, 본 프로젝트가 필요로 하는 두 핵심 기능이 유료 영역에 있다.

- 네이티브 임베드(iframe이 아닌 div 직접 렌더 + 토큰 인증): Metabase Pro 전용
- SSO 로그인 연동: Metabase Pro 전용

따라서 ECharts + Spring Boot 기반으로 동일한 임베드 방식을 자체 구축하여, 구독 비용 없이 사내 요구(임베드 + 향후 SSO + Type B 임베디드 배포)에 맞춘 솔루션을 확보하는 것을 목적으로 한다.

## 3. 대상 사용자

- 사내 직원 전용 도구다. 외부 고객 대상이 아니다.
- 개인 계정 단위로 사용한다. 인증은 사내 SSO(통합로그인)를 전제하며, 회사 차원에서 타 솔루션과의 통합로그인이 추진될 가능성이 높다.
- MVP 단계에서는 인증 없이 동작하며, SSO 로그인은 설계에 포함하되 구현은 최후순위로 둔다.
- 계정 생성/삭제/비밀번호는 IdP(SSO)가 관리하므로 멤버 관리 화면은 만들지 않는다. 로그인 시 사용자 레코드를 자동 생성(JIT)한다.
- 차트 가시성: 개인 사용자 소유 범위. 사용자는 본인이 등록한 데이터소스와 본인이 만든 차트를 보고 수정·삭제한다. 공유/팀 권한은 후속 기능이다.
- 인수인계서 원문은 "고객사 납품(B2B)"을 전제했으나, 본 프로젝트의 서비스 단위는 조직이 아니라 **개인 사용자**다. 실제 연결 대상 DB는 회사/조직의 업무 DB일 수 있지만, 데이터소스 등록·차트 정의·토큰 발급의 소유 범위는 개인 사용자(`owner_id`/`user_id`)로 잡는다.

## 4. 개발 조건 및 제약

- 개발 인원: 사실상 단독 개발
- 일정: 수 주 내 MVP
- 설계 주도권: 본 프로젝트 리드(인수인계서 명세 변경 권한 보유)
- MVP 범위 축소가 성공의 핵심이며, 화려한 기능보다 코어 파이프라인의 완결을 우선한다.

## 5. 시스템 아키텍처

### 5.1 3대 구성 요소

| 구성 요소 | 기술 스택 | 역할 |
|---|---|---|
| Chart SDK | Vanilla JS + Apache ECharts | div 자동 검출, 토큰으로 데이터 요청, ECharts 렌더 |
| Backend API | Spring Boot + JPA + Flyway | 메타 DB 소유, SQL 실행, ECharts JSON 생성, 토큰 검증 |
| Admin Console | Next.js | 차트 빌더 UI (DB 직접 접근 없음, API만 호출) |

### 5.2 DB 소유권 및 마이그레이션

- Backend(Spring Boot)가 메타 DB를 단독 소유한다.
- Admin Console(Next.js)은 DB에 직접 접근하지 않고 Backend API만 호출한다. 따라서 Prisma는 사용하지 않는다.
- 마이그레이션은 Flyway로 관리한다. Spring Boot 구동 시 자동 적용된다. (인수인계서 8페이지의 Prisma 자동화는 Flyway로 대체)

### 5.3 데이터 구조 (메타 DB + 다중 데이터 소스)

- 메타 DB 1개: 솔루션이 소유(`mc_` 객체). 사용자·토큰·개인별 데이터소스·차트 정의 저장. Spring + Flyway가 관리.
- 데이터 소스 N개: 차트가 데이터를 조회할 PostgreSQL DB들. Admin에서 등록(호스트/포트/계정)하며, 차트마다 하나를 지정한다.
- 동적 커넥션 풀: 데이터소스별 커넥션 풀(HikariCP)을 런타임에 생성·관리한다. 메타 DB 연결과 분리.
- 자격증명 보안: 데이터소스 접속 비밀번호는 암호화(AES-GCM)하여 저장한다. 암호화 키는 `.env`. 등록 계정은 읽기 전용을 권장(등록 화면에서 안내).
- 데이터소스 엔진은 PostgreSQL로 고정한다(JDBC 드라이버 단일, SQL 방언 단일).

### 5.4 배포 모드 (Type A / Type B 모두 지원)

| 모드 | 설명 | DATABASE_URL |
|---|---|---|
| Type A (독립 설치형) | docker-compose로 전용 PostgreSQL을 함께 패키징 | 전용 DB 가리킴 |
| Type B (임베디드) | 기존 운영 DB에 연결, `mc_` 메타 테이블만 추가 | 기존 DB 가리킴 |

- 애플리케이션 코드는 두 모드를 구분하지 않는다. `DATABASE_URL` 값만 다르며, docker-compose 구성과 `.env`만 달라진다.
- Type B에서는 기존 운영 DB의 업무 테이블을 절대 건드리지 않아야 한다. Flyway 마이그레이션은 솔루션 소유 `mc_` 객체만 생성/변경한다. 예외적으로 S1 검색 최적화를 위해 PostgreSQL 표준 contrib 확장 `pg_trgm`을 사용하므로, Type B 설치 전 `CREATE EXTENSION pg_trgm` 권한을 확인한다.

## 6. 데이터 렌더링 방식

서버가 ECharts 설정(option)을 완성된 형태로 생성하여 SDK에 전달하는 방식(방식 A)을 채택한다. (인수인계서 4페이지 "ECharts 전용 JSON 반환"과 일치)

```
PostgreSQL에서 SQL 실행
  → Backend가 결과를 ECharts option JSON으로 조립 (차트종류/색상/축/범례 반영)
  → SDK는 받은 JSON을 chart.setOption()으로 렌더만 수행
```

SDK는 차트 모양을 결정하지 않으며, 모든 시각화 설정은 Admin/서버에 집중된다.

### 6.1 데이터 형태 컨벤션 (서버 변환기 규칙)

- SQL 결과의 첫 번째 컬럼 = X축(카테고리), 나머지 숫자 컬럼 = 각각 하나의 시리즈.
- 시리즈가 2개 이상이면 다중 막대/다중 선이 되며, 시리즈별 색·범례가 자동 구성된다.
- ECharts option 조립은 서버의 단일 변환기에 둔다: (rows, chartType, options) → option JSON. 차트 종류·옵션 추가 시 이 변환기만 확장한다.
- 시리즈 분할(breakout) 확장 대비: 변환기는 (rows → [피벗] → series 조립) 단계 구조로 둔다. 카테고리로 시리즈를 나누는 요구(예: 부서별 월 매출 다중 선)가 오면 피벗 단계만 추가하고, "첫 컬럼=X" 컨벤션은 피벗 산출물에 그대로 유지된다.

## 7. 기능 요구사항

### 7.1 차트 렌더링 (코어, 최우선)

- SDK가 페이지 로드 시 `[data-chart-id]` 속성을 가진 div를 자동 검출한다 (DOM 스캐닝).
- 각 div에서 `data-chart-id`, `data-auth-token`을 읽어 Backend에 데이터를 요청한다.
- Backend는 chartId에 매핑된 SQL을 실행하고 ECharts option JSON을 반환한다.
- SDK는 `echarts.init()` 후 `setOption()`으로 div에 직접 렌더한다.
- SDK는 컨테이너 div의 크기 변화를 추종한다(ResizeObserver → `chart.resize()`). 크기·반응형은 호스트 페이지의 CSS 책임이고, SDK는 따라가기만 한다.

### 7.2 시각화 옵션 (핵심 기능, 지속 확장)

- 차트 분류 체계: **대분류 → 소분류(variant) 2단계** (v1.4).
  - 대분류 4종: 막대(bar) / 선(line) / 원형(pie) / 분포(scatter). **MVP는 4종 모두 활성** — 이후 추가 차트(레이더·지도 등)는 UI에 잠금("후속") 표기.
  - 소분류는 대분류에 종속된다 — 대분류 선택 시 소분류 목록이 교체된다: 막대[기본·누적·그룹·가로] / 선[기본·곡선·영역·누적영역·계단] / 원형[파이·도넛·로즈] / 분포[산점도·버블].
  - 소분류는 별도 chart_type이 아니라 **`options.variant`로 저장**: 막대(기본·누적·그룹·가로) / 선(기본·곡선·영역·누적영역·계단) / 원형(파이·도넛·로즈) / 분포(산점도·버블). chart_type 컬럼·CHECK는 대분류만 — 소분류 추가 시 마이그레이션 불필요. 서버 변환기가 variant를 ECharts 속성(stack, areaStyle, radius 등)으로 해석한다.
- MVP 옵션 (섹션별):
  - 기본: 대분류·소분류, 차트 제목(`title.text`), 제목 위치 — 가로(좌/중앙/우 `title.left`) × 세로(상/하 `title.top`) 2축, 설명(차트 메타 — S1 카드 표시용, option 미반영)
  - 색상: 색 모드(팔레트/개별 지정), 팔레트 프리셋, 항목별·시리즈별 개별 색 — 모든 대분류 공통(막대=항목/시리즈, 선=시리즈, 원형=조각)
  - 축(X·Y 그룹 구조): 그룹별 제목·단위 표기·범위(자동/수동 min·max)·스케일(선형/로그). X축의 범위·스케일은 X가 숫자일 때만 활성(분포 차트 — `appliesTo`로 제어), 카테고리 X축은 제목·라벨 회전만
  - 계열: 데이터 라벨 표시, 정렬(원본/오름/내림)
  - 범례: 표시 여부, 위치(상/하)
  - 데이터 갱신: 갱신 모드(실시간/주기/수동), 주기(TTL), [지금 갱신] — 7.7 참조
- 차트 종류 전환 규칙(비파괴): **데이터 구성(테이블·축·조건·정렬)은 어떤 전환에도 초기화하지 않는다.** 같은 대분류 내 소분류 전환은 옵션 전부 유지(완전 호환). 대분류 간 전환은 공통 옵션(제목·위치·색·범례)만 유지하고 이전 대분류 전용 옵션은 즉시 초기화 + 토스트 안내("막대 전용 설정이 초기화되었습니다" + 실행 취소). 비호환 데이터는 무시+안내로 처리(원형: 첫 시리즈만 사용 / 분포: 숫자 X축 필요).
- 옵션 정의에 `appliesTo`(적용 대분류 목록) 메타를 두고 옵션 패널이 차트 종류별 노출을 필터링한다 — "옵션 추가 = 정의 한 줄" 원칙 유지.
- 확장 예약(후속): 막대 너비, 0 기준 해제(`yAxis.scale`), 범례 좌/우, 차트 여백 프리셋(`grid`), 툴팁 포맷, 조건부 서식. (곡선·영역·누적은 variant로 흡수됨)
- 저장: 시각화 옵션은 DB의 `options` JSONB 컬럼에 저장한다. 옵션 추가 시 스키마 마이그레이션이 불필요하다.
- 구현 원칙: 옵션 정의(키·타입·기본값·섹션)를 코드에서 데이터 목록으로 관리하고 옵션 패널이 이를 렌더한다. 옵션 추가 = 정의 한 줄 + 서버 변환기 한 줄. 옵션 패널 상단에 옵션 검색창 자리를 확보한다(MVP 동작 미구현).

#### 개별 색 지정 (막대마다·선마다 다른 색)

- 팔레트 모드(기본): 색 배열을 순서대로 자동 적용. 데이터가 바뀌어도 깨지지 않는다.
- 개별 지정 모드: SQL 실행 성공 후 결과의 카테고리/시리즈 항목별로 색을 지정한다. 실행 전에는 비활성(동적 UI — 항목 수는 데이터에 의존).
- 저장 형태(JSONB): `colorMode`, `palette[]`, `colorMap{항목명: 색}`.
- 매핑 규칙: 항목이 `colorMap`에 있으면 지정 색, 없으면(SQL 변경으로 새 항목 등장) 팔레트 순서로 자동 적용. 차트가 깨지지 않게 한다.

### 7.3 차트 빌더 (Admin) — 노코드 + SQL 이중 모드

차트 정의는 두 모드를 제공한다. 노코드가 옵션 1(기본 경로), SQL이 옵션 2(고급 경로)다. MVP에서는 노코드만 구현하며, SQL 직접 작성 UI는 2차에서 추가한다. 새 차트는 항상 노코드에서 시작한다. 탭 자리는 화면에 미리 두되 SQL 탭은 2차까지 비활성("준비 중") 표시한다.

- 노코드 모드(옵션 1, 기본): 테이블 선택 → X축 컬럼 [+ 날짜 타입이면 묶기(일/주/월, 기본 월) — DATE_TRUNC, MVP 포함] → Y축 컬럼 + 집계(합계/평균/표준편차/개수/고유 개수/최소/최대/원본값) → 조건(WHERE: 컬럼·연산자·값 행 추가식) → 정렬. 내부적으로 SQL을 생성하여 기존 실행 파이프라인을 그대로 사용한다(노코드 = SQL 생성기).
- `원본값(agg:"none")`은 모든 차트 타입에서 지원한다. 막대/선은 X/Y 튜플, 원형은 name/value 튜플, 분포는 `[x,y]` 점을 그대로 그린다. 원본값 모드는 집계와 섞을 수 없고 `GROUP BY`를 만들지 않으며 표본 추출을 사용할 수 없다.
- 결과 영역은 [실행 결과](집계)/[원본 데이터](조건 적용 raw, 최대 1,000행 스크롤) 탭으로 구성 — 집계의 세부 데이터를 항상 확인 가능. 테이블 선택 시 원본은 자동 표시, 집계는 명시적 [실행]만(예외: 저장된 차트로 진입 시 1회 자동 실행).
- 확장 예약(노코드): 시리즈 나누기(breakout, `seriesBy`)는 폼에 자리만 비활성으로 표기하고 후속 구현한다(SQL 생성규칙 v1.1 10장).
- SQL 모드(옵션 2, 고급, 2차 구현): SQL 직접 작성. 스키마 탐색기·자동 실행·에러 노출은 기존 설계대로.
- MVP: 노코드의 "생성된 SQL 보기"(읽기 전용)만 제공. 전환 규칙(노코드→SQL 단방향, SQL 수정 시 builder_config 폐기 경고)은 2차의 SQL 탭과 함께 활성화. Metabase와 동일한 모델.
- SQL 실행 엔진(검증·읽기전용 실행·타임아웃·행제한)은 백엔드 기반으로 MVP에 포함된다 — 노코드 생성 SQL이 이 엔진을 사용한다. 2차에서 추가되는 것은 SQL 작성 UI뿐이다.
- 저장: `define_mode`('sql'|'builder') + `sql_query`(항상 저장) + `builder_config` JSONB(노코드 상태 복원용). builder 모드 저장 시 `sql_query`는 클라이언트 값을 신뢰하지 않고 서버가 `builder_config`에서 재생성·검증한 SQL로 저장한다.
- 저장 조건: 차트명 + 데이터소스·테이블·X축·Y축 1개 이상 + 검증 통과. 저장 시 서버가 SQL 재생성 후 1회 실행해 캐시를 시드하므로(7.7), 실행이 실패하면 저장도 실패로 처리한다(검증 400 동일 노출).
- 미저장 이탈 보호: 구성 변경 후 [←목록] 등으로 이탈 시 "저장되지 않은 변경이 있습니다" 확인 모달.
- 데이터소스 선택: 차트 생성의 첫 단계로 데이터소스를 선택한다. 스키마 탐색기·노코드 테이블 목록은 선택된 소스 기준.
- 연결된 소스의 스키마 탐색 패널 제공(읽기 전용, `mc_` 테이블 제외). SQL 에러는 DB 메시지·위치 그대로 노출.
- 요청/응답 형식은 API 계약서를 따른다.

### 7.4 임베드 및 사용자 토큰

- 토큰은 사용자에 귀속된다: JWT 페이로드 `{userId, iat, exp, v}`. 차트 정보는 토큰에 넣지 않는다.
- 임베드 코드: `<div data-chart-id data-auth-token>` — chart-id가 차트를 가리키고, auth-token(사용자 토큰)이 인증을 담당한다.
- 검증: 서명 + 만료 + DB의 is_active(회수). 유효한 사용자 토큰이면 해당 사용자 소유 차트 전체를 조회할 수 있다(차트별 권한 없음).
- 사용자 토큰 1개로 본인 소유 모든 차트를 임베드할 수 있다(차트마다 발급 불필요). 회수 시 그 사용자의 모든 임베드가 무효화된다.
- 로그인: 임시 자체 로그인(ID/PW) 골격만 MVP에 포함. 인증 구현은 개발 과정에서 후순위로 미뤄질 수 있으며, 추후 SSO로 교체한다(토큰 발급부만 교체, 임베드 구조 불변).
- MVP에서 만료는 길게 설정하고 회수로 관리한다.

### 7.5 화면 목록

전체 화면 및 상태 정의는 11장 화면 정의서를 참조한다. 요약하면 관리 콘솔(S1 목록, S2 편집[노코드], S3 임베드 코드, S5 데이터소스 관리, S7 토큰 관리, S6 로그인 골격)과 임베드 런타임(S4 렌더)으로 구성된다. MVP는 S1~S5·S7 + S6 골격이며, S2 SQL 탭은 2차다.

### 7.6 MVP 제외 항목 (명시적)

- SQL 직접 작성 UI (2차 — SQL 실행 엔진 자체는 MVP 포함)
- 본격 인증 구현 (임시 자체 로그인 골격만 MVP 포함, 구현은 후순위로 미뤄질 수 있음. SSO 교체는 추후)
- 멤버/사용자 관리 화면 (MVP는 수동 생성, SSO 전환 시 JIT 자동 생성)
- 조직 전환/조직 관리 UI, 외부 토큰 배포 보안. 본 서비스는 개인 사용자 단위로 스코프한다.
- DB 관리 기능 (테이블 생성/수정/데이터 편집). 본 솔루션은 조회 전용 뷰어이며 DB 편집은 하지 않는다.

### 7.7 결과 캐싱·갱신 모드 (대용량 대응, 코어)

기업 데이터는 매우 크다. 집계는 DB 안에서 실행되지만(GROUP BY pushdown), 임베드 차트가 사내 페이지에 깔리면 **페이지뷰마다 무거운 집계가 운영 DB를 때린다.** 해결은 실행 횟수를 줄이는 결과 캐싱이다.

- 차트별 갱신 모드 3종 (`mc_chart.refresh_mode`):

| 모드 | 동작 | 용도 |
|---|---|---|
| `live` | 매 요청 실행 | 소규모 테이블, 실시간성 필수 |
| `ttl` (기본, 1시간) | 캐시 반환, 만료 시 재계산 | 대부분의 기업 차트 |
| `manual` | 저장/[지금 갱신] 시에만 계산 — 완전 정적 | 무거운 통계, 일·주 단위 리포트 |

- 캐시 저장소: 메타 DB `mc_chart_cache` (JSONB) — 행 제한 1000행 덕에 결과가 수십 KB라 Redis 등 추가 인프라 불필요(Type A/B 배포 단순성 유지).
- 동작 규칙: ① S2 저장 시 실행 결과를 캐시에 시드(첫 임베드도 즉시 응답) ② TTL 만료 시 **stale-while-revalidate** — 일단 캐시를 반환하고 백그라운드 재계산 ③ 같은 차트의 재계산이 진행 중이면 중복 실행하지 않음(thundering herd 방지).
- 임베드 응답에 `computedAt` 포함 — S4 차트 하단에 "데이터 기준 {시각}" 캡션(옵션, 기본 켬)으로 정적 데이터임을 표시.
- 무거운 쿼리의 근본 해결은 고객 DB 측 집계 테이블/뷰(ETL)이며, S5 등록 화면 안내문으로 가이드한다.
- **표본 추출(보완 수단, MVP 포함):** 캐싱이 "DB를 덜 자주 때리는" 것이라면, 표본 추출은 "한 번 때릴 때 덜 아프게 때리는" 것이다. 노코드 구성에서 표본 비율(%)을 켜면 생성 SQL의 FROM에 `TABLESAMPLE SYSTEM (rate)`가 주입돼 **테이블 일부 블록만 스캔**(전체 스캔 회피)하고 평균·표준편차 등을 근사한다(생성규칙 3C). 합계·개수는 비율로 외삽하고, 결과엔 "근사치" 배지를 표시한다. 정확도 트레이드오프(표본=근사)를 사용자가 인지하도록 명시한다. 표본 추출은 집계 모드 전용이며 조인과 원본값 튜플 모드에서는 사용할 수 없다. 캐싱과 직교 — 함께 쓰면 캐시 수명 동안 표본 결과가 고정된다.
- 구현 단계: MVP = 모드 3종 + 저장 시 시드 + TTL 캐시 + 표본 추출(집계 모드, SYSTEM·% 입력) + 모든 차트 타입 원본값 튜플 모드. 2차 = stale-while-revalidate·[지금 갱신]·기준 시각 캡션. 후속 = 스케줄 갱신(매일 06:00 등)·표본 씨드 고정(REPEATABLE).

## 8. 비기능 요구사항 / 보안

### 8.1 SQL 실행 통제 (최대 리스크)

관리자가 직접 작성한 SQL이 DB에서 실행되는 구조이므로 다음을 필수로 적용한다.

- 차트 쿼리는 읽기 전용(read-only) DB 계정으로만 실행한다.
- SELECT 외 구문 차단(파서 검증).
- 쿼리 실행 타임아웃 및 결과 행 수 제한.

### 8.2 토큰 보안

- JWT 서명 검증 필수.
- 토큰은 사용자에 귀속되며 만료/회수로 유효성을 관리한다. 회수 시 해당 사용자의 모든 임베드가 무효화된다.
- 토큰은 DB에 **원문 저장**한다(해시 아님) — S3 임베드 모달이 발급된 토큰을 골라 스니펫에 끼우는 동선에 원문이 필요하다. 사내 전용 + 메타 DB 접근 통제를 전제로 한 의도적 트레이드오프이며, 외부 배포 전환 시 해시 저장 + 발급 시 1회 표시로 재설계한다.
- 인수인계서 4페이지의 Secret Key 서명 검증 계층은 유지하되 MVP 우선순위는 후순위로 둔다.

### 8.3 Type B 마이그레이션 안전성

- Flyway 마이그레이션은 `mc_` 접두사 테이블 범위 밖을 절대 변경하지 않는다.

## 9. 데이터베이스 스키마 (v5 — 개인 사용자 스코프·운영 최적화 반영)

`mc_` 접두사 적용. 테이블 5개: 사용자 / 사용자토큰 / 데이터소스 / 차트 / 차트캐시. 전체 DDL은 V1__init.sql(v5.0) 참조. **모든 화면의 모든 UI 요소 → DB 매핑은 `docs/DB스키마_UI매핑.md`** 참조. 저장 전략은 하이브리드(엔티티·조회 대상=정규화 컬럼 / 시각화 옵션·빌더 구성=JSONB).

운영 안정성 반영:
- `updated_at`은 애플리케이션 책임이 아니라 DB 트리거(`mc_touch_updated_at`)로 강제한다.
- S1 이름·설명 검색은 `pg_trgm` GIN 인덱스(`name`, `description` 각각)로 최적화한다.
- 개인 사용자 경계는 `owner_id`/`user_id`로 표현하고, `mc_chart`가 다른 사용자의 데이터소스를 참조하지 못하도록 `(datasource_id, owner_id)` 복합 FK를 둔다.

| 테이블 | 핵심 컬럼 | 비고 |
|---|---|---|
| mc_user | username, password_hash(임시), display_name, role, is_active | 개인 사용자. 인증 구현 전엔 수동 생성(S7 인라인). SSO 전환 시 password_hash 미사용 |
| mc_user_token | user_id FK, token(원문), expires_at(필수), is_active | 사용자 귀속 임베드 토큰(1인 1활성 토큰 — 본인 것만). id=JWT jti. 회수=is_active false |
| mc_datasource | owner_id, name, host, port, database_name, db_user, db_password_enc, max_pool_size, last_tested_at, last_test_ok | 개인 사용자가 등록한 업무 DB 연결. 비밀번호 AES-GCM 암호화. 데이터소스명은 사용자별 유니크 |
| mc_chart | owner_id, name, description(nullable), datasource_id FK, define_mode, sql_query, builder_config JSONB, chart_type, options JSONB, refresh_mode, cache_ttl_seconds | 개인 사용자 소유 차트. chart_type=대분류 4종(bar/line/pie/scatter), 소분류·외형은 options. builder_config는 노코드 복원용 |
| mc_chart_cache | chart_id PK·FK, result JSONB, computed_at, elapsed_ms, row_count, thumbnail, last_error, last_error_at | 차트 결과 캐시 (7.7). result는 항상 "마지막 성공" — 재계산 실패 시 에러만 기록하고 임베드는 성공 캐시로 계속 동작. thumbnail=S1 카드(후속). 차트 삭제 시 CASCADE |

### 9.2 mc_chart.options JSONB 키 명세 (구현 기준)

코드의 **단일 옵션 레지스트리(`chart-options/optionRegistry.ts` — `OptionDef[]`)** 와 1:1. 패널·서버 변환기·이 JSONB가 같은 목록을 공유한다(키 = `OptionDef.key` 점 경로). 모든 키는 선택(누락 시 레지스트리 기본값). 키는 옵션의 **존(zone)** 으로 묶인다 — Zone1 공통 / Zone2 축(직교 전용) / Zone3 대분류 전용. 미해당 키는 변환기가 무시·보존한다(7.2 전환 규칙). `chart_type`·`description`·`refresh_mode`·`cache_ttl_seconds`는 JSONB가 아니라 `mc_chart` 전용 컬럼이다.

```json
{
  "variant": "stacked",
  "title": "월별 매출", "titleH": "center", "titleV": "top",
  "colorMode": "palette", "palette": ["#5470C6", "…"], "colorMap": { "의류": "#FF0000" },
  "legend": { "show": true, "position": "bottom", "scroll": false },
  "tooltip": { "trigger": "axis", "valueFormat": "comma", "axisPointer": "line" },
  "dataLabel": false, "labelPosition": "top", "sortOrder": "desc",
  "grid": { "containLabel": true, "preset": "normal" },
  "xAxis": { "title": "카테고리", "rotate": 0, "splitLine": false, "min": null, "max": null, "scale": "value" },
  "yAxis": { "title": "매출", "unit": "원", "format": "comma", "rangeMode": "auto", "min": null, "max": null, "scale": "value", "splitLine": true, "secondAxis": false },
  "bar": { "width": null, "gap": 30, "borderRadius": 0, "normalize": false, "showBackground": false },
  "line": { "width": 2, "lineType": "solid", "showSymbol": true, "symbolSize": 4, "connectNulls": false, "areaOpacity": 0.3 },
  "pie": { "donutWidth": 40, "labelPosition": "outside", "startAngle": 90, "minAngle": 0 },
  "scatter": { "symbol": "circle", "symbolSize": 10, "bubbleField": null },
  "showComputedAt": true
}
```

- **Zone1(공통)**: `variant`·`title*`·`color*`·`legend`·`tooltip`·`dataLabel`·`labelPosition`·`sortOrder`·`showComputedAt`. 대분류 전환 시 유지.
- **Zone2(축, 직교 전용)**: `grid`·`xAxis`·`yAxis`. 막대·선·분포에만 적용, 원형 전환 시 숨김+보존. `xAxis.min/max/scale`은 숫자 X축(분포)에서만 유효 — 카테고리 X축에선 무시. `yAxis.format`+`yAxis.unit`이 합쳐져 `axisLabel.formatter`가 된다. `yAxis.secondAxis=true`면 이중축(시리즈별 `yAxisIndex` 부여).
- **Zone3(대분류 전용)**: `bar`·`line`·`pie`·`scatter`. 해당 대분류일 때만 존재, 대분류 전환 시 초기화. 위 예시는 키를 한눈에 보이려 전부 나열했으나 실제로는 현재 대분류 객체 1개만 저장된다.
- `sortOrder`는 서버에서 rows 정렬(원본 'none' / 'asc' / 'desc').
- `showComputedAt`: S4 "데이터 기준 {시각}" 캡션 표시 여부(기본 true, 캐시 모드일 때만).
- 각 옵션의 컨트롤·기본값·`showIf`·`echarts` 경로·`tier`(T1~T3)는 레지스트리가 보유한다. ECharts 조립 규칙은 별도 문서 "변환기 매핑 스펙(차트 옵션)" 참조.

### 9.1 임베드 토큰(JWT) 페이로드 설계

```json
{ "userId": 7, "jti": 42, "iat": 1781070087, "exp": 1812606087, "v": 1 }
```

- 토큰은 사용자에 귀속된다. 차트 정보를 넣지 않는다 — 사용자 토큰 1개로 본인 소유 모든 차트 임베드.
- `jti` = mc_user_token.id(PK). 회수 확인이 PK 단건 조회로 끝난다 — 토큰 문자열 대조 불필요.
- 검증: 서명 + 만료 + mc_user_token(jti 조회).is_active + mc_user.is_active.
- `exp`는 필수다. "무기한" 대신 긴 만료(기본 365일) + 회수로 관리한다(7.4).
- `v`(버전) 필드: 향후 파라미터 잠금, 차트별 권한 등 페이로드 확장 시 v2로 무중단 전환.
- 토큰 발급의 전제(누가 사용자인가)는 인증 구현체(임시 로그인 → SSO)가 담당하며, 임베드 검증 로직은 인증 방식과 무관하게 동일하다.

## 10. 개발 우선순위 (단독 개발 기준)

**MVP**
1. 코어 파이프라인: SQL 실행 엔진(검증·읽기전용·타임아웃·행제한) + chartId로 실행 → ECharts JSON → SDK가 div 렌더 (토큰 검증 스텁)
2. 사용자 토큰: mc_user 수동 생성 + 토큰 발급/검증/만료/회수 (단일 검증 필터)
3. 시각화 옵션: 막대/선/원형/분포(4종), 색(팔레트/개별), 축, 정렬, 라벨, 범례 + 미리보기
4. Admin: 목록(S1) + 노코드 빌더(S2, SQL 생성기) + 임베드 코드(S3) + 데이터소스 관리(S5) + 토큰 관리(S7)
5. 다중 데이터소스: 동적 커넥션 풀 + 자격증명 암호화
6. 결과 캐싱: 갱신 모드 3종(live/ttl/manual) + 저장 시 시드 + TTL 캐시 (7.7 — 대용량 대응 코어)
7. 임시 로그인 골격(S6) — 인증 구현은 미뤄질 수 있음

**2차**
8. SQL 에디터 모드(S2 옵션 2): 에디터 UI + 스키마 탐색기 + DB 에러 노출 + 노코드→SQL 전환 규칙
9. 캐싱 고도화: stale-while-revalidate, [지금 갱신], 데이터 기준 시각 캡션

**후속**
10. SSO 교체, 쿼리 파라미터({{}}), 시리즈 분할(breakout), 대시보드, 알림/스케줄, 캐시 스케줄 갱신 (날짜 버킷팅은 v1.3에서 MVP로 편입)

## 11. 화면 정의서 (Full Scope)

전체 기능 범위의 화면과 상태를 모두 정의한다. 우선순위(코어/보조/후속)에 따라 단계적으로 구현한다. 각 화면의 레이아웃·치수·컴포넌트·Figma 프레임 목록을 포함한 상세 설계는 별도 문서 "차트 솔루션 화면설계서 v2.5(Figma 작업용)"를 참조한다. 본 장은 그 요약이다.

### 11.0 UI 구조 결정 사항

- 내비게이션: 사이드바 없이 얇은 상단 바(56px) 하나로 통일한다. 이동 목적지가 적고(목록·설정), S2 편집 화면의 가로 공간 확보가 우선이다. 화면이 늘어나면 접이식 사이드바로 전환한다.
- S2 편집은 정의와 차트를 분리하지 않고 3분할 한 화면(테이블·컬럼 패널 / 노코드 구성+결과 탭 / 차트+옵션 — SQL 탭(2차)에선 스키마 탐색기/에디터+결과)을 유지한다. 구성 수정과 차트 확인의 왕복을 없애기 위함이며, Grafana·Metabase·Redash가 같은 구조다. 쿼리를 독립 엔터티로 분리(재사용 1:N)하는 것은 수요 확인 시 후속으로 검토한다.
- 옵션 확장 대비: 옵션 패널은 접이식 섹션 + 옵션 검색(자리 확보)으로 옵션 수십 개 규모까지 같은 레이아웃에서 수용한다(Grafana 패턴).
- 벤치마킹: Grafana(옵션 패널 구조), Redash(스키마 브라우저·SQL 레이아웃), Metabase(상단 바 내비게이션).

### 11.1 화면 전체 목록

| ID | 화면 | 영역 | 우선순위 | 비고 |
|---|---|---|---|---|
| S1 | 차트 목록 | 관리 콘솔 | 코어 | 카드형 + 썸네일 |
| S2 | 차트 편집 | 관리 콘솔 | 코어(최우선) | 노코드(기본) / SQL 탭(2차) / 옵션 패널 |
| S3 | 임베드 코드 | 관리 콘솔(모달) | 코어 | 사용자 토큰 선택 + 코드 복사 |
| S4 | 임베드 렌더 | 임베드 런타임 | 코어 | 외부 페이지의 실제 차트 |
| S5 | 데이터소스 관리 | 관리 콘솔 | 코어 | 다중 DB 등록/테스트/삭제 |
| S6 | 로그인 (임시 자체) | 관리 콘솔 | 골격만 | 추후 SSO 교체, 개발 중 우회 가능 |
| S7 | 토큰 관리 | 관리 콘솔 | 코어 | 사용자별 임베드 토큰 발급/회수 |

### 11.2 화면별 상태 요약

상세는 화면설계서 v2.5 참조. 핵심 상태만 요약한다.

- S1: 기본 / 빈 상태 / 삭제 확인(임베드 영향 경고). 카드에 차트 ID(#id)·설명 1줄 표시. 페이지 헤더에 검색(이름·설명 부분일치). 카드 호버 액션에 복제(2차)
- S2 추가 상태: 미저장 이탈 확인 모달
- S2(노코드, MVP): 신규(데이터소스 미선택·셀렉트 펼침 포함) / 구성 중(테이블 선택 시 [원본 데이터] 탭 자동 표시 — 최대 1,000행 스크롤) / 로딩 / 성공([실행 결과]·[원본 데이터] 탭 전환 — 집계와 세부 데이터 모두 확인) / 에러(생성 전 검증 400, 친화적 문구 — DB 에러 미노출) / 저장 / 소스변경확인 모달(구성 초기화 경고). 실행 실패 시 차트는 이전 상태 유지. 개별 색 지정은 실행 성공 후 활성(동적 UI)
- S2(SQL 탭, 2차): 작성 / DB 에러 그대로 노출 / 노코드→SQL 전환 경고(단방향)
- S3: 기본(토큰 선택+스니펫 복사) / 토큰 없음(S7 유도)
- S4: 로딩 / 정상 / 토큰 만료·에러(호스트 페이지 비파괴, 원인 미구분 표시)
- S5: 목록 / 빈 상태 / 추가 모달(연결 테스트) / 삭제 확인(사용 중 차트 N개 경고)
- S6: 기본(ID/PW 골격) / 실패 / (개발 중) 우회
- S7: 목록 / 발급 / 회수 확인(해당 사용자 전체 임베드 무효화 경고)

### 11.3 구현 단계 경계

- MVP: S1~S5, S7 전체 + S6 골격. S2는 노코드만(SQL 탭은 비활성 표기).
- 2차: S2 SQL 탭(에디터·스키마 탐색기·DB 에러 노출·전환 규칙).
- 후속: SSO 교체, 쿼리 파라미터, 시리즈 분할(breakout), 대시보드, 알림.
- 어느 단계든 핵심 상태(빈/로딩/에러)는 생략하지 않는다 — 상태 누락이 구현 정체의 가장 흔한 원인이다.

## 12. 향후 과제 (Post-MVP)

- 개인 계정 SSO(SAML/OAuth) 로그인 — 회사 통합로그인(타 솔루션 공통 IdP) 연동 대비. 도입 시 S7은 "내 토큰" 셀프서비스로 축소(본인 토큰만 발급·회수)
- 차트 종류 확장(파이, 영역, 산점도 등) 및 시각화 옵션 심화
- 토큰 짧은 만료 + 자동 재발급 파이프라인 — 전환 시 SDK에 토큰 콜백(`getToken`) 방식 병행 (JWT `v` 필드로 무중단 전환)
- SDK 명령형 API 병행: `ChartSDK.render(el, { chartId })` — SPA(React/Next)처럼 DOM 스캔 타이밍이 어긋나는 환경 대응 (선언형 div 스캔과 공존)
- 차트 미리보기 썸네일 캐싱 고도화
- 대시보드(여러 차트 묶음) 기능
