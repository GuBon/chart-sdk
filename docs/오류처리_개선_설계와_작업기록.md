# 오류처리 개선 설계와 작업기록

**문서 버전:** v0.1 — 전수 QA 발견 → 3-레이어 오류처리 설계 + 차트 복제(M3) 확정, 구현 착수 (2026-08-12)<br>
**관련 문서:** [인터페이스 계약서](인터페이스_계약서.md) · [코드구조 안내](코드구조_안내.md) · [화면설계서](화면설계서.md) · [제품요구사항](제품요구사항.md)<br>
**상태:** **구현 중** — §6 진행 상황 참조

이 문서는 하나의 작업 흐름을 처음부터 끝까지 기록한다: ① 전수 QA 테스트로 오류를 발견하고 ② 그 오류들을 성격별로 분류한 뒤 ③ 개별 수정이 흩어지지 않도록 하나의 오류처리 뼈대를 설계하고 ④ 발견별 처리를 확정하고 ⑤ 그 위에서 구현한다. "무엇을 고쳤나"뿐 아니라 **"왜 그렇게 고치기로 했나"**를 남기는 것이 목적이다.

## 설계 선택 근거

| 개선 목표 | 현재 선택 | 검토 대안 | 선택 이유와 현재 이점 | 한계·검증 |
|---|---|---|---|---|
| 클라이언트 유발 오류가 500으로 오보되지 않게 | `ResponseEntityExceptionHandler` 상속으로 프레임워크 예외 부류 통째 변환 | 표준 예외 4개만 화이트리스트 핸들러 추가 | 다음에 나올 미지의 스프링 예외까지 자동 커버(화이트리스트 아님) | 진짜 미지 예외만 500 — envelope에 requestId로 추적 |
| 개별 오류 수정이 제각각 흩어지지 않게 | 예방(전처리)·도메인 예외·핸들러 변환 3-tier 규칙 고정 | 발견마다 그 자리에서 임기응변 수정 | 9건 전부 한 뼈대 위에 앉아 일관·예측 가능 | tier 배치 기준을 §2에 명문화 |
| 오류 메시지를 사용자 친화적으로 | 서버 message 품질 + code 기반 프런트 분기 | 프런트에서 오류 문구를 개별 하드코딩 | 프런트가 이미 서버 message를 그대로 노출 → 서버만 고치면 대부분 반영 | 알려진 code override 맵으로 문구 통제 |

전체 기술 구조와 책임 경계는 [코드구조 안내](코드구조_안내.md)를 따른다.

## 0. 배경 — 전수 QA 테스트

### 0.1 방법

- **대상:** `localhost:8080`(Spring Boot) · `localhost:3000`(Next.js Admin) · `localhost:5433`(PostgreSQL)
- **API 직접 퍼징:** 8개 컨트롤러 전수, 103개 요청 시나리오(curl). 잘못된 타입·경계값·SQL 인젝션·다중 데이터소스 조인·낙관적 락 충돌 포함.
- **브라우저 자동화:** 실 Chromium으로 4회 실행(선택자 보정 반복). 콘솔 에러·네트워크 4xx/5xx·토스트/인라인 에러 문구를 전부 캡처·분류. S1(목록)·S2(빌더)·S4(임베드 런타임)·S5(데이터소스)·S7(토큰) 커버.
- **안전 규칙 준수:** 데이터소스 삭제 0건, 차트 삭제 정확히 1건(QA가 만든 임시 차트만). 시드 차트 6개(id 12·13·16·17·18·19)는 그대로 보존.
- **상태코드 분포:** 400×39, 200×31, 500×12, 404×10, 401×8, 기타×3.

### 0.2 진단 원칙 — stale 프로세스 분리

실행 중이던 `:8080` 프로세스가 최신 빌드를 반영하지 못하는 상태여서, 코드 결함과 "오래된 프로세스" 문제를 분리하기 위해 **동일 코드베이스를 최신 빌드로 재기동한 진단용 인스턴스(:8081)** 에서 모든 500을 교차 재현했다. `:8081`에서도 재현되면 코드 결함, `:8081`에서 정상이면 프로세스 문제로 판정했다.

## 1. 발견된 오류 (9건)

### 1.1 성격별 4분류

개별 오류를 "무엇이 실제로 잘못됐는가"로 나누면 처방이 달라진다.

| 분류 | 뜻 | 해당 항목 |
|---|---|---|
| **A. 계약 위반(거짓말)** | 상태코드 자체가 틀림 — 클라이언트 잘못인데 500, 없는 사용자인데 400 | High, M2 |
| **B. 메시지 품질(불친절)** | 상태코드는 맞는데 메시지가 뭉뚱그려짐 | M1 |
| **C. 입력 경계(조용한 왜곡)** | 이상값을 거부/기본값 처리 안 하고 몰래 클램프 | L1, L3 |
| **D. 마감 누락(프런트/운영)** | 기능·예외처리·빌드 상태 | M3, L2, L4, Ops |

A·B는 사실상 한 뿌리 — "예외를 의미 있는 계약으로 변환하지 못하고 catch-all로 흘림". 그래서 §2의 공통 뼈대 하나로 동시에 해결된다.

### 1.2 발견 상세

| # | 발견 | 재현 | 원인 |
|---|---|---|---|
| **High** | 숫자 파라미터에 문자, 없는 라우트, 잘못된 메서드 → 전부 500 | `GET /api/v1/charts/abc` → 500 (실제 `MethodArgumentTypeMismatchException`) · `GET /api/v1/does-not-exist` → 500(`NoResourceFoundException`) · `POST /health` → 500(`HttpRequestMethodNotSupportedException`) | `ApiExceptionHandler`의 `@ExceptionHandler(Exception.class)` catch-all로 낙하. :8081에서도 재현 → 코드 결함 |
| **Ops** | 노코드 빌더에서 테이블 선택 시마다 미리보기 500 | `:8080` 500 / `:8081` 200 (같은 요청) | 코드 아님. 오래 떠 있는 JVM이 변경된 클래스를 반영 못 함 → **재시작 필요** |
| **M1** | 데이터소스 저장 실패 사유가 뭉뚱그려짐 | 포트 `0`/`99999`, 이름 중복이 전부 `"Request violates data constraints."` | 포트 범위·이름 중복을 앱에서 사전 검증하지 않고 DB CHECK/UNIQUE 위반을 통째로 잡음 (`DatasourceService.validate()`가 이름·비밀번호만 검사) |

| **L1** | 토큰 만료일 상하한 없음 | `expiresInDays:-5` → 조용히 1일 클램프 · `999999` → **서기 4764년** 토큰 발급 | `IssueTokenRequest`에 범위 검증 없음. 서비스는 하한만 `Math.max(1, days)` |
| **L2** | 임베드 코드 복사 버튼이 클립보드 거부를 미처리 | 클립보드 쓰기 거부 환경에서 미처리 `NotAllowedError`, 사용자는 조용한 실패만 봄 | `EmbedModal.copy()`에 `try/catch` 없음 |

| **L4** | `/charts/new` 최초 진입 시 React hydration 경고 100% 재현 | 콘솔 경고 4회 모두 | 콘솔 캡처로 컴포넌트 특정 실패. 기능 무영향·프로덕션 양상 다름 → 최저 우선, 별도 조사 |

## 2. 개선 설계 — 3-레이어

전체를 관통하는 불변식:

> **모든 4xx는 구체적인 `code` + 사용자 친화 `message`를 가진다. `500`은 오직 "우리가 예상 못한 진짜 서버 버그"일 때만 나오며, 항상 `requestId`를 동반한다. 클라이언트가 유발할 수 있는 것은 절대 500이 아니다.**

### Layer 1 — 에러 계약(envelope)

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "포트는 1–65535 범위여야 합니다.",
    "fields": { "port": "1–65535 범위여야 합니다." },
    "requestId": "a1b2c3d4"
  }
}
```

| 필드 | 규칙 |
|---|---|
| `code` | 기계 판독용 안정 문자열(SCREAMING_SNAKE). 프런트가 이걸로 분기한다 |
| `message` | 사람이 읽는 문구. 사용자 대면은 한국어 |
| `fields?` | **필드 검증 오류일 때만** `{필드명: 메시지}` |
| `requestId?` | MDC의 요청 ID(`RequestIdFilter`가 심음). **5xx는 필수**, 4xx는 선택 |

**code 레지스트리**(안정 계약):
- 입력: `VALIDATION_FAILED` · `TYPE_MISMATCH` · `MISSING_PARAMETER` · `INVALID_REQUEST`
- 라우팅: `NOT_FOUND` · `METHOD_NOT_ALLOWED` · `UNSUPPORTED_MEDIA_TYPE` · `NOT_ACCEPTABLE`
- 도메인(기존): `CHART_NOT_FOUND` · `VERSION_CONFLICT` · `DATASOURCE_IN_USE` · `SQL_NOT_SELECT` · `INVALID_IDENTIFIER` · `SNAPSHOT_NOT_READY` · `QUERY_TIMEOUT` · `DATASOURCE_NAME_RESERVED` …
- **신규:** `USER_NOT_FOUND` · `PORT_OUT_OF_RANGE` · `MAX_POOL_SIZE_OUT_OF_RANGE` · `DATASOURCE_NAME_DUPLICATE`
- 최후: `INTERNAL_ERROR`(유일한 진짜 500)

### Layer 2 — 서버 처리 3-tier

원칙 한 줄: **"값이면 DTO, 도메인·존재면 서비스, 경쟁이면 DB + 핸들러."**

- **Tier 1 · 예방(전처리·검증):** 애초에 예외를 안 만든다.
  - DTO Bean Validation(`@Valid`+`@Min/@Max/@Pattern`): 순수 값·형식 경계.
  - Service `validate()`: 도메인 규칙 + 존재 검증(404 의미가 필요한 것).
- **Tier 2 · 도메인 예외:** 비즈니스 규칙 위반은 `ApiException(status, code, message)`로 **구체 code와 함께** 던진다(예상된 오류).
- **Tier 3 · 프레임워크/미지 예외:** `ApiExceptionHandler`가 `ResponseEntityExceptionHandler`를 상속해 부류 전체를 변환.

| 예외 | 상태 | code |
|---|---|---|
| `MethodArgumentTypeMismatch` | 400 | `TYPE_MISMATCH` |
| `MissingServletRequestParameter` | 400 | `MISSING_PARAMETER` |
| `MethodArgumentNotValid` | 400 | `VALIDATION_FAILED` (+`fields`) |
| `HttpMessageNotReadable` | 400 | `INVALID_REQUEST` |
| `HttpRequestMethodNotSupported` | 405 | `METHOD_NOT_ALLOWED` |
| `NoResourceFound`/`NoHandlerFound` | 404 | `NOT_FOUND` |
| `DataIntegrityViolation` | 400/409 | **제약명 → 구체 code**(백스톱) |
| `ApiException` | 그대로 | 그대로 통과 |
| `Exception`(미지) | 500 | `INTERNAL_ERROR` + `requestId` + 서버 로그 |

`ResponseEntityExceptionHandler`가 계산한 응답 헤더도 그대로 보존한다. 특히 405의 `Allow`, 415/406의 협상 관련 헤더를 envelope 변환 과정에서 버리지 않는다. 406에서도 오류 envelope를 쓸 수 있도록 오류 응답 `Content-Type`은 JSON으로 명시한다.

### Layer 3 — UI 전달 표준

프런트는 `apiErrorMessage(error, fallback)`과 `apiFieldError(error, field)`를 단일 접근점으로 사용한다. 전자는 5xx의 `requestId`를 사용자 메시지에 포함하고, 후자는 Bean Validation의 `fields`를 해당 입력 아래에 표시한다.

| 오류 상황 | 상태/code | 전달 방식 |
|---|---|---|
| 폼 필드 검증 | 400 `VALIDATION_FAILED` + `fields` | 해당 필드 아래 인라인 |
| 폼 전역 규칙 | 400/409 (fields 없음) | 폼 하단 배너(기존 `.text-danger`) |
| 행동 가능 오류 | 409 `VERSION_CONFLICT`, 503 `SNAPSHOT_NOT_READY` | 메시지 + [새로고침]/[다시 시도] 버튼(code 분기) |
| 배경 작업(저장·갱신) | 각종 | 토스트(기존) |
| 미지 500 | `INTERNAL_ERROR` | 토스트 + "문제가 지속되면 요청 ID `{requestId}`로 문의" |

**공통화:** `ApiError`에 `fields`·`requestId` 필드를 추가하고 공통 메시지·필드 헬퍼를 사용한다. 모달마다 요청 ID 조립이나 필드 추출을 손으로 반복하지 않는다.

## 3. 발견별 처리 결정 (확정)

| # | 처리 위치 | 확정 결정 |
|---|---|---|
| **High** | Tier 3 | `ResponseEntityExceptionHandler` 상속으로 프레임워크 예외 부류 통째 |
| **Ops** | 운영(별개) | 재시작 + `/actuator/info`에 빌드 커밋·시각 노출(재발 시 즉시 식별) |
| **M1** | Tier1 + Tier3 | 포트 범위 = 검증, 이름 중복 = DB 제약 → `DATASOURCE_NAME_DUPLICATE` 매핑 |
| **M2** | Tier1 | `issue()` 앞 존재 검증 → `404 USER_NOT_FOUND` |
| **M3** | UI | **확정 — §4** |
| **L1** | Tier1 | `@Min(1)@Max(3650)` — 조용한 클램프 대신 정직한 400 |
| **L2** | Layer3 | `try/catch` + 실패 시 코드 자동선택 폴백 |
| **L3** | Tier1 | `pageSize<=0`이면 기본값(8)로 — 클램프 일관화 |
| **L4** | 조사 | 원인 특정 전까지 보류(프로덕션 무해·기능 무영향, 최저 우선) |

전 항목이 3-tier + UI 매트릭스라는 하나의 뼈대 위에 앉는다. 개별 수정이 흩어지지 않는 것이 이 설계의 핵심이다.

토큰 만료 기간은 순수 값 경계이므로 `IssueTokenRequest`의 Bean Validation이 단일 권위다. 따라서 HTTP 계약은 항상
`400 VALIDATION_FAILED + fields.expiresInDays`이며, `TokenService`는 사용자 존재·토큰 회전 같은 도메인 규칙만 담당한다.

## 4. 차트 복제(M3) UI — 확정

백엔드 `duplicate`는 이미 완성되어 있다(`ChartRepository.duplicate`): 복사본 이름을 **`"원래이름 (복사)"`** 로 자동 생성, 데이터소스 junction + **캐시 스냅샷까지 복사**(복사본이 목록에서 즉시 렌더), owner 범위 + 없는 id면 404. UI는 이를 배선만 하면 된다.

**확정 사항:**
- **배치:** 카드 hover 코너에 복제(lucide `Copy`) 아이콘 추가, 기존 삭제(`Trash2`) 아이콘과 나란히. 색은 중립(삭제는 danger). 주 액션 2개(편집·임베드)는 그대로.
  - *근거:* 삭제가 이미 "hover 코너 아이콘 = 가끔 쓰는 부차 액션" 패턴. 복제도 같은 성격이라 같은 자리에 묶는 것이 일관적. 버튼 행에 3번째 버튼을 넣으면 각 버튼이 좁아지고 복제가 편집만큼의 자리를 차지할 이유가 없음. 오버플로 메뉴는 액션 2개엔 과함.
- **확인:** 가벼운 확인 모달 1회 — "'{차트명}'을 복사할까요?" → [취소]/[복사]. **문구는 삭제만큼 경고조로 하지 않는다**(삭제의 "모든 임베드에서…" 같은 무거운 경고 없음).
  - *근거:* 복제 아이콘이 삭제 아이콘 바로 옆이라 오클릭 위험이 실재. 확인 한 번으로 이를 막되, 비파괴 액션이므로 경고 문구는 가볍게. (대안이던 "즉시 복제 + 실행취소 토스트"는 흐름은 가볍지만 actionable 토스트 신규 구현이 필요 → 기존 `DeleteChartModal` 미러링이 더 싸고 일관적이라 확인 모달 채택.)
- **완료 후 동작:** **목록 유지.** 복제 성공 → 서버가 반환한 실제 이름으로 `"‘{복제명}’ 차트를 복제했습니다."` 토스트 → 목록 갱신. 현재 페이지·필터에 따라 새 카드가 바로 보이지 않아도 성공 여부와 실제 이름은 항상 확인할 수 있다. 편집기로 튀지 않는다.
  - *근거:* "여기 하나 더 복사해둬"의 심상에 맞고 화면이 갑자기 안 바뀌어 덜 놀람. 바로 수정하려면 새 카드에서 편집을 누르면 됨.

배선 규모: ① `chartsApi.duplicate(id)` 추가 → ② `DuplicateChartModal`(DeleteChartModal 미러링) → ③ 카드 hover 코너 Copy 아이콘 → ④ 확인 시 duplicate 호출 + 토스트 + 목록 갱신.

### 6.2 구현상 편차 (설계 대비)

- **M3 완료 후 피드백:** 페이지 2·필터·정렬 상태에서는 최신 복제 카드가 현재 목록에 보이지 않을 수 있어, reload만으로 성공을 알리는 구현을 폐기했다. 서버 응답의 실제 복제 이름을 토스트에 표시하고 현재 목록 상태는 유지한다.
- **L4·Ops는 후속:** 코드 결함이 아니거나(Ops=재시작) 조사가 선행되어야 해(L4) 이번 배치에서 제외.

각 단계 완료 시 이 표를 갱신한다. 원 QA 발견 로그·스크린샷·검증 스크립트는 세션 스크래치 디렉터리에, 요약은 프로젝트 루트 `QA_전수테스트_결과.md`에 있다.
