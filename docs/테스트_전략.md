## 계층별 책임 경계 (무엇을 어디서 잡나)

- **빌더 로직**: admin 단위가 순수 함수로, E2E가 UI 경유로 이중 커버. SQL 문자열 정합성은 서버 단위가 최종 권위.
- **SDK**: 분기 로직은 SDK 단위(echarts·fetch mock)로 검증한다. **실제 canvas 렌더**는 Chromium S3 E2E가 `/sdk.js`+MSW API 구간을, 라이브 스위프가 실제 백엔드·CORS·토큰까지 포함한 전 구간을 담당한다(jsdom/happy-dom은 canvas 미구현이라 단위 테스트에서는 echarts를 mock).
- **레이아웃 규칙**: `chart-options/layout-contract-cases.json`을 서버 JUnit과 Admin Vitest가 함께 읽어 Java 운영 변환기와 MSW 미러의 글꼴 기반 높이 수식·경로 결과를 직접 지정/FHD/custom 세로 크기 사례까지 고정한다. `admin/lib/display.test.ts`는 논리 크기 변경에 따른 자동 재계산과 직접 지정 px 고정을, S2 E2E는 같은 계약의 UI 안내·실제 전환과 논리 canvas의 CSS fit·패널별 복원·포커스 흐름을 검증한다. SDK 단위는 초기 setOption과 ResizeObserver 콜백을 검사해 임베드 CSS 리사이즈가 모든 fontSize를 패치하지 않고 제목 폭만 갱신함을 고정한다.
- **표본 계약**: `chart-options/sampling-contract-cases.json`을 서버·Admin이 함께 읽어 SUM/COUNT가 선택된 표본값 그대로이고 어떤 집계에도 비율 배율을 적용하지 않는 계산을 고정한다. 서버는 INDEX_RANDOM·RESULT_RANDOM 숨은 시리즈별 n/모멘트→sampling v6 구간 계산과 캐시 보존을, Admin mock은 같은 응답 형태를, SDK는 표본 집계/통계 추정/정확 실행·95% 배지·경고 전파를 검증한다.
- **관계 원본·결과 표본**: 서버 단위는 relationType/갱신 상태 API와 RESULT_RANDOM SQL 구조를 고정하고, DuckDB in-memory 테스트는 reservoir SQL을 실제 실행한다. 서버 통합은 PostgreSQL 17에서 TABLE·VIEW·MATERIALIZED VIEW와 seed 재현성을 검증한다. Admin E2E는 VIEW 배지/선택·조인 표본 유지와 raw 지연 요청을 검증한다.
- **데이터 카탈로그**: Admin 단위는 `/data/{datasourceId}/{schema}/{relation}/{chartId}` 인코딩을, E2E는 소스→스키마 검색→관계 컬럼→관련 차트 동선을 검증한다. 서버 통합은 `mc_chart_datasource` 기반 보조 조인 소스 필터와 `builder_config.table` 기준 관계 필터를 실제 PostgreSQL에서 고정한다.
- **구조 경계**: Admin 단위는 차트·관계 표시 규칙의 단일 권위를, 서버 단위는 목록 조회 값 객체와 데이터소스 서비스의 검증·행 매핑을 고정한다. Playwright는 공통 목록 훅으로 바뀐 뒤에도 삭제 후 페이지 보정, 배치 미리보기, 데이터 카탈로그 이동이 동일함을 검증한다.
- **공간 Point**: Admin 단위는 카탈로그 타입 판정·폼 검증·MSW SQL을, 서버 단위는 최종 PostGIS SQL과 페더레이션 거부를 맡는다. `SpatialPointIT`는 격리된 PostGIS의 실제 geometry/geography 데이터를 WGS84로 변환해 QueryRows와 ECharts option까지 확인하고, S2 E2E는 실제 대한민국 좌표 표본의 선택·결과표·canvas를 검증한다.
- **페더레이션**: SQL 생성은 서버 단위(`FederatedSqlBuilder`), 실행은 서버 단위 DuckDB reservoir + 서버 통합 + 라이브 스위프(실제 두 물리 PG를 DuckDB ATTACH로 조인).
- **임베드·CORS·토큰**: S3 mock E2E가 모달에서 생성한 HTML만 빈 문서에 붙여 `/sdk.js` 배포·`data-api-base`·Bearer 요청·canvas 렌더를 고정한다. 라이브 스위프는 실제 EmbedController → CORS → JWT/DB 토큰 → canvas 전 구간을 담당하고, 서버 단위는 JWT 검증(`JwtTokenProviderTest`)을 맡는다.

## 라이브 스위프 (실인프라 검증)

전제: 백엔드 :8080, 프론트 :3000(실백엔드 연결), 실데이터소스 2개(docker-user-db id1 / tandanji-db id2), CORS 허용 origin에 :3001 포함([CorsConfig.java](server/src/main/java/com/chartsdk/config/CorsConfig.java)).

절차(스크립트가 자동 수행): ① 사전 점검 + `__sweep_` 잔재 청소 → ② S1/S5/S7 UI 스모크 → ③ API 직접 run-builder(단일소스 + 크로스소스 페더레이션) → ④ 차트 저장(캐시 시드) → ⑤ SDK 정적서버(:3001)에서 `demo/embed.html` 렌더(canvas) + 위조 토큰 401 → ⑥ 정리(sweep 차트 삭제·토큰 회수).

규약: 쓰기 데이터는 **`__sweep_` 접두 + finally 정리**. 실데이터소스는 읽기만. 스크립트는 스크래치패드에 두고 **커밋하지 않는다**(실인프라·포트 하드코딩 의존).

## 알려진 한계·후속

- **소유권 격리 미완**: 스키마·임베드 읽기 검사(`owner_id=? OR owner_id IS NULL`)·토큰 신원은 구현됐으나, 로그인 부재로 차트 생성 시 `owner_id`가 NULL → `OR NULL` 탈출구로 임의 토큰이 임의 차트 접근. auth 구현 시 owner_id 주입 + 탈출구 제거로 완성(설계는 됨).
- **사용자 삭제 API 부재**: `POST /users`만 있고 `DELETE` 없음 → 라이브 스위프 `__sweep_user` 정리 불가. S7에 사용자 삭제/비활성 필요.
- **프론트 컴포넌트 렌더 단위 테스트 없음**: React 컴포넌트는 E2E로만 커버(현 전략상 의도 — 컴포넌트 단위는 도입 안 함).
