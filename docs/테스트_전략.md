# 테스트 전략 (수치·실행법 단일 관리)

**이 문서가 테스트 현황의 SSOT다.** 다른 문서는 절대 수치를 복사하지 않고 이 문서를 참조한다.
**최종 갱신:** 2026-08-19 (MSW E2E 전수 정상화·라우트 예열·병렬 실행, CI `admin-e2e` 게이트, 아이디 canonical·세션 세대·관리자 스냅샷 전용 미리보기 테스트 추가)

## 테스트 선택 근거

| 개선 목표 | 현재 선택 | 검토 대안 | 선택 이유와 현재 이점 | 한계·검증 |
|---|---|---|---|---|
| 빠른 UI 회귀와 실제 운영 계약 동시 검증 | 단위→MSW Playwright→실백엔드 E2E→통합→k6 계층 | mock-only, real-only, 수동 검수 | 각 계층이 다른 실패를 맡아 속도와 사실성을 균형 | 실제 인프라 수명주기 관리 비용. CI job 분리 |
| Java 운영 변환기와 TS mock drift 탐지 | 공용 fixture+전체 JSON parity | 예제 몇 개 육안 비교, 한쪽 snapshot만 유지 | 같은 입력을 양쪽이 독립 계산해 누락 옵션까지 발견 | 이중 구현 자체는 남음 |
| 테스트 환경 결정성 | 전용 port·PID·readiness·distDir·대표 라우트 예열 | existing server 재사용, 긴 sleep | 실행 artifact 정체성과 준비 상태를 확인하고, dev 서버의 최초 컴파일 비용을 테스트 밖으로 빼 flaky 원인을 줄임 | 콜드 예열 ~25초는 별도 예산 필요 |
| MSW E2E 실행 시간 | `fullyParallel` + 로컬 4·CI 2 worker | 단일 worker 순차, 파일 단위 샤딩 | MSW 상태는 브라우저 컨텍스트(=테스트) 안에서만 살아 병렬이 안전. 106개 18분→약 5분 | dev 서버 1대를 공유하므로 worker 수를 CPU에 맞춰 제한 |
| 문서 수치 drift 방지 | 절대 테스트 수치는 이 문서만 소유 | 모든 설계 문서에 숫자 복사 | 변경 시 수정 지점이 한 곳 | 실행 결과로 정기 대조 필요 |

테스트 관련 사건과 검증 근거는 [개발 문제해결 이력](개발_문제해결_이력.md)을 참조한다.

## 2. 기본 검증

```bash
npm run typecheck
npm run test:unit
npm run build

cd server
./gradlew test --no-daemon
cd ..
npm run test:parity
```

`test:parity`는 대상 Admin Vitest와 Server JUnit을 자체 실행해 snapshot을 새로 만든 뒤, 8종 기본값과 구성 사례 18개의 전체 option JSON이 같은지 검사하고 임시 파일을 제거한다. Gradle의 `UP-TO-DATE` 여부나 이전 실행 순서에 의존하지 않는다. 이 경로는 외부 DB 없이 결정적으로 실행돼 CI `verify` job이 항상 수행한다.

## 3. MSW 브라우저 E2E

```bash
npm run test:e2e
```

- Admin: `http://localhost:3100`
- `NEXT_PUBLIC_E2E_MSW=true`
- Next 산출물: `admin/.next-e2e`
- 테스트: `admin/e2e`
- 역할: 많은 UI 분기와 실패 상태를 빠르고 결정적으로 검증
- 준비 단계(`e2e/global-setup.cjs`): `/sdk.js` 준비 → 3100 미기동 시 dev 서버 spawn → 대표 라우트 12개를 병렬 예열(콜드 ~25초, 예열된 서버는 1초 미만). 예열 실패(200 이외)는 즉시 실패로 보고한다.
- 병렬: `fullyParallel: true`, worker 로컬 4·CI 2(`E2E_WORKERS`로 조정). MSW 워커·mock 상태·sessionStorage 초안은 브라우저 컨텍스트 단위라 테스트 간 공유가 없다.
- 결정성 규칙: 미리보기 canvas 존재 확인은 `.first()`(ECharts 는 진행 렌더·hover 레이어로 canvas 를 여러 장 만들 수 있어 strict locator 는 즉시 실패). 미저장 변경 뒤 새로고침하는 시나리오는 세션 초안(300ms 디바운스) 기록을 `expect.poll` 로 기다린 뒤 복구 안내를 명시적으로 처리한다.
- CI: `admin-e2e` job 이 배포 게이트로 전 시나리오를 실행하며 실패 시 `admin/test-results/`·`admin/playwright-report/` 를 artifact 로 보존한다(CI 는 1회 재시도, 재시도 통과는 flaky 로 리포트에 남는다).

MSW는 운영 서버 대체물이 아니다. Java SQL, datasource 암호화, DB catalog, 세션·CSRF·CORS, 임베드 키 DB 검증은 아래 실백엔드 계층이 맡는다.

## 4. 실백엔드 브라우저 E2E

```bash
npm run test:e2e:real
```

전용 환경:

| 구성 | 주소/자원 | 격리 방식 |
|---|---|---|
| PostGIS 메타+소스 DB | `localhost:56432/chartsdk_e2e` | `real-e2e` compose profile, tmpfs, 매 실행 재생성 |
| Spring | `http://localhost:8082` | 전용 PID tree |
| Admin | `http://localhost:3001` | MSW=false, `.next-realtest` |
| SDK | Admin `/sdk.js` | 실제 embed snippet과 Bearer API |

검증 흐름:

1. 공개 회원가입과 HttpOnly 세션 로그인
2. 데이터소스 추가와 실제 연결 테스트
3. `geometry_demo.korea_sigungu_statistics` 선택
4. PostGIS Polygon 지도 실행·canvas 렌더
5. 차트 저장과 정식 URL, 재진입 cache preview 복원
6. `POST /charts/{id}/refresh`와 마지막 계산 시각

global teardown은 Admin/Spring 프로세스 트리와 `chartsdk-real-e2e-db` 컨테이너를 제거한다. 기존 3000/3100/5433/55433 개발 환경은 사용하지 않는다.

## 6. 계층별 책임

### 운영 DB migration·권한·비밀번호

- `verifyFlywayResources`: V9과 afterMigrate callback의 source/package 일치
- `FlywayV8MigrationIT`: V7 DB를 V8로 올리고 기존 sampling v7 cache JSON 보존 확인
- `FlywayV9MigrationIT`: V8 DB의 기존 일반·지도 차트를 ColorBrewer v4 기본값으로 일괄 전환하고 색상 override 제거 확인
- `LegacyDatasourcePasswordMigrationIT`: v1 3건과 legacy 2건의 실DB 전환 및 datasource identity 보존
- `RuntimeDatabaseRoleIT`: `chartsdk_app` DML·sequence 허용, DDL·Flyway history 거부, source reader 전체 원본 SELECT와 write 거부
- `MultiSourceChartLifecycleIT`: v7 snapshot을 재계산 없이 v9으로 반환
- real-backend E2E: 제한 runtime role과 PostGIS reader로 저장·재진입·refresh·embed 관통

CI에서는 `CHARTSDK_REQUIRE_ROLE_IT=true`로 role IT skip을 금지한다. 기존 로컬 Docker volume은 init SQL이 소급되지 않으므로 role이 없을 때만 해당 테스트를 skip한다.

### 옵션·변환

- `chart-options/optionRegistry.ts`: 옵션 키·기본값·노출 조건의 권위
- Server Java converter: 운영 ECharts option의 권위
- Admin MSW converter: 프론트 테스트 mirror
- `transform-parity-contract-cases.json`: 8종 기본값 + 구성 사례 18개의 전체 Java/TypeScript JSON 패리티
- `optionTransformCoverage.test.ts`: 레지스트리 렌더 옵션을 적용 대상 차트마다 변경해 출력 또는 런타임 메타데이터 효과를 전수 검사
- 분야별 공용 JSON fixture: Java와 TypeScript가 같은 레이아웃·분석 세부 계약을 소비

옵션끼리 우선순위가 있는 규칙은 조건 함수를 한 곳에 두고 변환기와 편집기가 함께 소비한다. `movingAverageOverridesSort()`가 그 예로, 같은 함수가 MSW 정렬 분기와 `정렬` 컨트롤 잠금을 결정하며 서버 조건과의 일치는 `statistical-overlay-contract-cases.json`의 정렬 케이스 2개(정렬 적용 / 이동평균이 정렬을 덮고 숨긴 범례를 되살리지 않음)가 Java·TS 양쪽에서 고정한다.

### 캐시·갱신

- Server 단위: 별도 트랜잭션 coordinator, 승자/패자, 정의·표본 호환 캐시, 실패 기록, 저장 결과 재사용
- Server IT: 실제 PostgreSQL advisory lock 동시 요청 1회 실행, V5 최초 실패 error-only 행과 성공 시 오류 해제
- MSW E2E: 갱신 loading/error/disabled/computedAt UI
- 실백엔드 E2E: 실제 캐시 재계산→preview→지도→embed

### 지도

- Admin 단위/E2E: 공간 컬럼 선택과 viewport 상태
- Server 단위: PostGIS SQL과 타입 제한
- Server IT: 실제 geometry/geography 변환
- 실백엔드 E2E: 등록부터 SDK canvas까지

### 세션·임베드 키·CORS

- SDK 단위: API base, Authorization, `credentials: omit`, render/dispose
- MSW S3: 소유 차트 키와 생성한 snippet 자체의 선언형 렌더
- Server IT: member/admin 인가, 비활성화 세션·키 중단, 원문 비노출
- 실백엔드 E2E: 실제 Spring 세션·CSRF·CORS, DB embed key, cached chart response

## 7. CI

`.github/workflows/ci.yml`은 네 job을 수행한다.

1. `verify`: typecheck, workspace unit, production build, Server unit, 8종 Java/TypeScript transform parity
2. `integration`: PostgreSQL/PostGIS Server IT
3. `admin-e2e`: Chromium + MSW Admin 전 시나리오(배포 게이트)
4. `real-backend-e2e`: Chromium + PostGIS + Spring + MSW=false Admin

MSW E2E 실패 시 `admin/test-results/`·`admin/playwright-report/`를, 실백엔드 실패 시 `admin/test-results/real-e2e`의 screenshot, trace, Spring/Admin 로그를 artifact로 보존한다.

## 9. 15/30/100 VU 용량 검증

`load-tests/k6-query-capacity.js`는 15 VU 정상 구간, 30 VU 피크 구간, 100 VU 순간 버스트를 순서대로 실행한다. 자동 산점도 요청과 원본 탐색 요청을 섞고, `QUERY_BUSY` 재시도·원본 탐색 1,000행 상한·reservoir v9의 실제 표본 상한을 검증한다. p95는 마지막 HTTP 요청만이 아니라 최초 요청부터 재시도 backoff를 포함한 최종 응답까지 측정한다.

```bash
k6 run -e BASE_URL=http://localhost:8080 \
  -e DATASOURCE_IDS=1,2,3,... \
  load-tests/k6-query-capacity.js
```

100개 독립 데이터소스 격리를 강제하려면 `REQUIRE_100_DATASOURCES=true`를 추가한다. 로컬 검증 환경에는 k6와 100개 대용량 datasource fixture가 준비되지 않았으므로, 이번 변경에서는 시나리오의 정적 문법과 기능 회귀만 검증했다. 운영 승인 전 staging에서 실제 실행 결과를 보존해야 한다.

reservoir fallback 자체를 검증할 때는 `load-tests/README.md`의 통계 저평가 전용 fixture를 사용하고 `EXPECT_SAMPLE_METHOD=RESERVOIR_RANDOM`, `EXPECT_POPULATION_MIN=1000000`을 지정한다. 이 계약은 method가 reservoir인지, 반환 행과 `sampleSize`가 K인지, `populationCount`가 실제 최소 N 이상인지를 함께 검사한다.

## 10. 알려진 한계

- Admin React 컴포넌트는 순수 함수 단위와 Playwright 중심이며 별도 component renderer 계층은 없다.
- `tandanji:15432` 외부 federation IT는 기본 CI에서 skip될 수 있다.
- 인증/owner scope가 완성되지 않아 실백엔드 E2E는 개발 사용자 컨텍스트로 실행한다.
- 15/30/100 VU k6 시나리오는 마련됐지만 staging fixture 실행과 결과 보존은 CI에 자동화되지 않았다.
- admission은 이번 범위에서 JVM 로컬 구현이다. replica를 늘릴 때는 전체 DB 예산을 replica별 permit으로 나누거나 분산 구현을 추가해야 한다.
