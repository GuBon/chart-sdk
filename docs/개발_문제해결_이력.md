## A. 보안

### A1. 데이터소스 DB 비밀번호 평문 저장 🔴
- **원인:** 컬럼명 `db_password_enc`, 스키마 주석(`AES-GCM: base64(IV‖ct‖tag)`), `.env`의 `DATASOURCE_ENC_KEY`가 모두 암호화를 전제했으나, 구현은 입력 비밀번호를 **그대로 저장**(`password()`가 원문 반환)하고 조회 시 **그대로 JDBC 비밀번호로 사용**했다. 코드 전체에 `Cipher`/암복호화가 전무했고 `DATASOURCE_ENC_KEY`는 `.env.example` 외 어디서도 참조되지 않았다.
- **결과(영향):** 메타 DB가 유출되면 연결된 **모든 운영 PostgreSQL 자격증명이 평문 노출**. `_enc` 접미사가 "암호화됨"이라는 착각까지 유발.
- **해결방안:** `crypto/DatasourcePasswordCodec`(AES-GCM)은 `v1:` 형식의 암복호화만 담당한다. `DatasourcePasswordResolver`가 계측 가능한 레거시 평문 허용 정책을 맡고, startup migration 후 strict 모드에서는 평문이 한 건이라도 남으면 부팅을 차단한다.
- **코드:**
  ```java
  // DatasourcePasswordCodec — 키=SHA-256(DATASOURCE_ENC_KEY), 저장형식 v1:base64(IV(12)‖ct+tag(16))
  public String encrypt(String plaintext) { /* GCMParameterSpec(128, iv) */ }
  public String decrypt(String stored) { /* v1만 복호화, 그 외는 거부 */ }

  // DatasourcePasswordResolver
  public String resolve(String stored) {
      if (codec.isEncrypted(stored)) return codec.decrypt(stored);
      metrics.recordLegacyRead();
      if (!allowLegacyPlaintext) throw new IllegalStateException("legacy plaintext is disabled");
      return stored;
  }
  ```
- **이유:** 키 길이/인코딩 의존을 없애려 env 문자열을 SHA-256으로 32바이트 AES 키로 파생했고 GCM 인증 태그로 무결성을 보장한다. 형식 처리와 전환 정책을 분리해 잘못된 키·손상 암호문을 평문으로 오인하지 않으며, 레거시 폴백은 명시적인 전환 기간에만 허용한다.

## B. 데이터/SQL (노코드 빌더)

### B1. `DATE_TRUNC` bucket 직접 문자열 결합 인젝션 🔴
- **원인:** `"DATE_TRUNC('" + bucket + "', " + col + ")"` 처럼 사용자 입력 `xAxisBucket`을 **따옴표 이스케이프 없이** SQL 리터럴에 직접 결합. 식별자에 적용되던 `qident`의 따옴표 방어조차 없었다.
- **결과:** 작은따옴표로 탈출하는 전형적 SQL 인젝션. `xAxisBucket`에 임의 식을 주입해 데이터 탈취 가능. 가장 직접적인 공격 벡터.
- **해결방안:** bucket을 `{day, week, month}` 화이트리스트로만 허용하고, 그 외는 `400 BUCKET_TYPE_MISMATCH`로 차단.
- **코드:**
  ```java
  if (!Set.of("day","week","month").contains(bucket))
      throw new ApiException(BAD_REQUEST, "BUCKET_TYPE_MISMATCH", "Unsupported bucket: " + bucket);
  if (!isDate(typeOf(x)))
      throw new ApiException(BAD_REQUEST, "BUCKET_TYPE_MISMATCH", "Bucket requires a date/timestamp column.");
  ```
- **이유:** 고정 enum 값은 화이트리스트가 가장 단순·확실. 추가로 X축 컬럼이 실제 날짜 타입인지 검증해 의미 오류도 함께 차단(노코드 SQL생성규칙 §3A).

### B2. 식별자 화이트리스트 부재 + `mc_` 테이블 미차단 🔴
- **원인:** `table`/`column`/`join` 식별자를 `information_schema` 검증 없이 `qident`로 따옴표만 씌워 사용. `validateTable`은 스키마 미리보기 경로에서만 쓰였고 빌더 경로에선 호출되지 않았다. 내부 메타 테이블(`mc_*`) 차단도 빌더 경로엔 없었다.
- **결과:** 따옴표 escape만으로는 "실재 컬럼인지"를 보장 못 함. 자격증명이 접근 가능한 **임의 테이블/컬럼 + 솔루션 내부 테이블(`mc_user_token` 등) 열람** 가능.
- **해결방안:** `SchemaCatalog`(information_schema 로딩, `mc_` 제외)로 모든 식별자를 검증한 뒤에만 따옴표 적용(이중 방어). 미존재 식별자는 `400 INVALID_IDENTIFIER`.
- **코드:**
  ```java
  // QueryExecutor.catalog(): WHERE table_schema='public' AND table_name NOT LIKE 'mc\_%' ESCAPE '\'
  private Ref resolveRef(String ref) {
      // "table.col" 또는 base 암묵 컬럼 → 카탈로그 존재 검증
      if (!catalog.hasColumn(table, column))
          throw new ApiException(BAD_REQUEST, "INVALID_IDENTIFIER", "Unknown column: " + ref);
      return new Ref(table, column);
  }
  ```
- **이유:** 식별자는 PreparedStatement로 바인딩할 수 없으므로(노코드 SQL생성규칙 §1.2) 화이트리스트가 정석. 카탈로그가 `mc_`를 애초에 제외해 로딩하므로, 존재성 검증이 곧 `mc_` 차단을 겸한다(한 번에 두 문제 해결).

### B3. `agg:"none"` 원본값 모드인데 `GROUP BY` 강제 → 실행 불가 🟠
- **원인:** 집계 분기가 항상 `GROUP BY`를 붙였다. `none`은 집계가 아니라 원본 컬럼을 그대로 SELECT하는 모드라 `SELECT x, col1 … GROUP BY x`가 되면 PostgreSQL `must appear in GROUP BY` 에러가 난다.
- **결과:** 초기에는 scatter(분포) 차트 경로가 실행 불가였고, 이후 bar/line/pie 원본값 튜플 요구가 들어오면 같은 문제가 모든 차트 타입으로 확장될 수 있었다.
- **해결방안:** 모든 yAxis의 agg가 `none`이면 `GROUP BY`를 생략한다. `none`은 모든 차트 타입에서 허용하되, 한 builderConfig 안에서 집계와 섞지 못하게 막는다. 이후 원본 행 표본 계약(`ROW_SAMPLE`)을 추가해 sample과의 동시 사용은 허용했다.
- **코드:**
  ```java
  boolean allNone = yAxis.stream().allMatch(y -> "none".equals(str(y.get("agg"))));
  String groupBy = allNone ? "" : " GROUP BY " + (bucket == null ? x.quoted() : "1");
  ```
- **이유:** `none`은 "원본 행 조회"라 집계가 없으니 GROUP BY 자체가 성립하지 않는다. chartType이 아니라 `allNone`으로 판정해야 bar/line/pie 원본값 튜플과 scatter 원본 점을 같은 규칙으로 안전하게 처리한다.

### B4. LIKE 와일드카드 escape 누락 🟠
- **원인:** `contains`/`starts_with`가 사용자 입력의 `%`, `_`를 escape하지 않고 패턴에 넣었다.
- **결과:** 사용자가 입력한 `%`가 와일드카드로 동작해 의도와 다른 패턴 매칭(노코드 SQL생성규칙 §4 위반).
- **해결방안:** `\`, `%`, `_`를 escape한 뒤 서버가 `%`를 부착해 단일 파라미터로 바인딩.
- **코드:**
  ```java
  String escaped = s.replace("\\","\\\\").replace("%","\\%").replace("_","\\_");
  String pattern = "contains".equals(op) ? "%"+escaped+"%" : escaped+"%";
  parts.add(col.quoted() + " ILIKE ?"); params.add(pattern);
  ```
- **이유:** 와일드카드 조립은 서버 책임이라는 규칙(§4 비고)에 맞춤. 패턴 전체를 한 파라미터로 바인딩해 SQL 문자열엔 값이 끼어들지 않음.

### B5. 빌더/스키마 경로가 가드레일을 우회 🟠
- **원인:** `QueryController.runBuilder`·`SchemaController.preview`가 각자 raw `DriverManager`로 접속해 `setReadOnly`/`setQueryTimeout`/`setMaxRows`가 제각각(또는 미설정)이었다. 미리보기는 12행 하드코딩, 절단 감지 없음.
- **결과:** 운영 DB에 **무제한 타임아웃·쓰기 가능** 쿼리가 나갈 수 있었고, 에러 코드·행 제한도 경로마다 불일치.
- **해결방안:** 모든 고객 DB 조회를 `QueryExecutor` 단일 경로로 통일.
- **코드:**
  ```java
  // QueryExecutor: 읽기전용 + 타임아웃 10s + 1000행 + 절단 표기 + 에러 매핑 일원화
  conn.setReadOnly(true);
  ps.setQueryTimeout(QUERY_TIMEOUT_SECONDS); ps.setMaxRows(MAX_ROWS);
  boolean truncated = rows.size() >= MAX_ROWS;
  // SQLTimeoutException → 408 QUERY_TIMEOUT, 그 외 → 422 SQL_ERROR
  ```
- **이유:** "노코드는 별도 실행 경로를 만들지 않는다"(노코드 SQL생성규칙 §1.1). 가드레일을 한 곳에 모으면 새 엔드포인트가 생겨도 보안·제한이 자동 적용된다(SSOT 원칙의 실행 계층 버전).

## C. 변환기·렌더 (서버 단일 변환기, 방식 A)

### C1. `withDefaults` 얕은 병합 → 중첩 옵션 기본값 유실 🟠
- **원인:** `merged.putAll(options)`가 최상위 키만 덮어써, 사용자가 `{"yAxis":{"unit":"원"}}`만 보내면 `yAxis` 전체가 교체되어 `format`/`scale`/`splitLine` 등 기본값이 사라졌다.
- **결과:** 중첩 옵션 일부만 바꿔도 같은 그룹의 다른 기본값이 통째로 유실 → 축·범례·시리즈 옵션 광범위 손상.
- **해결방안:** 재귀 deep merge.
- **코드:**
  ```java
  private Map<String,Object> deepMerge(Map base, Map override) {
      // 양쪽이 Map 이면 재귀 병합, 아니면 override 값으로 교체
  }
  ```
- **이유:** 매핑 스펙 §3 "누락 키 = 레지스트리 기본값"은 중첩 키 단위 보존을 의미. 얕은 병합으론 충족 불가.

### C2. scatter 데이터가 `[x,y]` 쌍이 아니라 카테고리축으로 깨짐 🟠
- **원인:** scatter도 cartesian과 동일하게 `xAxis.data = categories`로 두고 시리즈 data를 y 1차원 배열로 만들었다. 분포 차트는 `xAxis.type='value'`에 `[x,y]` 쌍 데이터여야 한다.
- **결과:** 산점도가 인덱스 기반 y만 그려져 좌표가 무의미해짐(축 타입과 데이터 형태 모순).
- **해결방안:** scatter는 X·Y 모두 수치축(data 없음) + 데이터 `[x,y]`(버블이면 `[x,y,size]`).
- **코드:**
  ```java
  if (scatter) { /* xAxis.type=value, data 없음 */ data.add(Arrays.asList(x, y)); }
  // 버블: bubbleField 컬럼을 3번째 차원으로 → [x, y, size]
  ```
- **이유:** 매핑 스펙 §7/§10의 분포 데이터 컨벤션. `Arrays.asList`를 쓴 건 `List.of`가 null을 거부하기 때문(빈/짧은 행 방어).

### C3. `@variant`·직접매핑 미구현 🟠
- **원인:** 기존 변환기가 데이터만 끼운 골격이라 `variant`·`sortOrder`·title·color·grid·축 등 직접매핑과 특수 핸들러를 거의 읽지 않았다.
- **결과:** 누적·곡선·영역·도넛·버블 등 **중분류가 전혀 동작하지 않고**, 사용자가 설정한 대부분의 옵션이 무시됨.
- **해결방안:** 매핑 스펙대로 재작성 — `@sort`, `@variant`(stack/smooth/area/step/donut/rose/bubble/가로/100%정규화), 직접매핑(title/axes/legend/grid/palette/series), `@colorMap`, 이중축.
- **코드:** `ChartOptionConverter`의 `applyVariantDelta`·`applyAxes`·`applyLegend`·`buildCartesianSeries`/`buildPieSeries` 등(파일 참조).
- **이유:** 변환기는 TS/Java 이중 구현 금지(방식 A) — 서버 하나가 임베드·미리보기·재조립을 모두 책임지므로 스펙을 온전히 구현해야 클라이언트가 `setOption`만으로 끝난다.

### C4. ECharts formatter 함수의 JSON 직렬화 불가 🟡
- **원인:** 매핑 스펙은 숫자 포맷(콤마 등)·툴팁 valueFormatter를 **JS 함수**로 정의하나, option은 JSON으로 SDK에 전송되므로 함수를 담을 수 없다.
- **결과:** 콤마/소수 포맷 같은 함수 기반 포맷은 서버 JSON으로 표현 불가.
- **해결방안:** 표현 가능한 것만 처리 — 단위 접미사는 ECharts 문자열 템플릿 `'{value}단위'`로. 함수 포맷은 한계로 명시(후속: SDK 측 후처리 또는 포맷 토큰 전달).
- **코드:**
  ```java
  if (!unit.isEmpty()) label.put("formatter", "{value}" + unit); // 문자열 템플릿(JSON 안전)
  ```
- **이유:** 전송 매체(JSON) 제약을 인정하고 구조적 정확성(축/시리즈/색)을 우선. 거짓으로 함수 문자열을 넣어 클라이언트에서 깨지게 두지 않음.

## D. API·캐시

### D1. raw SQL 실행·refresh·duplicate 엔드포인트 부재 🟠
- **원인:** API 계약서에 정의된 `POST /query/run`(raw SQL), `POST /charts/{id}/refresh`(수동 갱신), `POST /charts/{id}/duplicate`(복제)가 구현되지 않았다.
- **결과:** SQL 탭 실행 불가, manual 모드 차트의 갱신 수단 부재, 카드 복제 액션 불가.
- **해결방안:** 세 엔드포인트 구현. refresh/duplicate는 `ChartComputeService` 재사용.
- **코드:**
  ```java
  @PostMapping("/query/run")          // SELECT/WITH 검증(SQL_NOT_SELECT) 후 QueryExecutor 실행
  @PostMapping("/charts/{id}/refresh")  // recompute → {chartId, computedAt, rowCount, elapsedMs}
  @PostMapping("/charts/{id}/duplicate")// INSERT ... SELECT(이름 "(사본)") + 캐시 복사(재실행 없음)
  ```
- **이유:** raw SQL은 SELECT만 허용해 쓰기/다중문 차단(노코드와 사용자층 분리). 복제는 원본 캐시를 그대로 복사해 재실행 비용 0(계약서 §3.6).

### D2. 저장 시 캐시 시드 부재 🟠
- **원인:** 차트 생성/수정이 INSERT/UPDATE만 수행하고 결과 캐시를 시드하지 않았다.
- **결과:** 저장 직후 manual 차트는 캐시가 없어 첫 임베드 요청의 self-heal에 의존(계약서가 약속한 "저장 시 시드" 미이행).
- **해결방안:** 저장 성공 시 `seedQuietly`로 1회 실행·캐시.
- **코드:**
  ```java
  compute.seedQuietly(id); // 데이터소스 장애 시에도 저장 트랜잭션은 보존(베스트 에포트)
  ```
- **이유:** 시드는 성능 최적화일 뿐 정합성의 필수 조건이 아니므로, 실패해도 저장은 성공시키는 게 옳다(캐시 미스는 self-heal로 복구됨).

### D3. HTTP 상태코드(201/204) 불일치 🟡
- **원인:** 생성/삭제가 `@ResponseStatus` 없이 일괄 200을 반환(계약서는 생성 201·삭제 204).
- **결과:** 201/204로 분기하는 클라이언트와의 계약 위반.
- **해결방안:** `@ResponseStatus(CREATED)`/`(NO_CONTENT)` 명시.
- **이유:** 계약서 정합. 무해해 보여도 표준 상태코드는 외부 통합의 신뢰 계약.

## E. 프론트엔드 동작 (Admin · SDK)

### E1. S2 stale 저장 — 빌더 변경 후 이전 실행 SQL 저장 🟠 (`4f8489a`)
- **원인:** 노코드 빌더(테이블·축·조건·정렬)를 바꿔도 직전 실행 결과(`result`/`generatedSql`/`option`)가 남아 있어, 사용자가 재실행 없이 저장하면 **바뀐 폼과 다른 옛 SQL**이 저장됐다.
- **결과:** 화면의 빌더 상태와 저장된 SQL이 어긋남 → 임베드/미리보기가 의도와 불일치.
- **해결방안:** 빌더 변경 시 실행 산출물을 무효화하고, 저장 버튼은 `result`가 있어야 활성(저장=실행 선행, PRD 7.3).
- **코드(패턴):**
  ```ts
  // ChartEditor: 빌더 config 변경 → result/generatedSql/option = null, canSave = !!result
  ```
- **이유:** "저장은 실행을 선행한다"는 PRD 규칙을 상태 모델로 강제해 stale 데이터 저장을 구조적으로 차단.

### E2. 저장 후 중복 생성·임베드 버튼 비활성 🟠 (`4f8489a`)
- **원인:** 생성 저장 후에도 차트가 "신규" 상태로 남아 재저장 시 또 INSERT됐고, 임베드 버튼은 id가 없어 비활성.
- **결과:** 동일 차트 중복 생성, 저장 직후 임베드 불가.
- **해결방안:** 저장 응답의 id로 `savedId` 전환 → 이후 PUT(수정) 경로 + 임베드 버튼 활성 + 상단 임베드 → S3 모달 연결.
- **이유:** "신규→저장됨" 상태 전이를 명시해 멱등성(중복 방지)과 후속 동선(임베드)을 동시에 확보.

### E3. 원본 데이터 탭에 WHERE 조건 미반영 🟡 (`4f8489a`)
- **원인:** 집계 실행만 호출하고 원본 데이터 탭은 조건 없이 보여줬다.
- **결과:** [원본 데이터]가 WHERE 필터를 무시한 전체를 표시.
- **해결방안:** 실행 시 `run-builder` `mode:rows`를 동시 호출해 같은 조건 바인딩으로 원본을 조회.
- **이유:** 집계/원본이 같은 조건을 공유해야 사용자가 "이 조건의 세부 행"을 신뢰할 수 있음(노코드 SQL생성규칙 §3B).

### E4. 임베드 스니펫 SDK 경로 하드코딩 🟠 (`480e71c`)
- **원인:** 임베드 스니펫이 `cdn.example.com/sdk.js`를 하드코딩.
- **결과:** 실제 배포 환경에서 동작하지 않는 스니펫.
- **1차 해결:** `NEXT_PUBLIC_SDK_SRC || window.location.origin + '/sdk.js'`로 환경 기반 해석.
- **코드:**
  ```ts
  const sdkSrc = () => process.env.NEXT_PUBLIC_SDK_SRC ?? `${window.location.origin}/sdk.js`;
  ```
- **이유:** 배포 출처가 환경마다 다르므로 빌드/런타임 env로 주입. 기본값을 현재 출처로 둬 단일 호스트 배포는 설정 0.
- **2차 검수에서 발견한 빈틈:** Admin은 실제 `/sdk.js`를 공개하지 않았고, SDK는 script 출처를 API 출처로 추론했다. 로컬처럼 Admin `:3000`·Spring `:8080`이 분리되면 파일이 404이거나 `/api/v1/charts/data`를 잘못된 서버로 요청하므로, 모달 코드를 그대로 붙여도 렌더되지 않았다.
- **최종 조치:** Admin dev/build 앞에서 SDK를 빌드해 `admin/public/sdk.js(.map)`로 복사하고 생성물은 git에서 제외했다. 스니펫에 `data-api-base="NEXT_PUBLIC_API_BASE"`를 넣고 SDK 해석 우선순위를 `window 전역 → script[data-api-base] → script 출처 → 페이지 출처`로 고정했다. `NEXT_PUBLIC_SDK_SRC`를 CDN으로 바꿔도 API 주소는 독립적으로 유지된다.
- **검증:** SDK 단위 테스트가 `data-api-base` 선택을 고정하고, S3 Playwright는 모달의 HTML 문자열만 빈 문서에 삽입해 `/sdk.js` 200 → Bearer 데이터 요청 → 실제 ECharts canvas 생성을 확인한다. MSW에도 `/api/v1/charts/data`를 추가해 이 선언형 경로를 인프라 없이 회귀 검증한다.

## F. 빌드·번들·툴체인

### F1. ECharts 번들 1.0MB(임베드 과대) 🟠 (`3ed9950`)
- **원인:** `echarts` 전체를 import해 임베드 SDK 번들이 ~1.0MB.
- **결과:** 외부 페이지 임베드 시 과대 페이로드(로딩 지연).
- **해결방안:** `echarts/core` + 필요한 charts/components/renderer만 `use()`로 트리셰이킹 → **522KB**.
- **코드:**
  ```ts
  import * as echarts from 'echarts/core';
  import { BarChart, LineChart, PieChart, ScatterChart } from 'echarts/charts';
  import { GridComponent, TooltipComponent, LegendComponent, TitleComponent } from 'echarts/components';
  import { CanvasRenderer } from 'echarts/renderers';
  echarts.use([BarChart, LineChart, PieChart, ScatterChart, GridComponent, TooltipComponent, LegendComponent, TitleComponent, CanvasRenderer]);
  ```
- **이유:** 임베드는 호스트 페이지에 얹히므로 용량이 곧 UX. 4종 차트 + 사용하는 컴포넌트만 등록하면 절반으로.

### F2. ESLint 9 / config 16 이 Next 15 와 비호환 🟠 (`c608d71`)

## J. 데이터 정합성 보강 (해결 진행 — 2026-06-25)

데이터 정합성 분석에서 도출한 갭(G1~G8)을 우선순위대로 해결한다. 각 항목은 분석 근거(원인/결과)와
실제 적용(해결/코드/이유)을 함께 기록한다. 강점(스키마 제약·FK·트리거·트랜잭션)은 양호했고,
부족분은 **캐시(파생 데이터)와 동시성**에 집중돼 있었다.

### J1. 동시 재계산 단일 비행 + SWR (G1·G4) ✅
- **원인:** 캐시 미스/`ttl` 만료 시, 동시에 들어온 임베드 요청들이 **모두 고객 DB를 재조회**하고 각자
  `upsert`로 덮어썼다. `V1__init.sql` 캐시 주석이 `pg_try_advisory_xact_lock(chart_id)` 단일 비행을
  명시적으로 권장했으나 미구현. 또 `ttl` 만료 시 `findUsable`이 empty → **동기 재계산(블로킹)** 이라
  만료 직후 요청이 운영 DB를 직격했다.
- **결과(영향):** 만료 순간 운영 DB 부하 스파이크(thundering herd), 표본(sample) 차트는 동시 재계산이
  서로 다른 근사값을 써 **결과가 깜빡임**. 임베드가 막으려던 "DB 직격"이 그대로 발생.
- **해결방안:** advisory 락으로 재계산을 한 요청(승자)으로 합치고, 경쟁에서 진 요청은 stale 캐시를
  즉시 반환(SWR). stale 이 없거나 `live` 모드면 승자 완료를 기다린 뒤 신선한 결과를 읽는다.
- **코드:**
  ```java
  // ChartComputeService.refreshSingleFlight (@Transactional — xact 락은 트랜잭션 종료 시 자동 해제)
  Boolean won = jdbc.queryForObject("SELECT pg_try_advisory_xact_lock(?)", Boolean.class, chartId);
  if (won) return cache.upsert(chartId, queries.execute(datasourceId, sql));   // 승자만 재계산
  if (allowStale) { var stale = cache.find(chartId); if (stale.isPresent()) return stale.get(); } // SWR
  jdbc.query("SELECT pg_advisory_xact_lock(?)", rs -> null, chartId);          // 승자 대기
  return cache.find(chartId).orElseGet(() -> cache.upsert(chartId, queries.execute(datasourceId, sql)));
  // EmbedChartService: findUsable(..).orElseGet(() -> compute.refreshSingleFlight(.., !"live".equals(mode)))
  // ChartCacheService.find(chartId): ttl 무시 raw 조회(stale 반환용) 추가
  ```
- **이유:** advisory **xact** 락은 `@Transactional` 종료 시 자동 해제돼 누수가 없다. 순수 백그라운드
  SWR(별도 스레드)은 `@Async`+새 트랜잭션이 필요해 복잡도가 큰데, "승자 동기 재계산 + 패자 stale 반환"은
  단일 비행과 비블로킹의 핵심 이득을 단순하게 얻는다(승자 1요청만 느리고 나머지는 즉시). `live`는 stale을
  내보내면 의미가 깨지므로 대기 후 신선 결과를 읽는다.

### J2. 정의-캐시 버전 일치로 stale 데이터 차단 (G2) ✅
- **원인:** 차트 `sql_query`/`builder_config`를 수정하면 `seedQuietly`로 재계산하지만, **데이터소스 장애로
  시드가 실패하면 옛 정의로 계산된 캐시가 그대로 남았다.** 캐시에 "어느 정의로 계산했는지" 식별자가 없었다.
- **결과(영향):** `manual` 모드면 임베드가 **새 정의 ≠ 옛 데이터**를 무기한 노출. 정의와 데이터가 어긋난 채 표시.
- **해결방안:** `mc_chart.version`(저장마다 +1)과 `mc_chart_cache.definition_version`을 둬, 임베드 조회 시
  **캐시 버전 ≠ 현재 정의 버전이면 stale 취급**(재계산). 캐시는 계산 시점의 정의 버전을 함께 스탬프.
- **코드:**
  ```sql
  -- V2__integrity.sql
  ALTER TABLE mc_chart ADD COLUMN version INTEGER NOT NULL DEFAULT 0;
  ALTER TABLE mc_chart_cache ADD COLUMN definition_version INTEGER;
  ```
  ```java
  // ChartCacheService.findUsable(.., int currentVersion)
  int cachedVersion = rs.getInt("definition_version");
  if (rs.wasNull() || cachedVersion != currentVersion) return Optional.empty(); // 정의 변경 → stale
  // upsert(.., definitionVersion): 계산 시점 정의 버전을 캐시에 스탬프
  // EmbedChartService: findUsable(.., chart.version()) + refreshSingleFlight(.., chart.version(), ..)
  ```
- **이유:** `version` 하나가 **낙관적 락(G3)과 캐시 무효화(G2)를 동시에** 해결한다 — 저장이 곧 버전 증가이고,
  캐시는 그 버전으로 태깅되므로 "정의가 바뀌면 캐시는 자동으로 stale"이 성립. 별도 해시 컬럼·트리거 불필요.
  마이그레이션은 `docs/V*__*.sql` 글로브로 복사하도록 빌드를 바꿔 V2 이후도 자동 반영.

### J3. 낙관적 동시성 제어로 갱신 유실 방지 (G3) ✅
- **원인:** 두 사람(또는 두 탭)이 같은 차트를 동시에 열어 저장하면 **마지막 PUT이 앞 변경을 덮어썼다**(lost update).
  버전 비교·`If-Match`가 없었다.
- **결과(영향):** 변경 유실. 개인 스코프라도 멀티탭에서 발생 가능.
- **해결방안:** `GET`이 `version`을 내려주고, `PUT`이 그 버전을 되돌려보내면 **`WHERE id=? AND version=?`로만 갱신
  + `version=version+1`**. 0행이면 차트 존재 여부로 갈라 **409 VERSION_CONFLICT**(존재) 또는 404(미존재).
- **코드:**
  ```java
  // ChartController.update — version 미전송 시 기존 동작(하위호환), 전송 시 낙관적 락
  if (expectedVersion != null) { sql.append(" AND version=?"); args.add(expectedVersion); }
  if (updated == 0) {
      boolean exists = count("mc_chart", id) > 0;
      throw exists ? conflict("VERSION_CONFLICT", "modified elsewhere; reload")
                   : notFound("CHART_NOT_FOUND");
  }
  ```
- **이유:** 낙관적 락은 비관적 락(행 잠금)보다 가볍고, 충돌이 드문 개인 툴에 적합. `version`을 보내지 않는 기존
  클라이언트는 종전대로 동작(점진 도입). 충돌은 **유실 대신 409로 드러내** 사용자가 새로고침 후 재시도하게 한다.

### J4. 암호문 버전 태그 + 명시적 복호화 실패 (G6) ✅
- **원인:** `decrypt()`가 복호화 실패 시 **입력을 그대로 반환**(레거시 평문 호환)했다. 그래서 *진짜 암호문이
  손상되거나 키가 바뀌어 복호화 실패*해도 **쓰레기 값을 비밀번호로 조용히 반환**했고, 키 회전 식별 수단도 없었다.
- **결과(영향):** 정합성 위반을 "조용한 접속 실패"로 흘려보냄. `DATASOURCE_ENC_KEY`를 바꾸면 기존 비밀번호
  전부 복호화 불가인데, 그조차 평문 폴백에 묻혀 진단이 어려움.
- **해결방안:** 암호문에 키 버전 마커 `"v1:"`를 붙인다. **마커가 있으면 우리 암호문 → 복호화 실패 시 평문 폴백
  금지하고 명시적 오류.** 마커가 없으면 레거시 평문으로 취급(마이그레이션 0). 회전 시 `v2:` 등으로 확장.
- **코드:**
  ```java
  private static final String PREFIX = "v1:";
  // encrypt: return PREFIX + base64(IV‖ct+tag);
  public String decrypt(String stored) {
      if (!stored.startsWith(PREFIX)) return stored;          // 레거시 평문 → 그대로
      try { /* base64 decode + AES-GCM 복호화 */ }
      catch (Exception e) { throw new IllegalStateException("decryption failed (key mismatch/corrupted)"); }
  }
  ```
- **이유:** "복호화 실패 = 명시적 오류"여야 키 불일치/손상을 **조용한 오접속이 아니라 즉시 가시화**한다.
  마커는 향후 키 회전(`v2:`)에서 "어느 키로 복호화할지"를 값 자체가 담게 해, 무중단 점진 회전의 토대가 된다.
  마커 없는 값만 평문 폴백이라 기존 시드(`'0218'`)·레거시 데이터와 호환된다.

### J5. 집계 절단(1000행) 제거 및 미리보기 제한 분리 (G5) ✅
- **원인:** 모든 조회가 `LIMIT 1000`+`setMaxRows(1000)`. GROUP BY 결과 그룹이 1000개를 넘으면 일부가
  잘린 채 집계되는데, 절단 여부가 임베드 응답에 드러나지 않았다.
- **결과(영향):** 합계/카운트 차트가 **소리 없이 부분값**이 될 수 있어 "정확한 합계"로 오해.
- **해결방안:** 초기에는 절단 여부를 임베드 응답에 노출했으나, 최종 제품 계약은 실제 차트에서 고정 제한 자체를 제거하는 것으로 교정했다. 모든 빌더·저장 SQL 차트는 제한 없는 실행 경로를 사용하고, `LIMIT 1000`과 JDBC `setMaxRows(1000)`은 원본 데이터·관계 미리보기에만 남긴다. 표본을 지정한 경우에만 사용자가 선택한 크기로 입력을 줄인다.
- **코드:**
  ```java
  // EmbedChartService.data
  response.put("rowCount", rows.rows().rowCount());
  response.put("truncated", rows.rows().truncated());
  ```
- **이유:** 차트 결과를 임의 절단한 뒤 안내하는 것보다, 기본 전체 결과와 명시적 표본추출을 분리하는 편이 정확성과 사용자 통제권을 함께 보장한다. `truncated` 필드는 미리보기와 레거시 응답 호환을 위해 유지한다.

### J6. 깨진 캐시를 예외 대신 미스로 처리 (G7) ✅
- **원인:** `ChartCacheService.readRows`가 캐시 JSONB 역직렬화 실패 시 `IllegalStateException`을 던져,
  손상된 캐시 한 줄이 **임베드 요청 전체를 500으로 깨뜨렸다**. 구조 검증도 `jsonb_typeof='object'`뿐이었다.
- **결과(영향):** 캐시 손상이 self-heal 가능한 상황인데도 사용자에게 장애로 전파.
- **해결방안:** `readRows`가 `{columns, rows}` 구조를 검증하고, 깨졌으면 `null` 반환 → `findUsable`/`find`가
  **미스로 처리**해 단일 비행 재계산으로 자가 복구.
- **코드:**
  ```java
  if (!(result.get("columns") instanceof List) || !(result.get("rows") instanceof List)) return null;
  // 호출부: QueryRows rows = readRows(..); return rows == null ? Optional.empty() : Optional.of(..);
  ```
- **이유:** 파생 데이터(캐시)의 손상은 **복구 가능한 미스**로 다뤄야지, 원본이 멀쩡한데 장애로 키우면 안 된다.
  "캐시는 언제든 버리고 다시 만들 수 있다"는 캐시의 본질에 맞춘 처리.

### J7. 생성 멱등성 (G8) — 의도적 후순위 ⏸
- **원인:** `POST /charts`는 매번 INSERT라, 재시도/더블클릭 시 중복 생성 가능.
- **결과(영향):** 중복 차트. 단 admin은 저장 후 `savedId` 상태 전환으로 클라이언트 측 중복을 이미 차단(트러블슈팅 E2).
- **결정:** **후순위로 보류.** 완전한 멱등은 `Idempotency-Key` + 단기 키 저장 테이블이 필요한데, 사용자 측
  중복 방지가 이미 있고 개인용 내부 툴이라 비용 대비 이득이 낮다.
- **권장 해결방안(추후):** `POST`에 `Idempotency-Key` 헤더 + (key, 응답) 단기 캐시 테이블 → 동일 키 재요청은
  기존 결과 반환. 또는 (owner_id, name) 단기 유니크로 중복 생성 거부.
- **이유:** 정합성 보강도 **비용 대비 효과로 우선순위를 매겨야** 한다. 이미 1차 방어선(클라이언트)이 있는
  저빈도 위험은, 더 시급한 캐시·동시성·보안(G1~G6)을 끝낸 뒤로 미루는 것이 합리적이다.

## L. 클린코드 리팩터링·원본값 튜플 확장 (2026-06-29)

### L1. 차트 컨트롤러 비대화와 owner/sort 책임 혼재 ✅
- **원인:** `ChartController`가 요청 파싱, SQL 생성, 저장, 조회, 정렬, owner 스코프 준비를 한 파일에서 처리했다.
- **결과(영향):** 코드가 커질수록 저장 경로와 조회 경로의 계약을 함께 검증하기 어려웠고, S1 정렬·owner 스코프 같은 횡단 규칙이 누락되기 쉬웠다.
- **해결방안:** `chart/ChartService`, `chart/ChartRepository`, `ChartDefinition`으로 역할을 분리했다. 컨트롤러는 DTO를 받아 서비스에 위임하고, repository가 목록 필터·정렬·owner 스코프를 담당한다.
- **이유:** 컨트롤러를 HTTP adapter로 얇게 유지하면 비즈니스 규칙을 테스트 가능한 서비스/저장소에 모을 수 있다.

### L2. 타입 없는 요청 바디와 에러 응답 불일치 ✅
- **원인:** 여러 API가 `Map<String,Object>` 요청 바디를 직접 해석했다.
- **결과(영향):** 필수값 누락·타입 오류가 런타임 분기에서 늦게 드러났고, 에러 envelope이 경로마다 달라질 위험이 있었다.
- **해결방안:** 핵심 요청을 record DTO(`ChartSaveRequest`, `BuilderQueryRequest`, `QueryRunRequest`, `ChartPreviewRequest`, `IssueTokenRequest`, `UserCreateRequest`)로 승격하고 Bean Validation과 `ApiExceptionHandler`를 적용했다.
- **이유:** API 계약은 타입으로 먼저 표현해야 한다. DTO 검증이 앞단에서 실패를 모으면 서비스 코드는 정상 입력만 다룰 수 있다.

### L3. 모든 차트 타입 원본값 튜플 모드 ✅
- **원인:** `agg:"none"`이 scatter 전용으로 설계되어 있어, `year`별 `print` 원본값처럼 “합계/평균 없이 튜플 값을 그대로 막대나 선으로 그리는” 노코드 요구를 표현할 수 없었다.
- **결과(영향):** 사용자는 SQL을 직접 쓰지 않고는 원본 행의 X/Y 값을 그대로 시각화할 수 없었다.
- **해결방안:** no-code UI와 서버 생성기 모두에서 `none`을 모든 차트 타입에 허용했다. 단 `none`과 집계 혼합, `none`과 sample 동시 사용은 차단한다. 서버는 `GROUP BY` 없는 SQL을 만들고, 변환기는 기존 rows 컨벤션으로 bar/line/pie/scatter를 조립한다.
- **검증:** `gradlew test`, admin typecheck, Playwright E2E를 통과했고, 실행 중인 3000/8080/5433 환경에서 line/pie 원본값 preview와 저장 smoke를 실제 API로 확인했다.
- **이유:** “원본값”은 차트 타입의 특성이 아니라 SQL shape의 특성이다. `allNone`으로 판정하면 차트 타입이 늘어나도 동일 규칙을 재사용할 수 있다.

## 횡단 교훈 (Cross-cutting)

1. **컬럼명/주석이 약속한 것을 코드가 이행하는지 검증** — `_enc`처럼 "이름이 보안을 약속"하면 반드시 구현을 확인(A1).
2. **식별자는 화이트리스트, 값은 바인딩** — SQL 안전의 2대 규칙. 식별자 escape만으론 부족(B1·B2).
3. **단일 경로(SSOT)로 가드레일 집약** — 실행은 `QueryExecutor`, 옵션 기본값은 `defaults.json`, 변환은 단일 Java 변환기. 경로가 갈라지면 보안·정합이 갈라진다(B5·C3).
4. **전송 매체 제약을 인정** — JSON으론 함수를 못 보낸다. 표현 가능한 범위에서 정직하게(C4).
5. **상태 전이를 모델로 강제** — "저장=실행 선행", "신규→저장됨"을 코드 상태로 못 박아 stale/중복을 구조적으로 차단(E1·E2).
6. **테스트 환경의 결정성** — stale 서버·콜드 컴파일·버퍼링은 "코드 버그"가 아니라 "관측 신뢰성" 문제. 환경을 통제해야 빨강/초록을 믿을 수 있다(G1–G4).
7. **프레임워크 지원 스택 우선** — 신버전(ESLint9)보다 프레임워크가 보증하는 조합이 빌드 안정성에 유리(F2).
8. **검증 게이트를 환경 제약 너머로** — 래퍼가 없어도 캐시 배포본으로 컴파일 게이트를 세운다(F3).

## 2026-06-26 작업 기록 - 목록 미리보기/팔레트/검증

### K1. 3001 프론트 정적 파일 404

- **증상:** `http://127.0.0.1:3001` 접속 시 HTML은 내려오지만 `/_next/static/css/app/layout.css`, `/_next/static/chunks/app/(console)/page.js`가 404로 실패했다.
- **원인:** 실행 중인 Next dev 서버가 참조하는 dev 산출물 경로와 현재 `.next` 디렉터리의 production build 산출물이 불일치했다.
- **조치:** dev 서버를 재시작해야 한다. 테스트에서는 별도 포트의 fresh dev 서버를 띄워 정적 파일 경합 없이 검증했다.
- **재발 방지:** `next build` 후 기존 dev 서버가 이상 상태면 프론트 기능을 판단하지 말고 서버 재시작/정적 파일 응답부터 확인한다.

### K2. 8080 백엔드가 오래된 코드로 실행 중

- **증상:** 현재 코드의 `GET /api/v1/charts`는 `{charts,page,pageSize,total,totalPages}` 응답을 반환해야 하지만, 실행 중인 8080은 배열만 반환했다. `GET /api/v1/charts/previews?ids=...`도 기대 계약과 맞지 않았다.
- **원인:** 로컬 8080 프로세스가 변경 전 백엔드로 떠 있었다.
- **조치:** 기존 8080은 사용자 환경일 수 있어 강제 종료하지 않았다. 프론트는 오래된 배열 응답을 1페이지 응답으로 감싸는 하위 호환 처리를 추가했고, 실제 새 API 코드는 `gradlew compileJava`로 검증했다.
- **재발 방지:** API 계약 변경 후에는 실행 중인 서버 버전과 코드 버전을 먼저 확인한다.

### K3. 목록 카드 미리보기 더미 렌더링 문제

- **증상:** 목록 카드의 미리보기가 실제 차트 option이 아니라 고정 샘플처럼 보일 수 있었다.
- **원인:** 카드용 `MiniChart`가 자체 샘플 데이터를 만들면 저장된 chartType/options/builder 결과와 불일치한다.
- **조치:** 목록은 현재 페이지 차트 id를 batch preview API로 요청하고, 응답의 ECharts option을 `ChartPreview`로 그대로 렌더링한다.
- **검증:** Playwright에서 목록 카드 canvas 5개 렌더, `/charts/previews` batch 호출 1회, `/charts/{id}/preview` 단건 호출 0회를 확인했다.

### K4. 색상 팔레트가 표시만 되고 편집되지 않음

- **증상:** 차트 편집 옵션 패널의 팔레트 색상 블록을 눌러도 색상을 바꿀 수 없었다.
- **원인:** `palette` control이 swatch 표시만 하고 선택/수정 UI를 갖지 않았다.
- **조치:** swatch 선택 상태, color input, R/G/B 숫자 입력을 추가했다. RGB는 0~255로 clamp하고 `options.palette[]`를 즉시 갱신한다.
- **검증:** Playwright에서 두 번째 swatch 선택 후 RGB를 `255,0,0`으로 변경했을 때 `#option-palette-color` 값이 `#ff0000`으로 바뀌고 편집 preview canvas가 유지되는 것을 확인했다.

### K5. Form field id/name 경고

- **증상:** 브라우저 감사에서 `A form field element should have an id or name attribute` 경고가 발생했다.
- **원인:** 검색 input, 필터 select, 옵션 패널 select/input 일부가 `aria-label`은 있으나 `id`/`name`이 없었다.
- **조치:** 공용 `Input`/`Select`에 `aria-label` 또는 `placeholder` 기반 `name` fallback을 추가하고, 핵심 컨트롤에는 명시적 `id/name`을 부여했다.
- **검증:** Playwright에서 목록/편집 화면의 `input, select, textarea` 중 `id`와 `name`이 모두 없는 항목이 0개임을 확인했다.

### K6. Windows PowerShell/Node 실행 환경의 PATH 중복

- **증상:** `Start-Process` 또는 `cmd.exe` 경유 실행에서 `Path/PATH` 중복으로 프로세스 시작이 실패하거나 `The syntax of the command is incorrect.`가 발생했다.
- **원인:** 현재 셸 환경에 `Path`와 `PATH`가 동시에 존재해 Windows 프로세스 환경 구성이 깨졌다.
- **조치:** 테스트 스크립트에서는 `npm.cmd` 대신 `node.exe npm-cli.js`를 직접 실행하고, `PATH` 계열 환경 변수를 정규화했다.
- **재발 방지:** Windows에서 장기 실행 dev 서버를 자동화할 때는 환경 변수 중복을 제거하거나 npm CLI JS를 직접 호출한다.

### K7. Figma 실제 대조 미수행

- **증상:** “Figma와 화면 구현 일치” 확인 요청이 있었지만, 이 세션에는 Figma `get_design_context`/`get_screenshot` 도구가 노출되어 있지 않았고 Figma URL/노드 ID도 제공되지 않았다.

### K8. `.env.local`의 실백엔드 설정 때문에 E2E seed가 비는 문제

- **증상:** Playwright에서 S1 목록 차트와 S2 데이터소스가 모두 비어 보였다.
- **원인:** `admin/.env.local`이 `NEXT_PUBLIC_API_BASE=http://localhost:8080`, `NEXT_PUBLIC_ENABLE_MSW=false`로 되어 있어 E2E dev 서버도 MSW 대신 로컬 8080을 호출했다. 8080이 꺼져 있거나 오래된 서버면 seed 데이터가 비었다.
- **조치:** E2E 전용 dev 서버(`admin/e2e/web-server.cjs`)가 `NEXT_PUBLIC_E2E_MSW=true`를 주입한다. 클라이언트 API base는 이 값이 `true`일 때 `.env.local`의 API base를 무시하고 상대 경로(`/api/v1`)를 사용한다. `MockProvider`도 같은 플래그에서 MSW를 강제 기동한다.
- **검증:** `npm run test:e2e`에서 전체 25개 테스트가 MSW seed 기준으로 통과했다.

### K9. `next build`와 dev E2E 동시 실행 시 `.next` 산출물 충돌

- **증상:** 전체 e2e 중 Next dev overlay에 `__webpack_modules__[moduleId] is not a function` 런타임 오류가 떴고, 동시에 `next build`는 page data 수집 중 `Cannot find module for page` 오류를 냈다.
- **원인:** `next build`와 Playwright dev 서버가 같은 `admin/.next` 디렉터리를 동시에 읽고 써서 산출물이 섞였다.
- **조치:** 생성물인 `admin/.next`를 workspace 내부 경로인지 확인한 뒤 삭제하고, e2e와 build를 순차 실행했다.

### L9. dev 서버가 `.env.local` 미반영 → 프론트 API 전량 404 + 미처리 rejection 크래시 🟠
- **증상:** 브라우저 dev 오버레이에 `Uncaught (in promise) ApiError: Not Found`(`lib/api/client.ts:41`). 화면의 모든 데이터가 비고 API가 404.
- **원인:** 요청이 `http://localhost:3000/api/v1/...`(프론트 자기 origin)으로 나갔다 — `.env.local`의 `NEXT_PUBLIC_API_BASE=http://localhost:8080`가 **적용 안 된 상태**로 dev 서버가 떠 있었다. `NEXT_PUBLIC_*`는 dev 서버 **시작 시점에 인라인**되므로, `.env.local`을 못 본 채(다른 cwd·재시작 타이밍) 기동되면 상대경로 `/api/v1`로 나가 프론트가 자기 자신에게 404. MSW도 `NEXT_PUBLIC_ENABLE_MSW=false`라 미개입.
- **진단:** Playwright 로 실패 응답 URL 캡처 → 전부 `3000/api/v1`(백엔드 `:8080`은 200)임을 확인. **코드 변경이 아니라 환경 문제로 특정**(직전 실브라우저 검증은 8080에 정상 연결됐었음).
- **조치:** `admin`에서 dev 서버 재시작(`Ctrl+C` → `cd admin && npm run dev`) → `.env.local` 로드 → API_BASE=8080 적용, 404 소멸.
- **코드 하드닝(병행):** API 호출 3곳(`datasourcesApi.list`·`chartsApi.get`·`schemaApi.preview`)이 `.catch` 없이 rejection 을 던져 dev 크래시 오버레이를 유발 → `.catch`/try-catch 로 그레이스풀 처리(토스트·빈 상태). 백엔드 일시 장애나 특정 테이블 미리보기 실패에도 앱은 크래시하지 않는다.
- **재발 방지:** 프론트 API 404면 **요청 URL이 3000인지 8080인지부터** 본다(DevTools Network). 3000이면 dev 서버가 env 미반영 → **admin/에서 재시작**. 상시 순서: DB(5433) → 백엔드(8080) → 프론트(3000, `cd admin` 후 기동).

- **왜 잠복했나:** 기존 MSW 시드가 차트 5개(항상 1페이지, `totalPages=1` 고정)라 사이클이 발동하지 않았다. E2E 확장을 위해 시드를 13개(2페이지)로 늘리자 비로소 노출됨.

- **재발 방지:** 상태가 페이지네이션처럼 **경계(1↔N페이지)로 갈리는 로직은 경계를 넘는 시드로 테스트**해야 잠복 결함이 드러난다. useCallback/useEffect deps 에 "상태에 의존하는 setter"를 넣으면 자기참조 사이클을 의심하고, 보정은 파생 상태 대신 소스(URL)를 직접 갱신한다.

### L11. 누적 100% 정규화가 잘못된 축(시리즈 합)으로 나눔 🟡

### L12. 기획서 "Prisma 마이그레이션 자동화" → Flyway 대체 (설계 결정) 🔵
- **맥락(기획서 p08):** DB 마이그레이션 자동화를 **Prisma + Next.js prestart hook**(`prisma migrate deploy` 선행 실행)으로 명시. 요건은 ①구동 전 마이그레이션 선행 ②테이블 부재 시 자동 진단·적용 ③수동 DDL 금지·이력 추적 ④기존 데이터 네임스페이스 격리.
- **편차:** 구현은 **Flyway + Spring Boot**(`spring.flyway.enabled`, `db/migration` V1~V5). Prisma·prestart hook 미사용.
- **사유(정당):** 기획서 자체가 백엔드를 **Spring Boot(Java, p04)**로 명시하는데 Prisma는 Node/TS ORM이라 스택 불일치. Java 표준 마이그레이션 도구인 Flyway로 대체하는 것이 자연스러운 귀결(기획서 내부 모순의 해소).
- **동등성(요건 4가지 충족):** ①Spring Boot 부팅 시 Flyway 자동 실행(서빙 전) ②버전 대조로 미적용 마이그레이션 자동 적용 ③`ddl-auto: none` + `mc_flyway_schema_history` 이력, 수동 DDL 금지 ④`mc_` 접두사 + `baseline-on-migrate: true`(고객 기존 테이블 불간섭). 즉 **도구만 다르고 목표는 전부 달성**.
- **기록 이유:** 스펙(Prisma)과 구현(Flyway)이 문서상 어긋나 보이므로 의사결정 근거를 남긴다. 참고: DB 배포·운용 전략(p06)·테이블 표준(p07)·나머지 파트 명세는 기획서와 일치.

### L16. 표본 SUM·COUNT 외삽 누락 + 캐시·임베드에서 근사치 정보 소실 🟠
- **증상:** MSW mock과 문서는 표본 SUM·COUNT를 `100/rate`로 외삽했지만 운영 Java SQL은 `SUM/COUNT`를 표본값 그대로 반환했다. 10% 표본이면 전체량이 약 10% 수준으로 표시될 수 있었다. Admin 결과 패널에는 근사치 배지가 있었지만 저장 캐시와 임베드 응답에는 sampling 정보가 없어 최종 사용자가 정확값으로 오인할 수 있었다.
- **원인:** `BuilderSqlBuilder`의 TABLESAMPLE 주입과 집계식 생성이 분리돼 표본 비율이 `aggSql`까지 전달되지 않았다. `QueryController`가 `approximate/sampleRate`를 일회성 응답에만 붙였고 `QueryRows` 캐시 payload에는 저장하지 않았다. 기존 builder 차트 재계산도 저장 당시 문자열 SQL을 재사용해 생성기 규칙 수정이 소급되지 않았다.
- **조치:** SUM·COUNT만 `(집계식 * (100.0 / rate))`로 외삽하고 AVG·STDDEV·MIN·MAX·COUNT DISTINCT는 표본값을 유지한다. 정식 `sampling:{approximate:true,method:'SYSTEM',rate}` 계약을 도입하고 레거시 별칭도 함께 반환한다. cache `result JSONB`에 sampling을 저장하며 구 payload도 읽는다. sampling 없는 구 표본 캐시는 자동 미스로 처리하고 builder 차트는 `builderConfig`로 현재 SQL 생성기를 다시 실행한다.
- **임베드:** 미리보기·refresh·embed API가 동일 sampling 객체를 반환하고 SDK는 차트 하단에 `표본 N% 기반 근사치 · 데이터 기준 …` 캡션을 표시한다.
- **계약 검증:** `sampling-contract-cases.json`을 서버 JUnit과 Admin Vitest가 함께 읽는다. cache codec 신규/레거시/손상 케이스와 SDK nested/legacy 응답·캡션도 단위 테스트로 고정했다.
- **검증:** 관련 server/Admin/SDK 단위 테스트 통과. 전체 E2E·production build와 최신 절대 수치는 `docs/테스트_전략.md`를 따른다.

### L18. 100%도 TABLESAMPLE로 실행되고 표본 결과의 재현성·분모·집계별 의미가 없었음 🟠
- **증상:** `sample.rate=100`도 `TABLESAMPLE SYSTEM(100)`과 `approximate:true`로 표시됐다. 같은 비율을 다시 실행하면 표본이 달라질 수 있었고, 결과의 `rowCount`가 그룹 수인지 표본 입력 수인지 사용자가 알 수 없었다. SUM과 MIN, COUNT DISTINCT가 모두 같은 “근사치” 문구를 써 계산 의미도 구분되지 않았다.
- **원인:** 표본 설정(`rate`)과 실행 결과 메타데이터가 하나의 얕은 객체였고, seed·실제 표본 수·집계별 treatment가 계약에 없었다. 캐시 서빙 시 실행 메타데이터를 차트 정의의 얕은 sampling 객체로 덮어써도 감지할 수 없는 구조였다.
- **조치(SQL):** 100%는 TABLESAMPLE·외삽·숨은 계수 열이 없는 `FULL_SCAN/exact`로 분기했다. 100% 미만은 `SYSTEM(rate) REPEATABLE(seed)`로 고정하고 0.1%까지 허용했다. 자동 모드는 `pg_class.reltuples`로 약 100만 행을 목표로 비율을 정하며 정확한 COUNT(*)를 실행하지 않는다.
- **조치(실행 통계):** 집계 SQL에 숨은 `COUNT(*)`와 `SUM(COUNT(*)) OVER()`를 추가해 한 쿼리에서 그룹별·전체 실제 표본 입력 행 수를 얻고, 변환기 전에 열을 제거해 `sampling.sampledRowCount/groups`로 이동했다. 캐시는 sampling v2 전체를 저장하고 mode/rate/seed/version만 정의 일치 여부로 비교해 실행 통계를 보존한다.
- **조치(정확도):** SUM/COUNT는 `EXTRAPOLATED_TOTAL`, AVG/STDDEV/VARIANCE는 `SAMPLE_ESTIMATE`, MIN/MAX는 `OBSERVED_EXTREME`, COUNT DISTINCT는 `OBSERVED_DISTINCT`로 분리했다. Admin 결과표와 SDK는 실제 표본 수·정확/추정·블록 표본 경고를 노출한다. SYSTEM 블록 상관을 무시한 가짜 95% 신뢰구간은 붙이지 않았다.
- **드리프트 방지:** server와 MSW mock이 같은 상수·계산 계약을 사용하고 공용 fixture에 SUM/COUNT/AVG/STDDEV/VARIANCE/MIN/MAX/COUNT DISTINCT 사례를 둔다. 캐시가 실제 표본 수를 덮어쓰지 않는지, 100% SQL에 TABLESAMPLE이 없는지, 자동 0.2%·실제 표본 수가 화면에 보이는지 단위/E2E로 고정했다.
- **재발 방지:** “설정”과 “실행 결과”를 구분한다. rate/seed는 정의, sampledRowCount/groups는 실행 통계다. 결과 그룹 수(`rowCount`)를 표본 입력 수처럼 사용하지 않으며, 집계 함수마다 통계적 의미를 명시한다.

### L19. STDDEV·VARIANCE 신뢰구간 누락 + NULL 포함 그룹 행수로 n 과대계상 🟠
- **증상:** INDEX_RANDOM 결과가 AVG/SUM/COUNT에는 95% 오차 배지를 제공했지만 사용자가 요구한 표준편차·분산 그래프에는 구간이 없었다. 또한 그룹에 NULL 값이 있으면 그룹 `COUNT(*)`를 모든 시리즈의 n으로 재사용해, 실제 비NULL 표본보다 n을 크게 잡고 오차를 과소 표시할 수 있었다. 유효 그룹과 n<30 그룹이 섞이면 소표본 경고가 사라지는 문제도 있었다.
- **원인:** `SamplingConfidence`의 대상 집계가 세 종류로 제한됐고 메타데이터가 시리즈당 하나의 대칭 MOE만 표현했다. SQL 숨은 통계도 그룹 전체 COUNT와 SUM/AVG용 mean/sd뿐이라 시리즈별 유효 n과 비대칭 분산 구간을 전달할 수 없었다.
- **조치:** sampling 계약을 v4로 올리고 `estimates[].intervals[{key,sampleCount,estimate,lower95,upper95,relativeErrorPct?}]`를 추가했다. INDEX_RANDOM SQL은 각 대상 열의 `COUNT(col)`·`AVG(col)`·`STDDEV_SAMP(col)`을 숨은 열로 수집한다. STDDEV·VARIANCE는 정규성 가정 아래 자유도 n−1 카이제곱 구간을 계산하며, `STDDEV_CI_NORMALITY_ASSUMED`를 Admin·SDK에 표시한다. 시리즈 요약 ±X%는 비대칭 구간 중 더 먼 쪽과 모든 그룹의 최댓값을 사용한다.
- **경계:** 이 구간은 데이터 분포에 대한 정규성 가정이 필요한 모수적 구간이다. SYSTEM 블록 표본에는 적용하지 않으며, INDEX_RANDOM이라도 비NULL n<30 그룹은 구간을 생략하고 `SMALL_SAMPLE_GROUPS`를 표시한다. 정확도 자체를 95%라고 표현하지 않고 **95% 신뢰수준의 추정 구간**이라고 표현한다.
- **미러·캐시:** MSW는 같은 v4 필드·경고를 반환하고, 캐시 직렬화 왕복이 그룹별 구간을 보존한다. v3 이하 캐시는 재계산 대상으로 처리한다.
- **검증:** 카이제곱 수치(STDDEV·VARIANCE), NULL 유효 n, 유효/소표본 혼합 경고, 숨은 SQL 열, 캐시 왕복, mock 계약, SDK 배지·정규성 경고를 단위 테스트로 고정했다. 최신 절대 수치는 `docs/테스트_전략.md`가 SSOT다.

### L20. SUM·COUNT 전체 외삽이 모집단 크기 추정 오차를 숨김 🟠
- **증상:** sampling v4는 SUM·COUNT에 `N̂/K` 또는 `100/rate`를 곱해 `전체 추정값`으로 표시했다. 그러나 `reltuples`는 계획용 근사 행수이고 SYSTEM은 블록 표본이므로, 배율 자체와 표본 구조의 불확실성을 함께 설명하지 않으면 큰 숫자가 실제 전체값처럼 보일 수 있었다.
- **결정:** MVP에서 SUM·COUNT는 선택된 표본의 합계·개수를 그대로 반환하고 `표본 합계`·`표본 개수`로 명시한다. AVG·STDDEV·VARIANCE만 모집단 통계의 추정값으로 다루며, INDEX_RANDOM에서 조건을 충족할 때 95% 추정 구간을 제공한다. 전체 구성 비교는 별도의 `% 점유율` 표현으로 다루고 자동 정규화하지 않는다.
- **조치:** `BuilderSqlBuilder`와 MSW 미러에서 모든 SUM·COUNT 배율을 제거했다. sampling v5에 `valueMode:"sample"`, `SAMPLE_AGGREGATE`, `SAMPLE_AGGREGATE_ONLY`를 도입하고 Admin·SDK 배지와 경고를 `표본 결과`로 변경했다. 값의 의미가 다른 v4 이하 캐시는 재계산되도록 계약 버전을 올렸다.
- **후속 경계:** `전체 추정값 보기`를 별도 옵션으로 추가할 때만 SUM·COUNT 외삽과 그 추정량에 맞는 오차구간을 함께 설계한다. 이 옵션 없이 모집단 행수 추정치를 배율로 재사용하지 않는다.
- **역사 기록:** L16·L18은 당시 외삽 계약을 구현한 과정의 기록이며 삭제하지 않는다. SUM·COUNT 해석은 L20이 유지되고, 현재 실행 계약은 sampling v9이 우선한다.

### L21. 개수 기반 표본 계약에 퍼센트 시대 계산·표현이 잔존 🟠
- **증상:** 자동 표본 UI와 계획기는 10,000행을 기준으로 바뀌었지만 일부 상수·주석·문서는 여전히 "약 100만 행" 또는 "5억 행의 0.2%"를 현재 동작처럼 설명했다. MSW는 선택한 테이블의 `estimatedRowCount` 대신 250만 행을 하드코딩했고, count 기반 INDEX_RANDOM 응답도 최상위 레거시 `sampleRate`를 정식 `sampling.rate`로 다시 주입할 수 있었다. 모집단 크기를 모를 때도 95% 오차범위가 항상 생기는 것처럼 안내했다.
- **원인:** 퍼센트 기반 SYSTEM 표본에서 개수 기반 INDEX_RANDOM 계획으로 이행하는 동안 `DEFAULT_SAMPLE_RATE`·자동 비율 헬퍼·레거시 응답 별칭과 sampling v5 정식 계약의 책임 경계가 남아 있었다. mock의 실행 계획도 서버 `SamplingPlanner`와 달리 seed 데이터의 테이블 통계를 사용하지 않았다.
- **조치(계획·mock):** 퍼센트 프리셋과 자동 비율 계산 상수를 제거하고 자동 목표를 10,000행, 직접 지정 범위를 1,000~50,000행으로 단일화했다. MSW는 현재 선택 테이블의 `estimatedRowCount`를 사용해 작은 테이블은 FULL_SCAN, 행 수 미상은 SYSTEM 폴백, 조건 충족 시 INDEX_RANDOM을 모사한다. count 기반 INDEX_RANDOM의 정식 nested 계약에는 `rate`를 넣지 않고 `populationEstimate`·`sampleSize`·`sampledRowCount`로 실제 의미를 전달한다.
- **조치(호환 경계):** `sampling` 객체가 존재하면 그 안의 스펙만 정식 계약으로 신뢰하고, 최상위 `sampleRate`는 nested 계약 자체가 없는 구버전 응답에만 정규화 입력으로 사용한다. 최상위 `sampleRate`는 구 SDK용 별칭으로 남기되 count 기반 정확도 계산에는 사용하지 않는다.
- **조치(표현):** 실행 전에는 "실행 후 실제 표본 수와 가능한 통계 구간을 표시"한다고 안내한다. 95% 구간은 INDEX_RANDOM이면서 집계·유효 표본 수 조건을 충족한 AVG·STDDEV·VARIANCE에만 표시하고, SYSTEM에는 블록 표본 경고만 제공한다. SUM·COUNT는 L20대로 표본값임을 명시한다.
- **검증:** Admin mock은 5억 행 테이블의 자동 목표가 `sampleSize=10,000`이고 정식 `rate`가 없음을, SDK는 최상위 레거시 `sampleRate`가 INDEX_RANDOM nested 계약을 오염시키지 않음을 단위 테스트로 고정했다. 개수 기반 결정은 그대로 유지되며 현재 실행 계약은 sampling v9이 우선한다. L16·L18의 비율 기반 내용은 역사 기록이다.

### L22. VIEW·물리화 뷰 미지원 + 조인 표본 금지로 실제 모집단을 뽑지 못함 🟠
- **증상:** 스키마 탐색이 일반 테이블만 반환해 고객이 이미 관리하는 VIEW·MATERIALIZED VIEW를 차트 원본으로 선택할 수 없었다. 조인이 있는 builderConfig에 `sample`을 넣으면 서버·Admin이 실행 전에 거부했고, 사용자는 조인 결과의 일부를 표본으로 시각화할 수 없었다. Admin의 [실행]은 집계와 raw 조인을 동시에 요청해 같은 구성을 불필요하게 두 번 실행했다.
- **원인:** 카탈로그가 `information_schema`의 테이블 중심 응답에 묶여 관계 종류와 `relispopulated`를 표현하지 못했다. 표본 SQL도 base 관계에 `TABLESAMPLE`을 붙이는 형태만 전제했기 때문에, 조인 선택률을 왜곡하지 않는 후단 표본 경로가 없었다. 프론트는 aggregate/rows를 `Promise.all`로 묶어 사용자가 상세 행을 보지 않아도 raw를 조회했다.
- **관계 카탈로그:** `pg_class`·`pg_namespace`·`pg_attribute` 기반으로 읽기 권한이 있는 TABLE·파티션 테이블·VIEW·MATERIALIZED VIEW와 컬럼 타입을 한 번에 읽는다. API는 `relationType`, 물리 관계의 `estimatedRowCount`, 물리화 뷰의 `populated`를 반환한다. 갱신되지 않은 물리화 뷰는 UI에서 비활성화하고 직접 preview도 409 `MATERIALIZED_VIEW_NOT_POPULATED`로 거부한다. 솔루션은 고객 DB 객체를 만들거나 갱신하지 않는다.
- **sampling v7 결과 표본 SQL:** `SamplingPlanner`가 VIEW·파티션 부모·JOIN을 `RESULT_RANDOM`으로 계획한다. `BuilderSqlBuilder`는 `EXPLAIN`으로 결과의 `N̂`을 구하고 `random() < min(1,K/N̂)`를 적용한다. 명시적 JOIN에는 `OFFSET 0` 실행 경계를 강제하고, JOIN 없는 View는 고비용 투영 지연을 위해 경계를 생략한다. 전체 `ORDER BY random()`·후보 재정렬·DuckDB reservoir는 사용하지 않는다.
- **통계 계약:** 조인 결과의 각 행을 모집단 단위로 본다. RESULT_RANDOM은 독립 Bernoulli라 목표 `sampleSize`와 실측 `sampledRowCount`가 다를 수 있으며 INDEX_RANDOM과 같은 95% 추정 구간 파이프라인을 사용한다. SUM·COUNT는 L20대로 표본 합계·표본 개수이며 외삽하지 않는다. 현재 sampling v9이 서버 캐시·Admin mock·임베드·SDK의 공통 계약이다.
- **Admin:** 관계 선택기와 탐색기에 VIEW/물리화 뷰 배지·갱신 상태를 표시한다. 조인을 추가해도 표본 설정을 유지하고 `조인 결과에서 무작위 행 표본` 또는 `뷰 조회 결과에서 무작위 행 표본`을 안내한다. [실행]은 aggregate만 요청하며 raw는 [원본 데이터] 탭을 열 때 지연 조회하고 구성 변경 시 폐기한다.
- **검증:** 서버 단위에서 계획 폴백·SQL 구조/파라미터·메타데이터/신뢰구간·카탈로그/API를, 실제 DuckDB에서 크로스소스 Bernoulli와 1:N JOIN 결과 행 독립성을 검증했다. 실제 PostgreSQL에서는 TABLE·VIEW·MATERIALIZED VIEW 카탈로그, VIEW/조인 RESULT_RANDOM의 seed 재현성, 표본 OFF 정확 집계, 물리화 뷰 SYSTEM, 미갱신 물리화 뷰 차단을 통합 검증한다. Admin mock/빌더·SDK는 현재 v9 배지와 가변 실측 행 수 회귀를 고정하며 최신 절대 수치는 `docs/테스트_전략.md`가 SSOT다.

### L23. 저장된 차트 편집 진입 시 미리보기보다 빌더 재실행에 의존 🟡
- **증상:** 저장된 노코드 구성은 복원되지만 우측 차트는 사용자가 [실행]을 다시 눌러야 보일 수 있었다. 코드에는 진입 후 자동 실행 플래그가 있었으나 정의·스키마 비동기 로드 순서와 실행 실패에 의존했고, 정상 동작해도 이미 저장한 결과를 고객 DB에서 불필요하게 다시 계산했다.
- **원인:** 저장 시 `mc_chart_cache`를 시드하고 단건 `/charts/{id}/preview`도 존재했지만, 편집기는 정의만 읽은 뒤 `POST /query/run-builder`를 호출하도록 구성되어 저장 캐시를 복원에 사용하지 않았다. 단건·목록 batch preview가 같은 얕은 응답이라 결과표에 필요한 rows도 없었다.
- **조치:** 단건 preview만 `columns/rows/elapsedMs`를 포함하고 목록 batch는 option만 유지하도록 계약을 분리했다. 편집 진입은 정의와 단건 preview를 병렬 조회해 노코드 폼·생성 SQL·실행 결과표·ECharts option을 한 번에 복원하며, 자동 `run-builder` effect를 제거했다. 구 서버처럼 rows가 없는 응답도 option만 표시하는 하위 호환 폴백을 둔다.
- **정합성:** 캐시 rows가 있으므로 저장 직후 옵션 변경은 SQL 재실행 없이 기존 `/charts/preview` option 재조립 경로를 그대로 사용한다. 데이터 구성 변경 시에만 캐시 화면을 무효화하고 사용자가 명시적으로 [실행]한다.
- **검증:** 서버 단위 테스트가 단건 rows 포함과 batch rows 제외를 각각 고정한다. Playwright는 `/charts/sales-db/public/sales/12` 진입 후 실행 버튼을 누르지 않고 결과 열과 canvas가 보이며 `/query/run-builder` POST가 0회임을 확인한다. 최신 수치는 `docs/테스트_전략.md`가 SSOT다.

### L24. 고정 미리보기와 고정 예약 높이로 FHD·사용자 글꼴 검수 불가 🟡
- **증상:** 우측의 작은 물리 영역에 맞춰서만 차트를 렌더하므로 작은 카드와 FHD가 같은 품질 기준으로 보였고, 큰 차트의 실제 글꼴·여백·밀도를 100%로 확인할 방법이 없었다. 미리보기 아래 옵션 편집기가 고정 높이를 차지해 큰 미리보기 공간도 확보하기 어려웠다.
- **원인:** 차트의 논리 설계 크기와 현재 편집 패널의 물리 크기를 구분하지 않았다. 미리보기는 단일 고정 영역이었고 fit/zoom, 패널별 접기, 최종 검수용 포커스 단계가 없었다. 레이아웃 예약 높이도 사용자 글꼴과 무관한 상수였다.
- **조치(설계 계약):** `options.display`에 360×240부터 FHD와 custom을, `options.typography`에 자동 배율과 요소별 px를 추가했다. 서버·mock은 논리 크기에서 글꼴을 결정하고 같은 글꼴로 제목·범례·visualMap 높이를 계산한다. 실제 임베드 DOM 크기는 계속 호스트 CSS 책임이다.
- **조치(미리보기):** `ChartDesignViewport`가 ECharts를 논리 폭·높이로 렌더한 뒤 바깥 wrapper만 CSS scale한다. 일반 패널에서 화면 맞춤, 중앙 패널을 접은 넓은 영역에서 너비 맞춤, 모든 단계에서 100%·25~200% zoom을 제공한다. 옵션은 미리보기 아래에 그대로 두고 경계 드래그·접기를 추가했다. 데이터 패널과 노코드 구성·결과는 각 헤더에서 독립적으로 접고 원래 가로 위치의 세로 레일에서 복원하며, 중앙을 접으면 미리보기가 남은 폭을 채운다.
- **후속 UX 교정:** 최초안의 단일 `영역 확대`는 좌측·중앙을 한 번에 숨겨 사용자가 어느 작업영역을 유지할지 선택할 수 없었다. 패널별 접기로 바꾼 뒤에도 펼치기 버튼을 전역 탭 줄 오른쪽에 둔 탓에 접힌 왼쪽 패널과 공간 관계가 끊겼다. 전역 정의 모드 줄을 제거하고 `노코드/SQL`을 중앙 `노코드 구성` 내부로 옮겼으며, 접힌 패널은 원래 자리의 40px 세로 레일로 복원하도록 교정했다.
- **상태 경계:** 설계 크기·글꼴은 차트 정의에 저장한다. 데이터/노코드/옵션 접힘과 패널 치수는 브라우저 `localStorage`, fit/zoom·포커스는 일시적 UI 상태로 두어 임베드 계약과 섞지 않는다.
- **시각 검수에서 잡은 빈틈:** 첫 구현의 옵션 편집기 기본 420px·최대 65%는 정상 패널에서 미리보기를 지나치게 눌렀다. 실제 640×360/FHD 화면을 비교한 뒤 기본 280px·최대 50%로 낮추고, 큰 검수는 노코드 패널 접기+옵션 접기 또는 전체 화면에 맡겼다.
- **검증:** display 순수 함수 단위 테스트, custom/FHD server/mock 공용 레이아웃 사례, S2 크기 선택·데이터/노코드/옵션 독립 접기·상태 복원·포커스 Playwright 회귀와 실제 Chromium 검수로 고정한다. 최신 절대 수치는 `docs/테스트_전략.md`가 SSOT다.

### L25. 지도 포인트가 사용자 조건과 무관하게 1,000개에서 잘림 🟠
- **증상:** 지도 포인트는 지역·기간 조건에 맞는 좌표를 모두 보여줘야 하지만 생성 SQL의 `LIMIT 1000`과 단일 DB JDBC의 `setMaxRows(1000)`이 이중으로 적용됐다. SQL LIMIT만 제거해도 실행 계층이 다시 자르며, 1,000행 이상이면 `truncated`도 무조건 참으로 계산했다.
- **원인:** 모든 차트 결과와 원본 미리보기가 하나의 고정 행 제한을 공유했고, `QueryRows`도 실행별 제한 정책을 전달받지 않았다. 지도 포인트는 집계 그룹 스냅샷이 아니라 실제 좌표 행 집합이라는 차이를 실행 계약에 표현하지 못했다.
- **조치:** 먼저 `geoscatter`의 SQL·JDBC 제한을 함께 제거했고, 이후 같은 원칙을 모든 실제 차트로 일반화했다. 단일 PostgreSQL과 다중 소스 DuckDB 라우터는 빌더 및 저장 SQL 차트에서 제한 없는 실행을 선택한다. `QueryRows.from(..., maxRows)`는 `maxRows=0`을 전량 실행으로 해석해 `truncated:false`를 보장한다. Admin MSW의 표시용 SQL도 동일하다.
- **경계:** `mode:"rows"` 원본 데이터 탭과 관계 preview의 1,000행 제한은 유지한다. 쿼리 타임아웃과 페더레이션 메모리 상한도 유지한다. 차트 데이터 축소는 시스템 고정 제한이 아니라 사용자가 선택한 표본추출로만 수행한다.
- **검증:** 서버 SQL 생성, 단일/다중 소스 실행 라우팅, JDBC `setMaxRows(0)`, 단위 1,001행 반환 시 비절단, 실제 PostgreSQL 조건 결과 1,205행 전량 반환, Admin mock SQL 계약을 테스트로 고정한다. 최신 절대 수치는 `docs/테스트_전략.md`가 SSOT다.

### L26. 지도 좌표가 두 숫자 컬럼에만 묶이고 편집 URL에 테이블 문맥이 없음 🟡
- **증상:** 고객 DB가 좌표를 PostGIS `geometry/geography(Point)` 한 컬럼으로 관리하면 지도 포인트 빌더에서 선택할 수 없었다. 저장 차트 편집 주소도 `/charts/{id}`뿐이라 앞으로 테이블 상세에서 해당 테이블 기반 차트를 연결할 URL 문맥이 없었다.
- **조치(공간 컬럼):** 카탈로그의 `format_type` 결과에서 SRID 지정 Point 타입만 선택지로 노출하고, `builder_config.geoPoint`에 숫자 컬럼/공간 컬럼 모드를 저장한다. 서버는 화이트리스트를 다시 검증한 뒤 `ST_Transform((point)::geometry,4326)`과 `ST_X/ST_Y`로 기존 행 계약에 투영한다. 선택적 숫자 크기값을 세 번째 열로 붙인다. 같은 소스 JOIN은 허용하고 여러 소스 공간 JOIN과 표본은 명확히 거부한다.
- **조치(URL):** 목록·단건 API가 `builder_config.table`과 현재 데이터소스 이름에서 `mainTable`을 파생해 반환하고 Admin 정식 경로를 `/charts/{datasourceName}/{schema}/{relation}/{chartId}`로 만든다. 신규 차트는 `/charts/new`를 사용하며 모든 저장 차트는 기준 관계를 필수로 가진다. DB 중복 컬럼이나 마이그레이션은 추가하지 않았다.
- **검증:** 실제 PostGIS 테스트 서비스에 Web Mercator Point 1,205건과 geography Point 3건을 삽입해 WGS84 변환·전량 조회·최종 ECharts 시리즈를 통합 검증한다. MSW에는 실제 대한민국 도시 좌표를 두고 UI 선택→요청 계약→생성 SQL→결과표→canvas를 E2E로 고정한다. URL은 순수 함수와 메인 관계를 포함한 정식 편집 경로를 검증하며 최신 절대 수치는 `docs/테스트_전략.md`가 SSOT다.

### L27. `/tables` 편집 전용 경로에 데이터소스·스키마 탐색 중간 화면 부재 🔵
- **문제:** `/tables/{datasourceId}/{schema}/{table}/charts/{id}`는 편집기 주소만 표현하고, 데이터소스 ID까지만 또는 스키마까지만 가진 URL에서 무엇을 보여줄지 정의하지 않았다. `tables`라는 이름도 같은 계층에 View와 Materialized View가 포함되는 현재 카탈로그 계약을 좁게 표현했다.
- **결정:** 사용자에게 보이는 최종 자원이 차트이므로 `/charts/{datasourceName}`에서 시작해 스키마→관계→차트 번호를 계층화한다. `/charts/new`는 정적 생성 경로이며 `new`를 데이터소스 예약 이름으로 둔다. 배포 전이므로 구 경로 리다이렉트는 만들지 않았다.
- **API 보강:** `GET /charts`의 `datasourceId`는 `mc_chart_datasource`를 조회해 조인 보조 소스까지 포함한다. `schema+relation`은 `builder_config.table`의 기준 관계만 필터링한다. URL은 탐색 문맥이고 DB 권위는 기존 JSONB·junction이므로 마이그레이션은 없다.
- **검증:** 경로 인코딩 단위 테스트, Chromium 데이터소스→스키마 검색→관계→관련 차트 동선, 저장 차트의 정식 URL 교체, 실제 PostgreSQL에서 조인 보조 소스·기준 관계 목록 필터를 검증한다. 최신 절대 수치는 `docs/테스트_전략.md`가 SSOT다.

### L28. 숫자 데이터소스 ID URL은 사람이 소스를 식별하기 어려움 🔵
- **문제:** `/charts/1/public/sales/1`은 안정적이지만 주소만 보고 어느 데이터소스인지 알 수 없다. 별도 slug는 사용자에게 새 식별자 개념과 관리 부담을 추가한다.
- **결정:** 이미 사용자별 고유 제약이 있는 `mc_datasource.name`을 URL 식별자로 사용한다. 예시는 `/charts/analytics-db/public/sales/1`이다. 한글·공백은 `encodeURIComponent`로 한 구간에 안전하게 인코딩한다.
- **책임 분리:** URL만 이름을 사용한다. DB FK, API 실행 입력, `builder_config.table`, 다중 소스 조인은 계속 숫자 `datasourceId`를 사용한다. 서버 목록·단건 응답은 `mainTable.datasourceName`을 현재 `mc_datasource.name`에서 파생해 내려주며 이 필드는 저장 입력에서 제외한다.
- **이름 변경:** 이름을 수정하면 다음 API 조회부터 새 이름이 정식 URL이 된다. 아직 배포 전이므로 이전 이름 주소의 리다이렉트나 별도 별칭 테이블은 두지 않는다.
- **검증:** 한글·공백 경로 인코딩 단위 테스트, 이름 기반 S5 전체 탐색, 이름 변경 후 링크, 저장 차트의 이름 기반 정식 편집 URL, 실제 PostgreSQL의 `mainTable.datasourceName` 파생을 검증한다. 최신 절대 수치는 `docs/테스트_전략.md`가 SSOT다.

### L29. 중앙 드롭다운과 좌측 카탈로그의 중복 관계 선택 경로 🟡
- **증상:** 원본·조인 관계를 중앙의 긴 드롭다운과 왼쪽 스키마 탐색기 양쪽에서 고를 수 있어 같은 기능의 진입점이 둘이었다. 관계가 수백 개면 중앙 드롭다운은 검색·스키마 필터·페이지 탐색을 재구현하지 않는 한 원하는 항목을 찾기 어렵고, 사용자는 왼쪽 목록 클릭이 원본과 어느 조인 중 어디에 들어가는지 알 수 없었다.
- **원인:** `NocodeBuilder`가 관계 옵션과 실제 선택 변경을 직접 소유하고 `SchemaExplorer`도 원본 변경을 수행했다. 새 조인은 사용자가 고르기 전에 현재 소스의 첫 미사용 관계를 자동 지정해 화면 밖의 암묵적 상태까지 만들었다.
- **조치:** `ChartEditor`가 `base`/`join(index)`/`newJoin` 선택 대상을 한 곳에서 소유한다. 중앙은 현재 관계와 `선택`/`변경`만 표시하고, 대상 클릭 시 왼쪽 패널을 자동으로 펼쳐 검색에 포커스한다. 검색 위 배너와 대상 칸의 파란 강조로 `원본 테이블 선택 중` 또는 `N번째 조인 테이블 선택 중`을 동시에 표시하며 취소 버튼·Esc로 종료한다. 왼쪽 관계 클릭은 선택 모드에서만 대상을 변경하고 평상시에는 컬럼 트리를 연다.
- **경계:** 기존 원본 교체는 조인·축·조건 초기화 확인을 유지한다. 조인은 원본·다른 조인에서 이미 사용한 관계를 비활성화한다. `+ 조인 추가`는 임시 `JoinSpec`을 만들지 않으며 실제 관계를 고른 순간에만 추가한다. 데이터소스 셀렉트는 구성 변경이 아니라 탐색 범위 변경으로 유지해 여러 소스 조인을 같은 흐름으로 선택한다.
- **검증:** 실제 Chromium에서 원본·새 조인·다른 소스 조인·View·Materialized View·기존 원본 교체, 선택 배너·검색 포커스·Esc/버튼 취소·중복 비활성을 포함한 S2 56개 회귀를 통과했다. 전체 절대 수치는 `docs/테스트_전략.md`가 SSOT다.

### M1. 서버에만 있던 `지금 갱신`이 동작 없는 버튼으로 남음 🟠
- **증상:** `POST /charts/{id}/refresh`와 캐시 재계산 서비스는 구현돼 있었지만 Admin의 `refreshNow`는 `Button`만 렌더하고 `onClick`이 없었다. 사용자는 갱신 모드를 선택해도 수동 갱신할 수 없었다.
- **원인:** 옵션 레지스트리는 저장 가능한 option을 렌더하는 데 집중했고, 차트 ID와 네트워크 상태가 필요한 action control의 상태 통로가 없었다.
- **조치:** `chartsApi.refresh`와 action props를 추가했다. 저장 차트에서만 활성화하고 미저장 변경이 있으면 저장을 먼저 안내한다. 성공하면 응답의 `computedAt`을 반영한 뒤 단건 preview를 재조회해 결과 rows와 option, 저장 preview snapshot을 함께 교체한다. refresh 실패와 refresh 성공 후 preview 실패를 구분한다.
- **효과:** 버튼·API·캐시·미리보기가 한 vertical slice로 완결됐다. 저장된 과거 정의와 현재 미저장 입력이 다를 때 잘못된 정의를 갱신하는 UX도 차단했다.
- **검증:** MSW Playwright가 성공, 신규/수정 중 비활성, 서버 오류 인라인 표시를 검증하고 실백엔드 E2E가 실제 PostGIS 차트의 refresh와 preview 재조회를 관통한다.

### M2. 브라우저 E2E가 MSW에 편중돼 실제 계약 차이를 가림 🟠
- **증상:** 기존 Playwright는 화면 회귀에는 강했지만 대부분 `NEXT_PUBLIC_E2E_MSW=true`였다. 데이터소스 암호화·PostgreSQL 카탈로그·PostGIS SQL·Spring 캐시·JWT·CORS는 한 테스트에서 연결되지 않았다.
- **조치:** `real-e2e` compose profile에 tmpfs PostGIS DB(`56432`)를 만들고 Spring(`8082`), MSW=false Admin(`3001`, `.next-realtest`)을 전용 프로세스로 기동한다. 테스트는 UI 데이터소스 등록→동적 Polygon 지도 생성·저장·재진입→지금 갱신→사용자/토큰 발급→실제 `/sdk.js` 임베드 canvas까지 실행한다. PID tree와 DB 컨테이너는 teardown에서 제거한다.
- **CI:** 일반 unit/build 외에 실DB `integrationTest`와 `real-backend-e2e` job을 추가했다.
- **효과:** mock 계약이 맞더라도 실제 CORS, 메시지, DB 타입, JWT가 다른 문제를 PR에서 발견할 수 있다. 기존 개발 DB·포트·Next 산출물을 건드리지 않는다.

### M3. 데이터소스 연결 결과가 mock은 한국어, 실서버는 영어 🟡
- **발견:** 첫 실백엔드 E2E에서 UI는 `Connection succeeded (Nms)`를 표시했고 MSW는 `연결 성공 (Nms)`을 표시했다.

### M6. 과거 `SUM` 기본 가정과 type 무시 raw mock이 현재 편집기 계약과 충돌 🟡

- **조치:** raw mock이 schema의 실제 text/numeric/date 타입으로 컬럼과 값을 생성하게 했다. 집계 결과를 검증하는 시나리오만 `SUM`을 명시하고 원본값 기본 시나리오는 그대로 유지했다. builder 구성이 바뀌면 기존 raw를 무효화하고 사용자가 [원본 데이터] 탭을 열 때 `mode:"rows"`로 지연 조회하도록 구현했다. locator는 role·exact·scope로 좁혔다.
- **효과·검증:** mock이 실제 서버의 컬럼 의미를 더 가깝게 반영하고 과거 기본값을 제품에 강제하지 않는다. 동시에 문서화된 aggregate/rows 요청 분리도 실제로 동작한다. Admin 단위 219개와 MSW Playwright 91개가 전부 통과한다.

### M9. 이동평균이 정렬을 조용히 덮고 범례를 만들 수 있으며, MSW 미러에 `@sort` 자체가 없었음 🟠

### M10. `POST /charts/{id}/refresh`만 소유자 범위 검사를 건너뛰고 재계산 계층으로 직행 🟠
- **증상:** 차트 목록·단건 조회·미리보기·수정·삭제·복제는 모두 `ownerId()`를 저장소 질의에 넘기는데, 수동 갱신만 `ChartService.refresh(id)`에서 곧바로 `ChartComputeService.recompute(id)`를 호출했다. 갱신 경로에는 "이 차트가 내 것인가"를 판정하는 지점이 아예 없었다.
- **영향:** 인증이 붙는 순간 열람 권한 없는 사용자가 임의 차트 ID로 POST해 ① 그 차트의 SQL을 고객 데이터소스에서 실제로 실행시키고 ② `mc_chart_cache`를 교체하며 ③ `computedAt`을 바꾸는 부수효과를 만들 수 있다. 응답에 rows는 없지만 `rowCount`·`elapsedMs`가 그대로 돌아가 차트의 존재 여부와 대략적 규모가 새어 나간다. 읽기 권한 없이 남의 DB에 부하를 거는 형태라 정보 노출보다 실행 트리거 쪽이 더 위험하다.
- **원인:** refresh가 "조회"가 아니라 "캐시 조작"으로 분류돼 조회 계열과 다른 흐름으로 구현됐다. `ChartComputeService`는 임베드 핫패스(`serve` → `refreshSingleFlight`)와 저장 직후 시드(`seedQuietly`)가 함께 쓰는 계층이라 설계상 `chartId`만 받고 owner 개념이 없다. `ChartService.refresh`가 그 계층을 그대로 호출하면서 사이에 있어야 할 인가 계층이 통째로 비었다.
- **조치:** `ChartService.refresh(id)`의 첫 줄에서 `charts.previewDefinition(ownerId(), id)`를 호출해 미리보기와 **같은** 범위 조건을 통과시킨다. 반환값은 쓰지 않고 접근 판정에만 사용하며, 왜 버리는지 주석으로 남겼다. 재계산 계층에는 owner 인자를 추가하지 않았다 — 임베드 서빙과 저장 시드가 같은 메서드를 공유하므로 인가는 HTTP 진입점의 책임으로 유지하는 편이 경계가 분명하다.
- **경계(중요):** `ChartRepository.appendOwnerScope`는 `ownerId == null`이면 조건을 붙이지 않고, 값이 있으면 `AND (owner_id=? OR owner_id IS NULL)`을 붙인다. 로그인이 없어 현재는 차트가 `owner_id NULL`로 저장되고 `ownerId()`도 비어 있으므로 **실질 격리는 아직 없다.** 이 수정은 refresh를 나머지 경로와 같은 수준으로 맞춘 것이지 격리를 완성한 것이 아니다. 완성은 인증 도입 시 `owner_id` 주입과 `OR owner_id IS NULL` 탈출구 제거로 이뤄진다(전수보고서 P0).
- **검증:** `ChartServiceTest.refreshChecksOwnerScopeBeforeRecomputing`이 `previewDefinition`이 `CHART_NOT_FOUND`를 던질 때 `ApiException`이 그대로 전파되고 `compute.recompute()`가 **한 번도 호출되지 않음**을 `verify(..., never())`로 고정한다. 재계산이 시작된 뒤 실패하는 것과 시작 자체가 없는 것은 부하 관점에서 다르므로 호출 횟수까지 검증한다.

### M11. `LocalTime` 초 단위 절삭으로 밀리초 시간축 순서가 뒤집힘 + MSW 미러에 시간 단독 파싱 부재 🟡
- **증상:** X축이 시간 단독(`time`) 컬럼인 선 차트에서 이동평균을 켜면 `12:00:00.100`과 `12:00:00.900`의 순서가 입력 순서 그대로 남아 SMA 구간이 실제 시간 순서와 어긋났다.
- **원인 1(서버):** `temporalSortKey`가 `LocalTime`을 `(long) time.toSecondOfDay() * 1_000`으로 변환해 밀리초를 버렸다. 두 값의 정렬 키가 같아지고 안정 정렬이 입력 순서를 그대로 유지했다.
- **원인 2(MSW 미러):** `temporalValue`가 문자열을 `Date.parse`로만 처리했다. `Date.parse('12:00:00.900')`은 `NaN`이라 시간 단독 값이 전부 "정렬 키 없음"으로 떨어져 원본 순서가 유지됐다. 날짜·타임스탬프 값은 우연히 양쪽 결과가 같았기 때문에, 계약 fixture가 날짜만 다루는 동안에는 이 차이가 드러나지 않았다.
- **조치:** 서버는 `time.toNanoOfDay() / 1_000_000`으로 밀리초 해상도를 유지한다. MSW는 `timeOnlyValue()`를 추가해 `HH:mm` / `HH:mm:ss` / `HH:mm:ss.[1~9자리]`를 `Java LocalTime.parse`와 같은 규칙으로 자정 이후 밀리초로 바꾸고, 시·분·초 범위를 벗어나면 `null`을 돌려 `Date.parse` 경로로 넘기지 않는다.
- **경계:** 두 구현 모두 밀리초 미만을 버린다. PostgreSQL `time(6)`의 마이크로초는 정렬 키에 반영되지 않고 같은 밀리초 안에서는 입력 순서가 유지된다. 의도된 동작이며 양쪽이 동일하다.
- **검증:** fixture `moving-average-sorts-time-only-values-like-java-local-time`이 `12:00:00.900 / 08:15:00 / 12:00:00.100 / 18:30:00` 입력에 대해 `xAxis.data` 순서와 SMA 값을 Java·TS 양쪽에서 고정한다. 소수 1·2·3·4·5·6·9자리 전 구간을 대조해 Java 정수 나눗셈 절삭과 TS `Math.floor` 결과가 전부 일치함을 확인했다.

### M12. 갱신이 되돌려준 파생 `autoColorMap`이 사용자 변경 없이 편집기를 미저장 상태로 만듦 🟡
- **증상:** 저장된 차트에서 `지금 갱신`을 누르면, 서버 응답 option에 새 계열 색이 포함될 때 편집기가 즉시 미저장 상태가 됐다. 방금 갱신했는데도 다시 누르려 하면 `변경사항을 저장한 뒤 갱신하세요.`로 막혔고, 이탈 시 저장 확인 모달까지 떴다.
- **원인:** `__chartsdkAutoColorMap`은 변환기가 팔레트와 계열명에서 계산하는 **파생값**인데, 편집기는 새 계열이 생겨도 색이 흔들리지 않도록 이 값을 `options.autoColorMap`에 되쓴다. 갱신 경로는 라이브 옵션에만 되쓰고 저장 스냅샷의 definition은 그대로 뒀기 때문에 `editorDefinitionEquals`가 달라졌다. 사용자가 아무것도 바꾸지 않았는데 dirty가 되는 오탐이다.
- **조치:** `withResolvedAutoColorMap(options, autoColorMap)`을 도입했다. 이미 같은 맵이면 원본 객체를 그대로 돌려주어 불필요한 리렌더와 비교 실패를 막고, 다를 때만 복제해 넣는다. 갱신 성공 시 라이브 옵션과 저장 스냅샷 definition에 **같은 맵을 함께** 적용한다. 미리보기 응답을 반영하는 `applyResolvedOption`도 같은 함수를 쓰도록 통일해 되쓰기 지점을 하나로 모았다.
- **경계:** 갱신으로 새로 생긴 색상 맵을 DB에 즉시 쓰지는 않는다. 서버가 매 변환에서 다시 계산하는 파생값이므로 저장하지 않는 편이 "사용자 변경만 dirty"라는 규칙과 맞고, 갱신이 조용히 저장 부수효과를 내지 않는다.
- **검증:** Admin 단위가 같은 맵을 적용한 현재 옵션과 저장 스냅샷이 `editorDefinitionEquals`로 동등함을 고정한다. S2 갱신 E2E는 preview 응답을 가로채 없던 계열 색을 주입한 뒤에도 `지금 갱신` 버튼이 활성으로 남고 저장 안내가 나타나지 않음을 확인한다.

### M13. 결과 캐시의 잠금 프록시·정의 버전·실패 상태·저장 이중 조회 불일치 🟠
- **발견:** `ChartComputeService.serve()`가 같은 객체의 `@Transactional refreshSingleFlight()`를 직접 호출해 Spring AOP 프록시를 우회했다. transaction-scoped advisory lock이 실제 임베드 경로에서는 요청 전체를 감싸지 못할 수 있었다. 다중소스는 버전을 검사하지 않는 stale 조회를 사용해 수정 뒤 시드 실패 시 이전 정의 결과를 반환할 수 있었고, DB의 `last_error` 필드는 성공 때 지우기만 할 뿐 실패를 쓰지 않았다. 저장도 검증 실행 뒤 `seedQuietly`가 원본 DB를 다시 조회했다.
- **조치(동시성):** `ChartRefreshCoordinator`를 별도 Spring 빈으로 분리하고 그 공개 메서드에 트랜잭션 경계를 둔다. 캐시 미스 경로만 `pg_try_advisory_xact_lock`을 잡으며, 락 경쟁 요청은 정의 버전·표본 계약이 모두 같은 stale만 반환한다. `live` 경쟁 요청은 승자 요청 이후 생성된 결과만 받아 승자 실패 뒤 과거 값을 반환하지 않는다.
- **조치(정합성·실패):** `findCompatible(chartId, definitionVersion, sampling)`으로 단일·다중·락 대기 경로를 통일했다. TTL이 지난 데이터 stale은 허용하지만 정의 stale은 금지한다. V5는 `result/computed_at`이 함께 NULL인 error-only 캐시 행을 허용하고, `recordFailure(REQUIRES_NEW)`가 기존 성공 결과를 보존한 채 실패 시각과 원인을 남긴다. 성공 UPSERT는 실패 상태를 지운다.
- **조치(원본 부하):** 저장 준비 결과에 `QueryRows`와 실행된 sampling 메타데이터를 포함한다. 생성은 version 0, 수정은 `UPDATE ... RETURNING version` 결과로 같은 rows를 즉시 UPSERT한다. raw SQL도 제한 검증 후 전량 재조회하지 않고 처음부터 한 번만 unbounded 실행한다.
- **브라우저 경계:** `/api/**`는 `Cache-Control:no-store`로 서버의 `live/ttl/manual` 정책을 우회하지 않는다. 폰트와 기본 지도는 `chart-options/assets.ts`의 버전으로 URL을 분리해 1년 immutable 캐시하고, 고정 이름 `sdk.js`는 매 배포 재검증한다. Redis는 도입하지 않았으며 결과 캐시의 단일 저장소는 PostgreSQL `mc_chart_cache`다.
- **검증:** coordinator 트랜잭션 경계·승자/패자·live 실패 복구, 정의 버전 캐시 호출, 실패 기록, 저장 결과 재사용, raw SQL 1회 실행, API/지도 헤더, SDK no-store·버전 URL을 서버 JUnit과 SDK Vitest로 고정한다.

### M14. 8종 편집기 옵션과 실제 차트 변환 계약 드리프트 🟠
- **증상:** 원형 차트는 데이터 라벨을 켜지 않아도 ECharts 기본값 때문에 라벨이 보일 수 있었다. 산점도의 숫자 X축 설정은 레지스트리에 있어도 `showIf`가 참이 되지 않아 UI에 나타나지 않았고, 지도 경계·기준 시각 표시처럼 저장값은 있으나 미리보기/SDK까지 이어지지 않는 옵션도 있었다. 버블 크기 컬럼은 크기 차원인 동시에 별도 Y 시리즈·색 대상이 됐고, Java 운영 변환기와 MSW 미러의 누락 기본값·숫자축·색·variant 처리가 서로 달랐다.

## N. 운영 전 대용량 쿼리·정합성·자동 포인트 표본 개선 (2026-08-05)

> 이 장은 100만 건 이상의 원본 데이터와 다수 고객의 동시 사용을 전제로 수행한 최신 개선의 기술 기록이다. 로그인·인증·테넌트 격리 강화는 요청에 따라 이번 범위에서 제외했다. M13은 당시의 문제 발견과 1차 개선 이력으로 보존하지만, M13에 적힌 **고객 쿼리 실행 중 transaction-scoped advisory lock을 유지하는 방식은 이 장의 만료형 DB lease 설계로 대체됐다.** 운영 판단은 이 장을 기준으로 한다.

### N1. 변경 목표와 지켜야 할 제품 계약

- **결과 용량 계약:** 실제 차트 실행 결과에는 제품 차원의 행 수 상한을 두지 않는다. 데이터가 크다는 이유만으로 막대·원형·선·일반 히트맵을 임의 축소하지 않는다.
- **탐색 계약:** 원본 데이터 탐색과 스키마 미리보기는 화면에서 최대 1,000행만 반환한다. 탐색 응답을 작게 유지하는 정책과 실제 차트 계산의 전체 결과 정책을 분리한다.
- **자동 표본 계약:** 자동 표본은 브라우저가 개별 점을 그려야 하는 `scatter`, `geoscatter`, `map + geoSeriesType=heatmap`의 **집계되지 않은 원본 포인트**에만 적용한다. 사용자가 기존 표본추출 토글을 끄면 전체 결과로 그린다.
- **수동 표본 계약:** 기존 `manual` 표본의 차트 종류·크기·비율·seed 동작은 유지한다. 이번 의미 기반 제한은 시스템이 자동으로 개입하는 `auto`에만 적용한다.
- **기능 보존 계약:** 원본 테이블/JOIN 변경 시 데이터 컬럼 초안만 제거하고 조건·표본·LIMIT와 차트별 시각화 옵션을 보존하는 `chartTypeDrafts` 동작은 바꾸지 않는다. 저장 버전 상태는 초안 저장소와 분리한다.
- **트랜잭션 계약:** 고객 DB 쿼리, 대형 JSON 직렬화, DB lease 대기를 메타데이터 DB 트랜잭션 안에서 수행하지 않는다. 메타데이터 변경은 짧고 원자적인 writer 서비스에서만 처리한다.

### N2. 고객 쿼리 admission control 도입

#### 기존 위험

쿼리별 JDBC timeout만으로는 동시에 들어오는 요청 수를 제어할 수 없다. 고객 여러 명이 대형 미리보기·차트·표본·카탈로그·페더레이션 요청을 동시에 시작하면 애플리케이션 스레드, 고객 DB 커넥션 풀, 메타 DB와 JVM heap이 함께 압박받는다. 개별 쿼리가 10초 안에 끝나더라도 100개가 동시에 실행되는 상황은 방지하지 못한다.

#### 구현

`server/src/main/java/com/chartsdk/query/QueryExecutionCoordinator.java`를 모든 고객 DB 작업의 공통 admission 계층으로 추가했다.

1. 데이터소스 ID를 중복 제거하고 오름차순 정렬한다. 페더레이션이 여러 데이터소스 permit을 얻을 때 항상 같은 순서로 획득해 교착 가능성을 없앤다.
2. 데이터소스별 fair semaphore를 얻는다. 한 고객 DB의 느린 쿼리가 다른 데이터소스의 실행 슬롯까지 독점하지 못한다.
3. 페더레이션이면 별도의 낮은 동시성 permit을 추가로 얻는다. 페더레이션은 여러 원본 연결과 DuckDB 연산을 함께 사용하므로 단일 소스보다 엄격하게 제한한다.
4. 전역 fair semaphore를 얻는다. 모든 permit은 별도 대기시간을 다시 부여하지 않고 하나의 deadline을 공유한다.
5. 실행 종료 시 전역 → 페더레이션 → 데이터소스 역순으로 해제한다. 일부 permit만 얻은 상태에서 timeout 또는 interrupt가 발생해도 `finally`에서 이미 얻은 permit을 반환한다.

기본값은 다음과 같다.

| 환경변수 | 기본값 | 의미 |
|---|---:|---|
| `QUERY_MAX_CONCURRENT` | `24` | 인스턴스 전체 고객 DB 작업 수 |
| `QUERY_MAX_CONCURRENT_PER_DATASOURCE` | `4` | 데이터소스 하나당 동시 작업 수 |
| `QUERY_MAX_CONCURRENT_FEDERATED` | `2` | 페더레이션 동시 작업 수 |
| `QUERY_ADMISSION_WAIT_MILLIS` | `2000` | permit 획득 전체 대기 deadline |

작업 종류는 `preview`, `chart`, `sample`, `explain`, `catalog`, `federation`으로 분류한다. Micrometer 지표는 다음과 같다.

- `chartsdk.customer_query.wait{kind}`: admission permit 대기시간
- `chartsdk.customer_query.duration{kind,outcome=success|error}`: 실제 실행시간
- `chartsdk.customer_query.rows{kind}`: `QueryRows` 결과 행 수 분포
- `chartsdk.customer_query.rejected{reason=admission_timeout}`: 대기시간 안에 permit을 얻지 못한 요청 수

데이터소스 ID를 metric label에 넣지 않았다. 고객 수가 늘어날수록 시계열 cardinality가 무한히 커지는 운영 장애를 피하기 위한 의도적인 결정이다. 데이터소스별 원인 분석은 요청 로그와 DB 풀 지표를 결합한다.

#### 오류 계약

- permit deadline 초과: HTTP 503 / `QUERY_BUSY`
- admission 대기 중 thread interrupt: HTTP 503 / `QUERY_INTERRUPTED`

`QUERY_BUSY`는 SQL 오류가 아니라 부하 보호가 정상 작동한 결과다. 클라이언트는 짧은 backoff 후 재시도할 수 있지만, 무제한 즉시 재시도해서는 안 된다.

### N3. 차트 결과 무제한과 원본 탐색 1,000행 경계 분리

`server/src/main/java/com/chartsdk/query/QueryExecutor.java`의 실행 모드를 명시적으로 나눴다.

- `MAX_ROWS = 1_000`: 미리보기, 검증 조회, 원본 데이터 탐색에만 사용한다. raw builder의 `mode:"rows"`와 스키마 탐색 경로도 `LIMIT 1000` 계약을 유지한다.
- `UNBOUNDED_CHART_ROWS = 0`: JDBC `PreparedStatement.setMaxRows(0)`의 의미를 사용해 실제 차트 결과에 제품 상한을 두지 않는다. 단일 PostgreSQL, 캐시 표본의 최종 집계, DuckDB 페더레이션 차트 경로가 같은 상수를 사용한다.
- `MAX_CACHED_SAMPLE_ROWS = 75_000`: 자동/수동 표본의 **내부 pre-aggregation L1 표본 실현값**이 Bernoulli 변동으로 비정상적으로 커지는 경우를 막는 방어선이다. 최종 차트 결과 제한이 아니다. 초과 시 잘린 값을 조용히 반환하지 않고 HTTP 413 / `SAMPLE_REALIZATION_TOO_LARGE`로 실패시킨다.

PostgreSQL에서 전체 차트 결과를 읽을 때 connection이 auto-commit이면 임시로 transaction을 열고 `fetchSize=1_000`을 설정해 서버 cursor 단위로 가져온 뒤 rollback한다. 이는 고객 DB와 애플리케이션 사이의 한 번에 전송되는 양을 줄이는 JDBC cursor fetch다. 그러나 현재 HTTP API는 streaming 응답이 아니므로 `QueryRows`와 JSON 응답은 JVM 메모리에 전체 materialize된다. 따라서 “행 상한 없음”은 “메모리 비용 없음”을 뜻하지 않는다. admission control과 자동 포인트 표본이 현재의 1차 보호선이며, 수백 MB 이상의 단일 응답이 실제 운영 요구가 되면 별도 과제로 HTTP streaming/Arrow·비동기 export·서버측 집계 중 하나를 도입해야 한다.

timeout은 실행 목적별 정책으로 분리한다. 원본 탐색·카탈로그·EXPLAIN은 10초, 차트 계산·표본·DuckDB 페더레이션은 30초다. 값은 `QueryTimeoutPolicy`와 `QUERY_TIMEOUT_*_SECONDS`에서 관리하며, timeout은 동시성 제한과 별도의 방어선이다. 초과는 HTTP 408 / `QUERY_TIMEOUT`, SQL 검증·실행 오류는 `SQL_ERROR`, 페더레이션 엔진 오류는 `FEDERATION_ERROR`로 구분한다.

### N4. 차트 정의 저장의 원자성 및 optimistic version handshake

#### 기존 위험

차트 본문 저장과 `mc_chart_datasource` 관계 갱신이 분리되면 중간 실패 시 차트 정의와 연결 데이터소스 집합이 달라질 수 있다. 또한 두 브라우저가 같은 차트를 열고 순서대로 저장하면 마지막 저장이 앞선 변경을 아무 경고 없이 덮어쓸 수 있다. 복제 경로는 다중 데이터소스 관계를 빠뜨릴 가능성도 있었다.

#### 구현 경계

`ChartService`는 먼저 고객 DB에서 정의 검증과 결과 준비를 끝낸다. 이 구간에는 메타데이터 write transaction이 없다. 이후 `server/src/main/java/com/chartsdk/chart/ChartDefinitionWriter.java`가 다음 작업만 짧은 `@Transactional`로 수행한다.

- 생성: `mc_chart` 생성과 `mc_chart_datasource` 설정을 한 transaction으로 묶고 version `0`을 반환한다.
- 수정: 요청 version을 조건으로 `UPDATE ... RETURNING version`을 실행하고 연결 데이터소스 집합을 같은 transaction에서 교체한다.
- 복제: 차트 본문, 데이터소스 관계, 호환 캐시를 같은 복제 작업으로 처리한다.

업데이트 대상이 존재하지만 요청 version이 오래됐으면 HTTP 409 / `VERSION_CONFLICT`, 대상 자체가 없으면 HTTP 404 / `CHART_NOT_FOUND`를 반환한다. UI는 조회 응답의 `version`을 `savedVersion`으로 보관하고 생성 응답은 `0`, 수정 응답은 증가된 version으로 다시 동기화한다. MSW도 생성 `0`과 수정 시 증가 동작을 똑같이 구현해 로컬/E2E가 운영 서버와 다른 저장 경쟁을 숨기지 않게 했다.

기존 클라이언트의 일괄 장애를 피하기 위해 version 강제는 observe-first 방식이다.

- `chartsdk.chart.update.version_missing`: version 없이 수정한 요청 수
- `CHART_REQUIRE_UPDATE_VERSION=false`: 현재 기본값. 누락을 계측하되 즉시 차단하지 않는다.
- `CHART_REQUIRE_UPDATE_VERSION=true`: 누락 요청을 HTTP 428 / `CHART_VERSION_REQUIRED`로 차단한다.

운영에서는 누락 지표가 0이거나 알려진 레거시 호출만 남았음을 확인한 뒤 강제를 켠다. `VERSION_CONFLICT`를 받은 편집기는 서버 정의를 다시 읽고 사용자가 병합/재적용하도록 해야 하며, 동일 payload를 오래된 version으로 반복 재시도하면 안 된다.

### N5. 결과 캐시 version fence와 짧은 transaction

고객 쿼리가 끝나는 사이 차트 정의가 수정될 수 있으므로 “실행을 시작할 때 읽은 version”만 확인해서는 부족하다. 이전 정의로 계산한 결과가 늦게 도착해 새 정의의 `mc_chart_cache`를 덮을 수 있기 때문이다.

현재 캐시 쓰기 순서는 다음과 같다.

1. 계산 시작 전에 차트 정의와 version을 읽는다.
2. 고객 DB 쿼리를 transaction 밖에서 실행한다.
3. 결과와 sampling metadata를 JSON으로 직렬화한다. 대형 직렬화도 메타데이터 transaction 밖이다.
4. `ChartCacheWriter.upsert(..., expectedVersion)`가 `REQUIRES_NEW`의 짧은 transaction을 시작한다.
5. `SELECT version FROM mc_chart WHERE id=? FOR SHARE`로 현재 version을 확인한다.
6. version이 같을 때만 `mc_chart_cache`를 UPSERT하고 `last_error`, `last_error_at`을 지운다.

version이 달라졌으면 HTTP 409 / `CHART_DEFINITION_CHANGED`를 발생시켜 오래된 결과를 폐기한다. 이 오류는 데이터 쿼리 자체의 실패가 아니라 저장 경쟁에서 새 정의가 이긴 정상적인 fence다. 같은 이유로 오래된 계산의 실패도 새 정의의 `last_error`를 덮지 않으며, 성공 캐시가 있을 때 실패 기록은 결과를 삭제하지 않고 오류 시각·원인만 갱신한다.

캐시 조회 호환성은 최소한 `chartId + definitionVersion + sampling contract`를 모두 확인한다. TTL이 지난 **같은 정의**의 결과는 정책에 따라 stale로 사용할 수 있지만, version이 다른 정의 stale은 반환하지 않는다. 저장 직전 이미 준비한 `QueryRows`를 캐시 seed에 재사용하므로 원본 고객 DB를 같은 저장 요청에서 두 번 읽지 않는다.

### N6. 차트 갱신 single-flight: 장시간 advisory transaction을 만료형 lease로 교체

M13의 1차 방식은 `pg_try_advisory_xact_lock`을 통해 갱신 승자를 정했지만, transaction-scoped lock을 고객 DB 쿼리 전체 동안 보존하려면 메타데이터 DB transaction과 connection도 같은 시간 점유해야 했다. 다중 인스턴스에서 중복 실행은 줄여도 느린 외부 쿼리가 메타 DB 자원을 붙잡는 구조였다.

현재 `ChartRefreshCoordinator`는 두 단계 single-flight를 사용한다.

- **같은 인스턴스:** `(chartId, definitionVersion)`을 key로 한 `ConcurrentHashMap<RefreshKey, CompletableFuture>`를 사용한다. 첫 요청만 실행하고 나머지는 같은 future를 기다린다.
- **여러 인스턴스:** `mc_chart_refresh_lease`의 chart별 행을 짧은 UPSERT로 획득한다. lease에는 `definition_version`, 임의 UUID `lease_token`, `expires_at`이 있다. 만료됐거나 다른 definition version이면 새 요청이 인수할 수 있다.

lease를 획득한 뒤 고객 쿼리를 실행하는 동안 메타데이터 transaction은 열려 있지 않다. 완료 시 `chart_id + lease_token` 조건으로 자신의 lease만 삭제한다. 삭제가 실패해도 원래 쿼리 결과를 가리지 않으며 만료시간이 복구를 보장한다.

경쟁 요청의 동작은 다음과 같다.

- `allowStale=true`: definition version과 sampling contract가 같은 stale 캐시가 있으면 즉시 반환할 수 있다.
- live 또는 stale 불허: 기존 `computedAt`을 기억하고 cache/lease를 polling한다. 승자 이후 새로 기록된 호환 결과만 반환하며, 과거 결과를 새 결과로 오인하지 않는다.
- 대기 deadline 안에 새 결과도 lease도 얻지 못하면 HTTP 503 / `REFRESH_IN_PROGRESS`를 반환한다.
- 대기 thread가 interrupt되면 HTTP 503 / `REFRESH_INTERRUPTED`를 반환한다.

기본값은 `CHART_REFRESH_LEASE_SECONDS=45`, `CHART_REFRESH_WAIT_SECONDS=35`, `CHART_REFRESH_POLL_MILLIS=100`이다. `wait < lease`를 유지하고, lease는 최악의 쿼리 timeout뿐 아니라 JSON 직렬화와 캐시 insert 여유까지 포함해 설정해야 한다. 현재 heartbeat/lease renewal은 없다. 매우 큰 동일-version 계산이 45초를 넘으면 다른 인스턴스가 lease를 인수해 같은 계산을 중복 수행할 수 있다. definition version fence는 잘못된 정의의 캐시 덮어쓰기는 막지만 동일 version 중복 부하는 막지 않으므로, 이런 사례가 관측되면 무작정 lease를 크게 늘리기 전에 장기 작업용 renewal 또는 비동기 job queue를 검토한다.

### N7. L1 표본 캐시 build lease와 용량 quota

조인 후 Bernoulli 표본처럼 재사용 비용이 큰 중간 결과는 `mc_sample_row_cache`에 저장한다. 기존 장시간 lock 대신 `mc_sample_cache_build_lease(fingerprint, lease_token, expires_at)`를 사용해 같은 fingerprint를 여러 인스턴스가 동시에 만들지 않게 했다.

처리 순서는 cache 조회 → 인스턴스 내 global/데이터소스별 build permit → cache 재확인 → DB lease 획득 → transaction 밖 loader 실행 → transaction 밖 payload 직렬화 → 짧은 quota transaction 저장 → token 조건 release다. 다른 인스턴스가 만들고 있으면 polling 중 완성된 cache를 사용하고, deadline을 넘기면 HTTP 503 / `SAMPLE_CACHE_BUSY`를 반환한다.

여기에는 의도적으로 남긴 advisory lock이 하나 있다. 서로 다른 fingerprint의 쓰기가 동시에 끝나도 per-datasource/global byte quota를 정확히 지키기 위해 **직렬화가 끝난 뒤의 짧은 cache insert·LRU eviction transaction**만 `pg_advisory_xact_lock`으로 직렬화한다. 이 lock 안에서는 고객 DB 쿼리나 JSON 직렬화를 하지 않는다. 따라서 제거한 “장시간 고객 쿼리 lock”과 같은 문제가 아니다.

| 환경변수 | 기본값 | 의미 |
|---|---:|---|
| `SAMPLE_CACHE_DEFAULT_MAX_AGE_SECONDS` | `900` | 기본 재사용 가능 시간 |
| `SAMPLE_CACHE_HARD_TTL_SECONDS` | `86400` | 절대 보존 상한 |
| `SAMPLE_CACHE_MAX_ENTRY_BYTES` | `67108864` | 한 항목 64 MiB |
| `SAMPLE_CACHE_MAX_DATASOURCE_BYTES` | `134217728` | 데이터소스별 128 MiB |
| `SAMPLE_CACHE_MAX_TOTAL_BYTES` | `536870912` | 전체 512 MiB |
| `SAMPLE_CACHE_MAX_CONCURRENT_BUILDS` | `2` | 인스턴스별 동시 build 수 |
| `SAMPLE_CACHE_BUILD_LEASE_SECONDS` | `45` | 분산 build lease |
| `SAMPLE_CACHE_BUILD_WAIT_SECONDS` | `35` | 경쟁 build 대기시간 |
| `SAMPLE_CACHE_BUILD_POLL_MILLIS` | `100` | cache/lease 확인 주기 |

한 항목이 64 MiB를 넘으면 요청 결과 자체는 정상 반환하되 cache 저장만 건너뛰고 warning log를 남긴다. 반면 내부 Bernoulli 실현 행 수가 75,000을 넘는 경우는 잘린 cache를 만들지 않기 위해 `SAMPLE_REALIZATION_TOO_LARGE`로 명시적으로 실패한다.

### N8. 자동 표본을 원본 포인트 렌더러에만 적용

`PointSamplingPolicy`를 별도 순수 정책 객체로 분리해 Java 실행 경로와 TypeScript UI/MSW 미러가 같은 의미를 사용하도록 했다. `sample.mode == "auto"`일 때 아래 조건을 모두 만족해야 표본을 적용한다.

1. 차트 종류가 `scatter`, `geoscatter`이거나 `chartType=map`이면서 `geoSeriesType=heatmap`이다.
2. 공간 `Point` 컬럼을 직접 쓰는 `geoPoint.mode=spatial`이거나, Y축이 하나 이상이고 모든 Y축의 `agg`가 `none`이다.

따라서 막대·원형·선·표 형태·격자 히트맵·박스플롯·지도 영역은 자동 축소하지 않는다. 산점도라도 `SUM`, `AVG` 등으로 이미 집계된 결과는 그룹 수만 렌더하므로 자동 표본하지 않는다. 사용자가 표본 토글을 끄면 sample 설정이 제거되어 전체 결과를 실행한다. `manual`은 기존 사용자 의도를 존중해 같은 차트 종류 제한을 받지 않는다.

이 정책은 “100만 행 자체가 무조건 문제”라는 가정 대신 “브라우저가 100만 개의 symbol/지도 point를 생성하는가”를 기준으로 한다. 선 차트 시간축 다운샘플, 막대 top-N+기타, 원형 그룹 표본, 격자 히트맵 bin 확대는 이번 구현에서 하지 않았다. 결과 의미를 자동으로 바꾸는 위험이 점 렌더 비용보다 크기 때문이다.

### N9. 자동 표본 planner의 선택 규칙

자동 포인트 표본의 기본 목표는 10,000행이다. 수동 표본의 기존 허용 범위 1,000~50,000과 legacy rate/SYSTEM 고정 계약은 그대로 유지한다.

#### WHERE/JOIN이 있는 경우

큰 원본 테이블이 WHERE/JOIN 후 작은 결과가 될 수 있으므로 base table 크기만 보고 먼저 표본하지 않는다. `EXPLAIN (FORMAT JSON)`의 JOIN+WHERE 이후 `Plan Rows`를 모집단 추정치로 사용한다.

- 추정 결과가 목표 이하: `FULL_SCAN`, 정확한 전체 결과
- 추정 결과가 목표 초과: JOIN+WHERE 뒤의 `RESULT_RANDOM` Bernoulli 표본

이 방식은 join 전 한쪽 테이블을 먼저 뽑아 관계 분포를 왜곡하는 문제를 피한다. PostgreSQL 통계가 오래되어 `Plan Rows`가 실제보다 작더라도 sampling v9의 `ReservoirPointCollector`가 자동 포인트 `FULL_SCAN` 결과를 수집하면서 실측 행 수가 K를 넘는 순간 bounded reservoir로 전환한다. 따라서 planner 오차가 100만 포인트 materialization으로 이어지지는 않는다. 쿼리 자체는 정확한 모집단 N 계산을 위해 끝까지 scan하므로 실행시간·DB I/O는 timeout과 admission으로 별도 통제한다.

#### 필터 없는 물리 테이블

`pg_class.reltuples`와 관계 종류를 읽어 모집단을 추정한다. 자동 모드에서는 추정치가 10,000 이하일 때 정확한 `FULL_SCAN`을 사용한다. 그보다 크면 다음 순서로 선택한다.

- 단일 정수 PK가 있고 `population / (max(pk)-min(pk)+1) >= 0.5`: 균일 난수 key probe 기반 `INDEX_RANDOM`
- key 밀도가 낮거나 PK가 없고 TABLESAMPLE 가능한 관계: `SYSTEM` fallback
- 일반 VIEW, partition parent, 관계 종류 불명 또는 planner 오류: 불법 TABLESAMPLE을 피하고 `RESULT_RANDOM`

인덱스 probe는 최대 60,000개로 제한한다. 희소 key에서 목표 행을 얻으려고 무제한 probe하지 않으며, 예산 안에서 최소 표본 크기도 확보하지 못하면 SYSTEM으로 폴백한다. seed는 동일 설정 재현성을 유지한다.

`SamplePlan.automatic` 표시는 자동 결과 표본에만 부여한다. 실행 후 더 정확한 모집단 추정이 들어왔을 때 실제 모집단이 목표 이하이면 approximate 메타데이터를 정확 실행으로 되돌릴 수 있게 수동 계획과 구분한다. 단일 PostgreSQL과 DuckDB 페더레이션 모두 같은 `PointSamplingPolicy`와 planner 결정을 거치며, 자동 표본 비대상은 L1 표본 cache도 조회하지 않는다.

### N10. 지도 히트맵의 표본 강도 보정

지도 히트맵은 표본 포인트 수가 줄면 같은 지역의 밀도와 강도도 함께 작아져 시각적 의미가 달라진다. `GeoHeatmapSamplingWeights`가 표본된 `map + heatmap`에만 inverse-probability weighting을 적용한다.

- SYSTEM 표본 포함확률: `p = rate / 100`
- INDEX_RANDOM 또는 RESULT_RANDOM: `p = sampleSize / populationEstimate`
- RESERVOIR_RANDOM: `p = sampleSize / populationCount` (`populationCount`는 전체 scan의 실측 N)
- 보정 가중치: `w = 1 / p`

변환 결과에 숫자형 `__chartsdk_point_value`가 있으면 기존 값에 `w`를 곱하고, 없으면 해당 내부 컬럼을 추가해 `w`를 넣는다. 기대값 관점에서 전체 포인트 강도를 보존하기 위한 Horvitz–Thompson 형태의 보정이다. 포함확률을 계산할 수 없거나 `p`가 유효한 `(0,1)` 범위가 아니면 임의 보정을 하지 않는다. 산점도와 지도 산점도에는 가중치를 적용하지 않아 점의 위치·개별 의미를 바꾸지 않는다.

1차 확률 보정에서 공유 `SAMPLING_CONTRACT_VERSION`을 `7 → 8`, `SampleFingerprint.CONTRACT_VERSION`을 `2 → 3`으로 올렸다. 이번 실제 행 수 reservoir 추가로 각각 `8 → 9`, `3 → 4`로 다시 올렸다. 이전 cache는 호환되지 않는 것으로 판단해 재계산하며 SDK normalization과 Admin/MSW도 contract 9를 사용한다.

### N11. 편집기·MSW 미러와 기존 차트별 초안 기능 보존

Admin에는 Java 정책과 같은 `supportsAutomaticPointSampling` helper를 추가해 다음을 일치시켰다.

- 자동 표본 비대상 차트는 “표본 ON” 상태라도 정확한 전체 결과를 실행한다는 안내를 표시한다.
- MSW builder/mock도 같은 차트 종류·집계·공간 Point 조건으로 `FULL_SCAN` 또는 표본 결과를 만든다.
- API `Chart` 응답에 `version`을 포함하고 `ChartInput.version`은 수정 요청에서 전달한다. 생성 전에는 보내지 않는다.

기존 `admin/lib/chartTypeDrafts.ts`의 초안 정책은 유지했다. version은 서버에 저장된 차트 정의의 동시성 토큰이고 차트 종류별 미저장 초안이 아니므로 draft 객체에 섞지 않고 `ChartEditor`의 별도 저장 상태로 관리한다. 그 결과 다음 기존 동작을 보존한다.

- 원본 테이블/JOIN 변경: 모든 차트 종류의 X/Y·집계·지도 컬럼 초안만 삭제
- 조건·표본·LIMIT: 차트별 복제 없이 공통 설정 유지
- X/Y·집계·정렬·지도 컬럼·시각화 옵션: 차트 종류별 독립 저장
- 원본/JOIN 변경 뒤에도 시각화 옵션 유지
- 쿼리 영향 설정 변경 시 저장하지 않은 결과 폐기 및 재실행
- 상단 초기화 또는 다른 차트 편집 진입 시 숨은 미저장 초안까지 제거

즉, 이번 version handshake와 자동 표본 helper는 초안 전환의 단일 진입점과 초기화 규칙을 우회하지 않는다.

### N12. Flyway V8 마이그레이션과 배포 순서

`docs/V8__refresh_lease.sql`을 추가했다. Gradle `processResources`가 `docs/V*__*.sql` 전체를 `db/migration`으로 복사하므로 문서 디렉터리가 Flyway migration의 단일 원본이다.

추가 객체는 다음 두 개다.

```sql
mc_chart_refresh_lease(
  chart_id bigint primary key references mc_chart(id) on delete cascade,
  definition_version integer not null,
  lease_token uuid not null,
  expires_at timestamptz not null
)

mc_sample_cache_build_lease(
  fingerprint char(64) primary key,
  lease_token uuid not null,
  expires_at timestamptz not null
)
```

두 테이블 모두 `expires_at` index가 있고, sample fingerprint에는 소문자 64자리 SHA-256 형식 check가 있다. lease 행은 기능상 만료 후 acquisition UPSERT가 덮어쓸 수 있으므로 별도 cleanup job이 없어도 복구된다.

권장 배포 순서는 다음과 같다.

1. 배포 전 DB backup과 Flyway 현재 version을 확인한다.
2. V8을 먼저 적용할 수 있는 애플리케이션 배포를 수행하고 두 lease 테이블과 index 생성을 확인한다.
3. `CHART_REQUIRE_UPDATE_VERSION=false`로 시작한다.
4. admission/쿼리/오류/누락 version 지표를 실제 트래픽에서 관찰한다.
5. 모든 수정 클라이언트가 version을 보내는 것을 확인한 뒤 별도 배포에서 `CHART_REQUIRE_UPDATE_VERSION=true`로 전환한다.

기본 동시성 값을 올릴 때는 고객 datasource Hikari pool의 max size, DB `max_connections`, 애플리케이션 heap과 CPU를 먼저 확인한다. per-datasource 값을 pool보다 크게 잡으면 semaphore 뒤에서 다시 connection 대기가 발생해 admission 지표의 의미가 흐려진다. federation은 여러 source connection과 DuckDB 메모리를 함께 쓰므로 전역 값보다 충분히 낮게 유지한다.

### N13. 운영 오류 코드와 진단 절차

| HTTP / 코드 | 의미 | 우선 확인 |
|---|---|---|
| `503 QUERY_BUSY` | admission deadline 안에 실행 슬롯 없음 | wait/duration/rows, rejected 증가, DB pool 대기 |
| `503 QUERY_INTERRUPTED` | admission 대기 thread interrupt | shutdown, request cancel, thread interrupt 로그 |
| `408 QUERY_TIMEOUT` | PostgreSQL 또는 DuckDB timeout | 실행 SQL, execution plan, index, DB 부하 |
| `422 SQL_ERROR` | 단일 소스 SQL/바인딩 오류 | 사용자 정의, schema 변경, DB 오류 첫 원인 |
| `422 FEDERATION_ERROR` | DuckDB/다중소스 변환 오류 | source 추출 결과와 DuckDB SQL |
| `413 SAMPLE_REALIZATION_TOO_LARGE` | 내부 L1 표본이 75,000행 초과 | rate/size, 모집단 통계, Bernoulli 계획 |
| `503 SAMPLE_CACHE_BUSY` | 같은 L1 fingerprint build가 대기시간 초과 | build lease 만료시각, cache 생성 여부 |
| `503 REFRESH_IN_PROGRESS` | 갱신 승자 결과를 대기시간 내 받지 못함 | refresh lease, cache `computed_at`, 쿼리 지속시간 |
| `503 REFRESH_INTERRUPTED` | 갱신 대기 thread interrupt | 배포/종료/취소 이벤트 |
| `428 CHART_VERSION_REQUIRED` | 강제 모드에서 수정 version 누락 | 구형 Admin/외부 API 호출자 |
| `409 VERSION_CONFLICT` | 다른 저장이 먼저 version 증가 | 차트 재조회 후 변경 재적용 |
| `409 CHART_DEFINITION_CHANGED` | 계산 중 정의가 변경되어 cache write 차단 | 최신 정의로 preview/refresh 재시도 |
| `404 CHART_NOT_FOUND` | 대상 차트 없음 또는 현재 owner scope 밖 | id, owner scope, 삭제 여부 |

#### `QUERY_BUSY`가 증가할 때

1. `chartsdk.customer_query.wait`가 먼저 늘었는지, `duration` 자체가 늘었는지 구분한다.
2. `kind`별로 preview 폭주인지, 실제 chart인지, federation인지 확인한다.
3. 고객 DB connection pool active/pending, DB CPU·I/O·lock, slow query를 확인한다.
4. 쿼리가 느려진 원인을 해결하기 전에 `QUERY_MAX_CONCURRENT*`만 올리지 않는다. 동시 실행 수를 올리면 DB가 더 느려져 전체 처리량이 오히려 떨어질 수 있다.

#### refresh가 끝나지 않을 때

```sql
SELECT chart_id, definition_version, lease_token, expires_at, now() AS checked_at
  FROM mc_chart_refresh_lease
 ORDER BY expires_at;

SELECT c.id, c.version,
       cc.definition_version, cc.computed_at, cc.row_count,
       cc.last_error_at, cc.last_error
  FROM mc_chart c
  LEFT JOIN mc_chart_cache cc ON cc.chart_id = c.id
 WHERE c.id = :chart_id;
```

- lease가 미래인데 실제 작업이 살아 있으면 삭제하지 않고 승자 쿼리를 조사한다.
- lease가 만료됐으면 다음 acquisition이 자동 인수한다. 운영 정리 목적이라면 `DELETE ... WHERE expires_at <= now()`만 수행한다.
- 애플리케이션 인스턴스와 PostgreSQL의 시계 차이를 확인한다. 만료 판정은 DB `now()`를 사용하므로 app wall clock은 acquisition에 직접 쓰이지 않는다.
- `definition_version`이 현재 차트 version과 다르면 새 version 요청이 lease를 즉시 교체할 수 있다.

#### sample build가 끝나지 않을 때

```sql
SELECT fingerprint, lease_token, expires_at, now() AS checked_at
  FROM mc_sample_cache_build_lease
 ORDER BY expires_at;

SELECT fingerprint, primary_datasource_id, row_count, payload_bytes,
       created_at, last_accessed_at
  FROM mc_sample_row_cache
 ORDER BY last_accessed_at DESC;
```

만료되지 않은 lease를 임의 삭제하면 같은 fingerprint loader가 중복 실행될 수 있다. 먼저 query timeout/instance 생존 여부와 cache 생성 여부를 확인한다. 만료 행 cleanup은 기능 복구에 필수는 아니다.

### N14. 검증 결과와 잔여 위험

이번 변경의 최신 테스트 정의 수와 실행법은 `테스트_전략.md`를 단일 기준으로 사용한다. 서버 단위·실DB 통합, workspace 단위, TypeScript typecheck, 차트 종류별 초안 E2E, production build와 diff 검사를 모두 배포 gate로 둔다.

전체 S2 editor E2E 파일 일괄 실행은 외부 4분 제한에서 실패 출력 없이 timeout됐기 때문에 변경 관련 3개 시나리오를 선택 실행해 통과를 확인했다. 이는 기능 실패 증거는 아니지만 전체 파일 완주 증거도 아니므로, CI에서는 충분한 timeout으로 전체 suite를 다시 실행해야 한다.

현재 의도적으로 남은 한계는 다음과 같다.

- 전체 차트 결과는 JDBC cursor로 나눠 읽지만 HTTP streaming이 아니어서 서버 heap에 materialize된다.
- RESERVOIR_RANDOM은 서버 heap과 브라우저 포인트 수를 K로 제한하지만 실제 N을 세기 위해 고객 DB 결과는 끝까지 읽는다. 느린 전체 scan 자체를 빠르게 만들지는 않는다.
- refresh/sample lease에는 heartbeat가 없다. 작업이 lease보다 길면 같은 version/fingerprint의 중복 계산이 가능하다.
- `ConcurrentHashMap`의 데이터소스별 semaphore 항목은 active admission과 새 항목이 엇갈릴 때 permit 상한을 우회하지 않도록 의도적으로 즉시 제거하지 않는다. 현재 목표인 약 100개 등록 소스에서는 메모리 영향이 미미하며, ID가 장기간 무한 생성되는 운영 모델로 바뀌면 generation-aware admission state를 별도로 설계한다.
- 인증·테넌트 owner 격리의 완성은 이번 범위 밖이다. 현재 성능·정합성 개선이 인증 부재를 보완하지는 않는다.

이 한계들은 결과를 임의 제한하거나 기존 편집 기능을 바꾸지 않고 운영 전 부하를 통제하기 위해 선택한 경계다. 실제 트래픽의 `wait`, `duration`, `rows`, rejection, version 누락 지표를 기준으로 다음 개선 우선순위를 정한다.

## N16. 100개 독립 데이터소스 운영 준비: bounded pool·안전한 무효화·sampling v9

### N16.1 변경 경계와 보존 계약

이번 단계는 약 100개 등록 데이터소스, 평상시 5~15명, 피크 30명, 순간 burst 100명을 목표로 한다. 인증, Redis 분산 semaphore, 전체 결과 HTTP streaming/columnar 전환, 일반 차트 자동 축소, 표본 OFF 강제 축소는 범위에 포함하지 않았다.

다음 기존 동작은 그대로 유지한다.

- 원본 탐색과 `mode=rows`는 최대 1,000행이다.
- 일반 차트 결과와 raw SQL 차트 결과에는 제품 행 상한을 새로 넣지 않았다.
- 자동 표본은 산점도·지도 산점도·지도 포인트 히트맵의 원본 point에만 적용한다.
- 표본 OFF와 manual 설정은 runtime reservoir를 거치지 않는다.
- 차트별 X/Y·집계·정렬·지도 컬럼·시각화 옵션 초안과 공통 조건·표본·LIMIT 분리 규칙은 변경하지 않았다.
- 데이터소스 수정 성공 응답 형식, query 응답의 `columns/rows/rowCount/truncated/elapsedMs`, 저장 차트 sampling 호환 판정 형식을 유지했다.

### N16.2 AdmissionController와 로컬 구현

쿼리 엔진이 `QueryExecutionCoordinator` 구현체에 직접 의존하던 구조를 `AdmissionController` 인터페이스로 바꿨다. 현재 구현은 기존과 같은 fair semaphore이며 기본값도 전역 24, 데이터소스별 4, federation 2, 대기 2초로 동일하다.

호출 순서와 permit 획득 순서는 바꾸지 않았다. 여러 데이터소스 permit은 ID 오름차순으로 얻고 역순으로 반환하므로 교착 회피 규칙도 유지된다. `QueryExecutor`와 `DuckDbFederation`은 인터페이스만 보므로 향후 고정 replica 예산 분할이나 분산 lease 구현을 추가해도 SQL 실행 코드가 바뀌지 않는다.

추가 metric은 다음과 같고 datasource ID label은 사용하지 않는다.

| metric | tag | 의미 |
|---|---|---|
| `chartsdk.customer_query.queued` | `kind` | admission 대기 중 요청 |
| `chartsdk.customer_query.running` | `kind` | permit을 얻어 실행 중인 요청 |
| `chartsdk.customer_query.wait` | `kind` | permit 대기 timer/histogram |
| `chartsdk.customer_query.duration` | `kind`, `outcome` | 고객 쿼리 실행 timer/histogram |
| `chartsdk.customer_query.rows` | `kind` | 반환·보관한 결과 행 수 |
| `chartsdk.customer_query.rejected` | `reason` | admission 거절 |
| `chartsdk.customer_query.failures` | `kind`, `reason` | timeout/query error/interruption |

여러 인스턴스에서는 각 JVM의 permit 합이 전체 동시성이 된다. 분산 admission을 도입하기 전에는 replica 수를 고정하고 `QUERY_MAX_CONCURRENT*` 값을 전체 DB 예산을 replica 수로 나눠 설정한다.

### N16.3 Bounded datasource pool registry

기존 registry는 데이터소스 ID마다 `HikariDataSource`를 영구 map에 남겼고 수정·삭제 시 active connection 여부와 무관하게 즉시 `close()`했다. 현재 책임은 세 객체로 분리했다.

- `DatasourcePoolFactory`: 최신 암호화 자격증명으로 read-only Hikari pool 생성
- `DatasourcePoolHandle`: borrower reference count, retiring/closed 상태, 마지막 사용시각 관리
- `DatasourcePoolRegistry`: active generation map, soft cap/LRU/TTL, cleaner와 metric 관리

기본값은 soft cap 128, idle TTL 1,800초, cleanup 60초다. 새 데이터소스 pool이 필요하고 cap에 도달했으면 가장 오래된 idle pool을 먼저 제거한다. 모든 pool이 사용 중이면 현재 요청을 실패시키거나 active connection을 끊지 않고 일시적으로 cap을 초과한다. borrower가 반환되거나 다음 cleanup이 실행되면 idle LRU를 제거해 cap으로 수렴한다.

`evict(id)`는 map에서 현재 generation을 분리하고 `retiring=true`로 바꾼다. borrower가 0이면 즉시 닫고, 사용 중이면 마지막 managed `Connection.close()`가 실제 JDBC connection을 반환한 다음 pool을 닫는다. 같은 ID의 다음 요청은 최신 자격증명으로 새 generation을 만든다. 따라서 수정·삭제와 장시간 조회가 겹쳐도 사용 중 connection을 중간에 강제 종료하지 않는다.

| 환경변수 | 기본값 | 의미 |
|---|---:|---|
| `DATASOURCE_POOL_REGISTRY_MAX` | `128` | active registry soft cap |
| `DATASOURCE_POOL_IDLE_TTL_SECONDS` | `1800` | borrower 없는 pool 보존 시간 |
| `DATASOURCE_POOL_CLEANUP_INTERVAL_SECONDS` | `60` | LRU/TTL cleanup 주기 |

운영 metric은 `chartsdk.datasource_pool.registry_size`, `retiring`, `borrowers`, `idle`, `pending`이다. Hikari pool별 datasource ID를 metric label로 만들지 않아 등록 고객 증가가 시계열 cardinality 폭증으로 이어지지 않는다.

### N16.4 커밋 이후 datasource runtime invalidation

컨트롤러에서 pool만 직접 제거하던 방식을 제거했다. `DatasourceService.update/delete`는 짧은 metadata transaction 안에서 변경 영향을 판정하고 `DatasourceChangedEvent`를 발행한다. 실제 invalidation listener는 `AFTER_COMMIT`에만 실행하므로 DB rollback인데 runtime만 먼저 바뀌는 상태를 만들지 않는다.

변경 영향은 다음처럼 구분한다.

| 영향 | 조건 | 처리 |
|---|---|---|
| `POOL_CONFIGURATION` | password 또는 max pool 변경 | pool generation retire만 수행 |
| `SOURCE_IDENTITY` | host, port, database, DB user 변경 | generation fence 증가, pool retire, catalog/L1/chart cache 제거 |
| `DELETED` | soft delete 성공 | identity 변경과 같은 derived state 제거 |

이름만 바뀌면 고객 DB 결과가 달라지지 않으므로 pool과 cache를 버리지 않는다. source identity 변경 시 `mc_sample_row_cache`는 primary ID뿐 아니라 `datasource_ids` JSONB 배열에 해당 ID가 포함된 federation 표본도 제거한다. `mc_chart_cache`는 `mc_chart_datasource` 관계를 이용해 단일·다중소스 차트를 함께 제거한다.

pool retire가 active query를 끝까지 살려두기 때문에 “무효화 뒤 옛 쿼리가 늦게 cache를 다시 쓰는” 경쟁을 별도로 막아야 한다. `DatasourceRuntimeVersions`가 조회 시작 시 datasource generation snapshot을 만들고 L1 cache hit 및 cache write 시 같은 generation인지 확인한다. generation bump와 local cache read/write fence는 fair read/write lock으로 직렬화한다.

- 재계산 cache: 실행 전 관계 ID snapshot → 실행 완료 후 같은 generation에서만 UPSERT
- 저장 준비 cache seed: 저장 검증 쿼리 전 snapshot → 차트 저장 뒤 같은 generation에서만 seed
- L1 sample cache: loader 전 snapshot → 같은 generation에서만 quota transaction write

변경이 중간에 감지되면 `DATASOURCE_CHANGED_DURING_QUERY`로 재계산을 요구하거나 quiet seed를 생략한다. listener의 각 component 실패는 다른 무효화 작업을 막지 않고 `chartsdk.datasource_runtime.invalidations{component,outcome}`와 warning log에 남는다.

현재 generation fence는 JVM-local이다. metadata cache 삭제는 공유 DB에 적용되지만 다른 인스턴스에서 이미 실행 중인 옛 작업의 늦은 write까지 완전히 fence하려면 datasource runtime version을 DB에 영속화하는 다음 단계가 필요하다. 현재 초기 운영의 고정 단일/소수 replica 경계에서는 local fence와 공유 cache 삭제를 사용한다.

### N16.5 RESERVOIR_RANDOM sampling v9

적용 조건은 다음을 모두 만족할 때뿐이다.

1. 저장/실행할 실제 차트 결과이며 원본 탐색이 아니다.
2. `sample.mode=auto`다.
3. `PointSamplingPolicy.supportsAutomaticSampling`이 참이다.
4. planner의 최종 결정이 `FULL_SCAN`이다.

`QueryExecutor`와 `DuckDbFederation`은 `ResultSet`을 cursor로 읽으면서 Algorithm R을 수행한다. 처음 K행을 보관하고 N번째 행마다 `[0,N)`의 seeded 난수를 뽑아 값이 K 미만일 때 해당 reservoir 슬롯을 교체한다. 보관 메모리는 O(K), 전체 scan 시간은 O(N), 각 행의 최종 포함확률은 `K/N`이다. 반환 전 원본 ordinal로 정렬해 선택된 점의 source 흐름을 보존한다. 같은 seed와 같은 ResultSet 순서에서는 같은 표본을 만든다.

- `N <= K`: `FULL_SCAN`, exact metadata 유지
- `N > K`: 최대 K행, `method=RESERVOIR_RANDOM`, `populationCount=N`, `sampleSize=K`, `sampledRowCount=K`
- 지도 히트맵: `populationEstimate`가 아닌 실측 `populationCount`로 `1/(K/N)` 가중치 적용

sampling contract는 v9이며 `RESERVOIR_RANDOM_SAMPLE` warning과 `populationCount` 필드를 추가했다. Java, 공유 `chart-options`, Admin mock, SDK normalization/배지 문구를 동시에 갱신했다. L1 fingerprint version은 4로 올려 이전 sampling 의미의 cache를 재사용하지 않는다.

이 안전장치는 결과 전송량과 브라우저 point 수를 K로 제한하지만 고객 DB scan을 생략하지 않는다. 10초 PostgreSQL/30초 DuckDB timeout 안에 N을 읽을 수 없는 쿼리는 timeout된다. 표본 OFF·manual·raw SQL 차트는 사용자 계약대로 이 자동 전환을 하지 않으므로 100만 행 exact 결과에서 JVM/HTTP/브라우저 부담이 남는다.

### N16.6 운영 경보와 배포 순서

Prometheus 규칙은 `ops/prometheus/chartsdk-alerts.yml`에 있다. query rejection/queue/p95/timeout, pool cap/pending/retiring, refresh·sample cache busy, invalidation failure, heap/GC, update version 누락을 포함한다. `/actuator/health` 상세는 인증 전 기본 `never`로 바꿨다. 상세가 필요하면 management endpoint를 내부망/별도 port/인증으로 격리한 뒤 `MANAGEMENT_HEALTH_SHOW_DETAILS`를 조정한다.

배포 순서는 다음과 같다.

1. 새 metric과 경보 규칙을 먼저 반영하고 `CHART_REQUIRE_UPDATE_VERSION=false`를 유지한다.
2. 15 VU normal, 30 VU peak, 100 VU burst를 순서대로 실행한다.
3. `version_missing` 증가가 안정적으로 0인지 확인한다.
4. Admin/외부 호출자의 version 전달을 확인한 별도 배포에서만 `CHART_REQUIRE_UPDATE_VERSION=true`로 바꾼다.
5. replica를 늘릴 때는 인스턴스 수만큼 permit이 곱해짐을 반영해 각 인스턴스 값을 다시 나눈다.

### N16.7 15/30/100 부하 검증

`load-tests/k6-query-capacity.js`와 `load-tests/README.md`를 추가했다. 입력한 datasource ID를 VU별 round-robin으로 배정하므로 100개 독립 ID를 전달하면 pool registry와 per-source admission을 함께 검증한다. 기본 workload의 90%는 sampling v9 자동 산점도, 10%는 원본 탐색이다.

자동 점 결과는 `sampling.version=9`, `approximate=true`, `rowCount <= K`를 검사하고 원본 탐색은 `rowCount <= 1000`을 검사한다. normal/peak/burst별 p95와 실패율을 분리하며 `QUERY_BUSY`는 100~400ms exponential backoff+jitter로 최대 3회 재시도한다. burst에서는 bounded 503을 서버 장애와 구분하되 최종 busy 비율 상한을 둔다.

현재 개발 장비에는 k6가 설치되어 있지 않고 100개 독립 100만행 fixture가 준비되어 있지 않으므로, 이 커밋에서 실환경 용량 수치를 임의로 기록하지 않는다. 서버 단위/통합 검증은 완료했으며 실제 15/30/100 합격 결과는 staging의 동일 자원 제한과 100개 datasource fixture로 실행해 보관해야 한다.

### N16.8 의도적으로 하지 않은 변경

- `(owner_id, updated_at DESC, id DESC)` 신규 index: 현재 목록 정렬은 ID tie-breaker를 이미 사용하고 기존 `(owner_id, updated_at DESC)` index가 있다. 약 100 고객 규모에서 중복 index write 비용을 만들지 않고 실제 `EXPLAIN` 병목이 확인될 때 추가한다.
- datasource별 admission semaphore map 즉시 삭제: active 작업과 새 semaphore가 겹치면 per-source 상한을 우회할 수 있어 제거하지 않았다.
- 전체 `QueryRows` streaming/columnar: 표본 OFF와 raw SQL exact 100만행의 다음 병목이지만 응답·cache 포맷 변경 폭이 커 이번 안전 범위에서 제외했다.
- ECharts large/progressive 강제: 현재 point item style/label/emphasis 계약과 충돌할 수 있어 자동 표본 OFF 의미를 보존하고 별도 renderer 전략으로 남겼다.
- Redis 분산 semaphore: 현재 고정 replica 예산 분할로 시작하고 실제 replica 확장 시 `AdmissionController`의 새 구현으로 추가한다.

상세 설계와 운영 체크리스트는 `대용량_운영_설계.md`, 최신 검증 수치는 `테스트_전략.md`를 따른다.
## 2026-08-05 — sampling v9 배포 호환·reservoir 할당·cache fail-closed 보완

### 증상과 위험

- sampling 계약을 v7에서 v9로 올린 뒤 버전을 완전 일치시켰더니, 기존 v7 snapshot을 사용하는 다중 데이터소스 차트가 `SNAPSHOT_NOT_READY`가 될 수 있었다.
- reservoir collector가 최종적으로 버리는 행도 먼저 `List<Object>`로 만들고 모든 JDBC 컬럼을 읽어, 보관 메모리는 K행이어도 100만 행 전체에 객체 할당이 발생했다.
- 데이터소스 수정 후 sample/chart cache DELETE 중 하나가 실패해도 성공한 것처럼 진행되어 이전 데이터소스 결과가 다시 읽힐 수 있었다.
- k6 지연값이 마지막 HTTP 요청만 포함해 `QUERY_BUSY` 재시도와 backoff를 사용자 대기시간에서 제외했고, 결과 크기만 확인해 실제 reservoir fallback 실행을 보장하지 못했다.

### 적용한 최소 변경

- `SamplingMetadata.matchesDefinition`은 현재 v9 정의에 대해 v7과 v9 cache만 허용한다. mode, requestedMethod, rate, sizeTarget, seed가 모두 같아야 하며 v8과 기타 버전은 거부한다. 호환 v7 payload는 반환 전에 v9로 승격하고 v9에 새로 생긴 `populationCount`는 null로 유지한다.
- Algorithm-R의 첫 K행은 그대로 materialize하고, 이후 행은 replacement index를 먼저 계산한다. 선택된 행만 `ResultSet.getObject`와 `List<Object>` 생성을 수행한다. 전체 모집단 계수와 표본 선택 확률은 기존과 같다.
- 데이터소스 source identity 변경·삭제 시 해당 ID를 local cache-blocked 상태로 먼저 등록하고 generation을 증가시킨다. sample cache와 chart cache 삭제가 모두 성공해야 차단을 해제한다. 실패 상태는 30초마다 idempotent DELETE로 재시도한다.
- 차단은 데이터소스별이다. 해당 sample cache는 저장소를 우회해 live loader 결과를 반환하고 쓰지 않는다. 해당 데이터소스를 참조하는 chart cache는 읽기·쓰기에서 제외한다. 다른 데이터소스의 캐시는 계속 사용한다.
- 이 fail-closed 상태는 현재 초기 운영 범위에 맞춘 JVM local 보호다. 여러 인스턴스 간 영속 상태 공유나 outbox는 이번 범위에 포함하지 않았다.
- k6의 `query_capacity_duration`은 최초 요청 시각부터 최종 성공 또는 최종 `QUERY_BUSY`까지 재시도·sleep을 모두 포함한다. `EXPECT_SAMPLE_METHOD=RESERVOIR_RANDOM`과 `EXPECT_POPULATION_MIN`으로 method, K, 실제 N을 함께 검증한다.

### 회귀 방지

- v7 스펙 일치/불일치 및 v9 응답 승격
- 버린 reservoir 행을 materialize하지 않는 호출 수 검증
- cache 삭제 1회 실패 후 데이터소스별 차단과 재시도 복구
- 차단 중 sample cache DB 무접근 및 live 결과 반환
- 차단 데이터소스를 참조하는 chart snapshot만 제외

# 2026-08-06 — Flyway V8 이력·runtime 최소권한·datasource 평문 전환

## N17.1 V8 untracked와 clean artifact 누락

- **증상:** 코드는 `mc_chart_refresh_lease`, `mc_sample_cache_build_lease`를 사용하지만 운영 history는 V7이었다.
- **원인:** `docs/V8__refresh_lease.sql`이 로컬에는 있어 `processResources`에 복사됐지만 Git untracked라 clean checkout artifact에는 존재하지 않을 수 있었다.
- **조치:** V8을 정식 migration으로 포함하고 `verifyFlywayResources`가 source/package 파일 목록·내용과 필수 callback을 검증한다. `check`, `bootJar`, CI integration의 배포 gate로 연결했다.
- **검증:** `FlywayV8MigrationIT`가 실제 V7 DB를 V8로 올리고 기존 sampling v7 JSON이 byte-equivalent JSONB text로 유지됨을 확인한다. 두 lease의 중복 거부, 만료 인수, 이전 token release 차단도 실DB에서 검증한다.

## N17.2 broad default privilege가 Flyway history를 노출한 문제

- **발견:** 제한 role E2E DB에서 `ALTER DEFAULT PRIVILEGES ... GRANT DML ON TABLES`가 Flyway history(`mc_flyway_schema_history`, 당시 기본명 `flyway_schema_history`)에도 적용됐다. runtime이 history를 읽고 변경할 수 있으므로 허용할 수 없다.
- **조치:** broad default grant를 제거했다. `afterMigrate__runtime_grants.sql` callback이 role 존재 여부를 확인한 뒤 `mc_*` table/sequence만 동적으로 grant하고 Flyway history 권한은 전부 revoke한다.
- **검증:** `chartsdk_app`은 `mc_chart`, serial sequence, V8 lease DML이 true이고 schema CREATE와 Flyway history SELECT/UPDATE는 false다.

## N17.3 Flyway 별도 URL fallback이 테스트 DB와 분리된 문제

- **증상:** `MultiSourceChartLifecycleIT`가 임시 `spring.datasource.url`을 사용했지만 Flyway는 기본 `DATABASE_URL` DB를 migrate해 임시 DB에 `mc_datasource`가 없었다.
- **원인:** custom `FLYWAY_DATABASE_URL` 기본값을 runtime 환경변수로 고정해 Spring Boot의 “Flyway 설정 미지정 시 runtime datasource 재사용” 동작을 깨뜨렸다.
- **조치:** custom alias를 제거하고 Spring 표준 `SPRING_FLYWAY_URL/USER/PASSWORD`만 선택적으로 사용한다. 미설정 시 기존 runtime datasource를 그대로 재사용한다.
- **검증:** `MultiSourceChartLifecycleIT` 전체가 재통과하고 제한 role real-backend E2E에서도 별도 Flyway 계정 적용을 확인했다.

## N17.4 legacy 평문 migration과 fail-closed

- **구조:** codec은 v1 암호 형식만, resolver는 runtime 허용 정책만, repository/service는 migration만 담당한다.
- **안전장치:** 기존 v1을 모두 먼저 복호화해 키를 검증한다. 미지원 버전 마커도 평문으로 오인하지 않고 변경 전에 거부한다. 이후 `FOR UPDATE`와 `id + old value + not v1` 조건부 update로 평문만 변경한다. secret이나 datasource ID는 기록하지 않는다.
- **운영:** migration flag는 1회만 켜고 legacy 0건과 연결 시험을 확인한 뒤 fallback을 false로 전환한다. strict 상태에서 legacy가 남으면 readiness 전에 startup을 실패시킨다.
- **검증:** 단위 테스트와 3 v1 + 2 plaintext 실DB IT, 제한 role API smoke, real-backend Playwright를 통과했다.

# 2026-08-07 — 갱신 모드 단순화: ttl 제거(V10)와 Flyway history mc_ 네임스페이스 이관

## N18.1 갱신 모드 3종 → 2종 단순화 (결정)

- **결정:** `mc_chart.refresh_mode`에서 `ttl`을 제거하고 `manual`(기본)/`live` 2종만 유지한다. 기존 `ttl` 차트는 전부 `manual`로 이관한다.
- **사유:** `ttl`은 만료 판정·만료 후 첫 요청 동기 재계산·경쟁 요청 stale 반환 등 서빙 경로 복잡도의 주 원인이었으나, 실사용은 "저장 스냅샷 재사용"(manual)과 "항상 최신"(live) 두 축으로 수렴한다. 이관 방향을 `manual`로 정한 것은 고객 데이터소스 부하가 갑자기 증가하지 않게 하기 위함이다(`live` 이관이었다면 기존 ttl 차트 전부가 매 요청 실행으로 바뀐다).
- **의도된 운영 변화:** 기존 ttl 차트는 1시간 주기 자동 갱신이 사라지고 [지금 갱신] 전까지 저장 시점 스냅샷을 유지한다. 자동 주기 갱신은 도입하지 않는다는 제품 결정 — 최신성이 필요한 차트만 운영자가 `live`로 전환한다. 스케줄러·백그라운드 큐 대체제는 의도적으로 만들지 않았다.

## N18.2 V10 마이그레이션과 서버 서빙 경로 축소

- **DB(V10):** `ttl` 행을 `manual`로 UPDATE 후 `cache_ttl_seconds` 컬럼 제거, `chk_mc_chart_refresh`를 `('live','manual')`로 교체, `chk_mc_chart_ttl` 제거, 기본값 `manual`.
- **서버:** `ChartCacheService`의 TTL 만료 판정 삭제 — 스냅샷 사용 가부는 정의 버전·표본 계약 호환성만 본다. `serve()`/`refreshSingleFlight()` 시그니처에서 `cacheTtlSeconds` 제거, `allowStale`은 `reuseCompatibleSnapshot`으로 리네이밍(TTL이 없는 세계에서 "stale"은 의미를 잃음). `ChartSaveRequest.refreshMode`에 `@Pattern(live|manual)` — `ttl` 저장 요청은 400. 생략(null) 시 repository가 `manual`을 채운다.
- **프론트:** `RefreshMode` 타입 축소, `optionRegistry`에서 `cacheTtlSeconds` 정의·TTL 선택지 제거, 갱신 모드 세그먼트는 [수동/항상 최신 조회](기본 수동). 목/시드/e2e 미러 동기화.
- **검증:** `FlywayV10MigrationIT` — 실DB에서 V9→V10 실행: ttl 행 manual 이관, live 행 보존, 컬럼 제거, `ttl` INSERT 제약 거부, 신규 행 기본값 manual. `ChartSaveRequestValidationTest`.

## N18.3 편집기 복원 시 컬럼 저장 옵션이 기본값으로 덮이던 버그

- **증상:** S2 진입 복원이 `options` JSONB만 주입해 컬럼 저장 옵션(`description`, `refreshMode`)이 레지스트리 기본값으로 표시됐고, 그 상태로 저장하면 저장돼 있던 갱신 모드·설명이 조용히 기본값으로 덮어써졌다.
- **조치:** 복원 시 `c.description`/`c.refreshMode`를 options에 재주입하고, 저장 후에는 서버 응답의 `refreshMode`(다중 소스 manual 정규화 포함)로 로컬 상태를 되맞춰 dirty 판정이 어긋나지 않게 했다.
- **검증:** e2e `s2-refresh` — live 시드 차트 진입 시 세그먼트가 live로 복원됨을 확인.

## N18.4 live 모드의 "데이터 기준 시각" 캡션 숨김

- live는 매 요청 계산이므로 "데이터 기준 {시각}" 캡션이 무의미하다. 서버 변환기·MSW 목·옵션 레지스트리 `showIf` 세 곳이 같은 규칙(`refreshMode !== 'live' && showComputedAt !== false`)을 적용한다.
- **검증:** `ChartOptionConverterTest`, e2e — live 차트에서 토글·캡션 부재 확인. TS/Java parity fixture 통과.

## N18.5 Flyway history를 mc_ 네임스페이스로 이관

- **결정:** history도 ChartSDK 소유 객체이므로 `spring.flyway.table=mc_flyway_schema_history`를 사용한다.
- **조치:** `FlywayHistoryTableConfiguration`(신규)의 `FlywayMigrationStrategy`가 마이그레이션 직전 transaction advisory lock 안에서 legacy `flyway_schema_history`의 이름만 변경한다(행·checksum·설치 시각 불변). 두 이름이 동시에 존재하면 이력을 자동 병합하지 않고 기동을 실패시킨다. runtime grants(`afterMigrate__runtime_grants.sql`, ops 스크립트)는 `mc_*` grant 대상에서 history를 제외하고 revoke를 유지한다.
- **검증:** `FlywayHistoryTableConfigurationIT` — 실DB에서 legacy 이름으로 V9까지 이력 생성 → rename 후 전체 행 보존·V10 계속 진행·양쪽 존재 시 거부.

# 2026-08-07 — ttl 제거 코드 리뷰 후속: previews live 재평가·Flyway rename 소유권·정리

위 N18 변경분을 리뷰하면서 발견한 문제의 수정 기록이다.

## N19.1 목록 배치 미리보기의 live 재계산 — 상한 도입 후 철회(재평가)

- **경위:** 리뷰에서 "`GET /charts/previews`가 live 카드를 최대 60개까지 순차 동기 재계산한다"고 지적하고, 요청당 live 재계산 상한(`chartsdk.previews.max-live-recomputes`, 기본 5)을 도입했다.
- **재평가:** 목록 UI(`ChartListView`)는 8개/페이지로 페이지네이션하고 배치 미리보기도 현재 페이지 id만 보낸다. 실제 워스트 케이스는 페이지뷰당 live 8회이며, live는 PRD상 "소규모 테이블, 최신성 필수" 용도라 설계 의도 안이다. 60은 API 방어 상한일 뿐 실사용 경로가 아니었다 — 최초 지적이 과장이었다. 오히려 기본값 5 < 페이지 크기 8이라 정상 화면에서도 live 6개 이상이면 일부 썸네일이 이유 없이 스냅샷으로 그려지는 부작용이 있었다.
- **결론:** 상한 기능(설정·분기·전용 테스트)을 전부 제거하고 "live 카드는 재계산, manual은 배치 스냅샷"이라는 원래 설계(72a3bdf)로 복귀한다. 페이지네이션이 자연 상한이다. live 스냅샷을 배치 조회에서 제외하는 것도 원래 설계 그대로다(재계산 실패 시 에러 카드, 스냅샷 폴백 없음 — 목록이 장애를 숨기지 않는다). 남긴 것은 60 리터럴의 상수화(`MAX_PREVIEW_CARDS`)와 이 결정을 설명하는 주석뿐이다.
- **검증:** `ChartServiceTest` — live 카드 재계산·manual 전용 배치 expectation·live 스냅샷 미조회.
- **교훈:** API 계약 상한(60)을 실제 소비자(UI 8/페이지)와 대조하지 않고 부하 시나리오를 산정했다. 부하 지적은 실 호출 경로 확인이 먼저다.

## N19.2 legacy Flyway history rename의 권한 오류를 조치 가능한 메시지로

- **배경(가정 시나리오, 관찰 사례 아님):** rename은 소유 role만 가능하다. role 분리 배포에서 `SPRING_FLYWAY_USER`를 빠뜨리면 runtime role(`chartsdk_app`)로 실행돼 raw `permission denied`로 기동이 실패한다. 다만 그런 배포는 rename이 없어도 다음 마이그레이션(예: V10 `ALTER TABLE mc_chart`)에서 같은 원인으로 실패하므로, rename 도입이 새 실패 모드를 만든 것은 아니다 — 이 변경의 가치는 실패 방지가 아니라 **원인 진단 메시지의 명확화**다.
- **조치:** rename 전에 `pg_has_role(current_user, relowner, 'MEMBER')`로 소유권을 확인하고, 아니면 현재 사용자명과 조치(`SPRING_FLYWAY_USER/SPRING_FLYWAY_PASSWORD` 또는 수동 rename)를 담은 `IllegalStateException`으로 중단한다. 슈퍼유저는 비소유여도 통과한다(실DB로 `pg_has_role` 동작 확인 — 슈퍼유저는 실제로 rename 가능). `application.yml` flyway 블록과 운영 권한 문서에 전제를 명시했다.
- **검증:** `FlywayHistoryTableConfigurationIT` — 비소유 role 접속 시 예외 메시지(사용자명·조치 포함)와 테이블이 원래 이름 그대로 남아 있음을 실DB에서 확인.
