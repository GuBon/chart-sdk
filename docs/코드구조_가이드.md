# 코드 구조 가이드

최종 갱신: 2026-07-21.

이 문서는 기능 명세가 아니라 코드의 책임과 의존 방향을 설명한다. 새 파일을 만들 때는 “파일이 길다”보다 “서로 다른 이유로 바뀌는 코드인가”를 먼저 판단한다.

## 1. 전체 의존 방향

```text
Admin 화면(app)
  └─ 도메인 컴포넌트(components/charts, components/data)
       ├─ 공통 UI(components/ui)
       ├─ 순수 규칙(lib)
       └─ API 클라이언트(lib/api)
                ↓ HTTP
Server Controller(web)
  └─ Service(chart, datasource, cache)
       ├─ Repository/JdbcTemplate
       └─ query · converter · federation 규칙 엔진
                ↓
        메타 DB / 고객 데이터소스
```

- 위 계층은 아래 계층을 호출할 수 있지만, 아래 계층이 화면 컴포넌트를 알면 안 된다.
- Admin은 DB에 직접 접근하지 않고 서버 API만 호출한다.
- ECharts option의 운영 권위는 Java 변환기다. Admin mock은 테스트용 미러이며 공용 계약 fixture로 드리프트를 막는다.
- `chart-options`는 옵션 정의·기본값·표시 조건의 SSOT다.

## 2. Admin 책임

### 라우트와 화면

`admin/app`의 page 파일은 URL 파라미터를 읽고 화면 컴포넌트에 전달하는 얇은 경계로 둔다. 데이터 카탈로그 URL은 다음 계층으로 고정한다.

| URL | 화면 의미 |
|---|---|
| `/data/{datasourceId}` | 데이터소스의 스키마와 관련 차트 |
| `/data/{datasourceId}/{schema}` | 스키마의 TABLE·View·Materialized View |
| `/data/{datasourceId}/{schema}/{relation}` | 관계 컬럼과 이 관계 기반 차트 |
| `/data/{datasourceId}/{schema}/{relation}/{chartId}` | 해당 차트 편집 |

경로 조립은 `admin/lib/chartRoutes.ts`만 사용한다. `tables`, `charts` 같은 중간 구간은 상위 문맥과 중복되므로 넣지 않는다. SQL 모드처럼 메인 관계가 없는 차트만 `/charts/{id}`를 사용하고 신규 차트는 `/charts/new`를 사용한다.

### 공통화한 경계

- `lib/chartTypes.ts`: 차트 대분류의 사용자 표시명과 아이콘. 목록 카드·필터·옵션 패널이 공유한다.
- `lib/relations.ts`: TABLE·View·Materialized View 표시명과 선택 가능 여부. 데이터 탐색·스키마 선택기가 공유한다.
- `components/ui/Pagination.tsx`, `EmptyState.tsx`: 도메인 의미가 없는 반복 UI.
- `components/charts/useChartPage.ts`: 차트 목록, 배치 미리보기, 페이지 보정, 재조회와 오래된 응답 무시를 한 수명주기로 묶는다.
- `OptionPanel.tsx`: 검색·존·섹션·접힘을 조정한다. `OptionControl.tsx`: 레지스트리의 각 입력 종류를 렌더링한다.

### 의도적으로 유지한 큰 컴포넌트

- `ChartEditor`: 편집기 전체 상태와 패널 간 전이를 조정하는 오케스트레이터다. 상태를 여러 훅으로 잘게 나누면 저장·실행·복원 순서를 추적하기 어려워지므로 독립된 변경 축이 생길 때만 분리한다.
- `NocodeBuilder`: 하나의 빌더 폼과 검증 흐름이다. 조인, 필터, 표본 중 하나가 다른 화면에서도 재사용되기 전에는 억지로 분리하지 않는다.

## 3. Server 책임

### HTTP 경계와 서비스

- `web/*Controller`: URL·요청 바인딩·응답 형태만 담당한다.
- `chart/*Service`, `datasource/*Service`: 유효성 검사와 작업 순서 같은 애플리케이션 규칙을 담당한다.
- Repository/JdbcTemplate 사용 코드는 영속화와 행 매핑을 담당한다.
- `query`, `converter`, `federation`: SQL 생성, ECharts 변환, 다중 소스 실행처럼 계산 규칙이 밀집된 엔진이다.

`DatasourceController`에 있던 JDBC·암호화·연결 시험은 `DatasourceService`로 이동했다. 컨트롤러는 변경·삭제 성공 뒤 기존 커넥션 풀을 폐기하는 HTTP 경계 동작만 조정한다. API 읽기 모델은 비밀번호가 없는 `DatasourceView`로 고정한다.

차트 목록의 검색 조건은 `ChartListQuery` 값 객체로 전달한다. 여러 계층에 8개의 위치 인자를 반복하지 않고, 페이지 크기·스키마 기본값 같은 해석도 이 객체가 한 번만 수행한다.

### 의도적으로 유지한 규칙 엔진

- `BuilderSqlBuilder`: builderConfig를 검증하고 SQL과 파라미터를 함께 만드는 한 규칙 엔진이다.
- `ChartOptionConverter`: QueryRows를 ECharts option으로 바꾸는 한 규칙 엔진이다.

두 파일은 길지만 규칙 순서와 공용 문맥을 함께 읽어야 한다. 차트 종류별 구현이 독립 배포되거나 독립 테스트 계약을 갖게 되기 전에는 파일 길이만으로 전략 클래스를 늘리지 않는다.

## 4. 분리 여부 판단 기준

다음 중 하나가 참이면 분리를 고려한다.

1. 서로 다른 기능 변경이 같은 파일에서 반복적으로 충돌한다.
2. 같은 규칙을 둘 이상의 화면이나 서비스가 복사한다.
3. 외부 자원 접근과 순수 계산이 섞여 단위 테스트가 어려워진다.
4. 입력·출력 계약을 독립적으로 이름 붙이고 테스트할 수 있다.

반대로 한 번만 쓰는 짧은 표현 컴포넌트, 같은 상태 전이에 강하게 결합된 로직, 단순히 줄 수가 많은 규칙표는 그대로 둔다. 공통화는 중복 제거보다 의미의 단일 권위를 만드는 데 목적이 있다.

## 5. 검증 기준

- 순수 규칙은 단위 테스트로 값과 경계를 고정한다.
- 컨트롤러/서비스 분리는 위임 순서와 DB 행 매핑을 단위 테스트한다.
- 실제 PostgreSQL 계약은 서버 통합 테스트가 담당한다.
- URL과 사용자 동선은 `chartRoutes.test.ts`와 Playwright E2E가 함께 검증한다.
- 전체 명령과 최신 테스트 수치는 `docs/테스트_전략.md`만 갱신한다.
