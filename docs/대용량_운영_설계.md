# 대용량·다중 데이터소스 운영 설계

**기준일:** 2026-08-05<br>
**목표:** 약 100개 독립 고객 데이터소스, 일반 동시사용 5~15명, 피크 30명, 순간 burst 100명<br>
**상세 장애 이력:** [개발 문제해결 이력 N16](개발_문제해결_이력.md#n16-100개-독립-데이터소스-운영-준비-bounded-pool안전한-무효화sampling-v9)

## 운영 구조 선택 근거

| 개선 목표 | 현재 선택 | 검토 대안 | 선택 이유와 현재 이점 | 한계·검증 |
|---|---|---|---|---|
| burst 요청이 thread·pool·고객 DB를 함께 압박 | 전체·source별·federation admission | timeout만 사용, pool max만 사용, 전역 semaphore 하나 | 실행 시작 전 부하를 제한하고 noisy source와 고비용 federation을 구분 | JVM local quota라 replica별 예산 분할 필요 |
| 약 100개 source pool 누적과 수정 중 연결 중단 | soft cap·TTL·LRU·retiring generation | 영구 map, 즉시 close, 요청별 연결 | idle 객체를 회수하면서 in-flight query는 끝까지 보호 | churn이 수천 ID면 admission state 정리 추가 필요 |
| 다중 instance 중복 refresh | JVM future+만료형 DB lease | local lock, Redis lock, 장시간 advisory transaction, queue | 추가 인프라 없이 transaction을 짧게 유지하고 process 죽음은 expiry로 복구 | heartbeat 없음. lease 초과 관측 시 renewal/queue 검토 |
| metric cardinality 폭증 방지 | kind·outcome 중심 low-cardinality tag | datasourceId label | 고객 수가 늘어도 시계열 수가 bounded | source별 상세 원인은 로그·pool 지표 결합 필요 |

사건별 선택 근거와 검증 결과는 [개발 문제해결 이력](개발_문제해결_이력.md)을 참조한다.

## 1. 보장 범위

| 경로 | 결과 행 계약 | 보호 방식 |
|---|---|---|
| 원본 데이터 탐색 / `mode=rows` | 최대 1,000행 | SQL/JDBC materialization 상한 |
| 자동 원본 산점도·지도 산점도·지도 히트맵 | 기본 K=10,000, 최대 설정 K=50,000 | planner 표본 + FULL_SCAN runtime reservoir |
| 일반 집계 차트 | 기존 전체 결과 | admission과 JDBC cursor |
| 표본 OFF/manual/raw SQL 차트 | 기존 사용자 설정 그대로 | 자동 축소 없음 |

“100만 행을 실행해도 항상 빠르다”는 보장이 아니다. 자동 point는 서버 보관·JSON·브라우저 렌더 행을 K로 묶지만 실제 모집단 N을 세기 위한 scan은 timeout 안에 끝나야 한다. exact 100만행을 반환하는 경로는 다음 단계의 streaming/columnar 전환 대상이다.

## 2. 구성과 책임

```text
QueryExecutor / DuckDbFederation
        │
        ├─ AdmissionController
        │    └─ QueryExecutionCoordinator (현재 JVM-local fair semaphore)
        │
        ├─ DatasourcePoolRegistry
        │    ├─ DatasourcePoolFactory (Hikari 생성)
        │    └─ DatasourcePoolHandle (borrower 보호 + retire)
        │
        └─ ReservoirPointCollector (auto point FULL_SCAN만)

DatasourceService transaction
        └─ DatasourceChangedEvent
             └─ AFTER_COMMIT DatasourceRuntimeInvalidator
                  ├─ pool generation retire
                  ├─ QueryExecutor catalog 제거
                  ├─ L1 sample cache 제거
                  ├─ chart cache 제거
                  └─ DatasourceRuntimeVersions generation/cache-block fence
                       └─ 실패한 cache DELETE 30초 재시도
```

호출부는 admission 구현, pool 생성 세부사항, sampling 알고리즘을 알지 않는다. 변경 영향 판정은 service, 자원 정리는 event listener, 알고리즘은 collector에 각각 격리했다.

## 3. 핵심 불변식

1. active connection이 있으면 pool을 강제 종료하지 않는다.
2. datasource metadata transaction이 rollback되면 runtime을 무효화하지 않는다.
3. source identity 변경 전 시작한 결과는 변경 후 cache를 다시 채우거나 L1 cache hit로 반환하지 않는다.
4. automatic point가 아닌 결과를 runtime에서 몰래 축소하지 않는다.
5. datasource ID를 metric label로 사용하지 않는다.
6. 메타데이터 DB transaction을 고객 DB 쿼리 동안 열어두지 않는다.
7. 기존 차트별 초안과 공통 설정의 소유권을 성능 코드가 건드리지 않는다.
8. source identity 변경 후 cache DELETE가 실패하면 해당 datasource cache만 fail-closed하고, 성공한 재시도 뒤에만 다시 연다.

## 4. 용량 계산

초기 기본값은 JVM 한 대 기준이다.

| 자원 | 기본 예산 |
|---|---:|
| 전체 고객 DB 작업 | 24 |
| 데이터소스별 작업 | 4 |
| DuckDB federation | 2 |
| pool registry soft cap | 128 |
| datasource pool 기본 max | 각 등록값, 기본 5 |
| 자동 point K | 10,000 |

replica가 R개면 로컬 admission의 이론상 전체 허용량은 각 값에 R을 곱한 수다. 중앙 admission 전에는 `인스턴스별 permit = 전체 허용 예산 / 고정 replica 수`로 잡고 부하 결과에 따라 내림 조정한다. per-source permit이 Hikari maximum보다 크면 admission 뒤에서 connection 대기가 다시 생기므로 `min(고객 DB 허용 동시성, pool max)`를 넘기지 않는다.

soft cap 128은 100개 등록 소스에 28개 여유를 둔다. cap은 연결 수 상한이 아니라 pool 객체 generation 상한이다. Hikari `minimumIdle=0`이므로 idle physical connection은 줄어들며 registry TTL이 pool 관리 객체까지 회수한다.

## 5. Sampling v9 판정표

계획·runtime collector 판정, Reservoir 메타데이터와 v7 캐시 승격 규칙은 [표본추출 계약](표본추출_계약.md)의 권위다. 이 운영 문서는 collector가 K행 메모리 경계를 지키는지, reservoir 활성 횟수와 `populationCount / retainedRows`가 관측되는지, 표본 OFF·manual 결과가 바뀌지 않는지만 부하 gate에서 검증한다.

## 6. 데이터소스 변경 영향표

| 변경 | pool | catalog | L1 sample | chart cache | generation fence |
|---|---:|---:|---:|---:|---:|
| name | 유지 | 유지 | 유지 | 유지 | 유지 |
| password | retire | 유지 | 유지 | 유지 | 유지 |
| max pool size | retire | 유지 | 유지 | 유지 | 유지 |
| host/port/database/user | retire | 제거 | 제거 | 제거 | 증가 |
| delete | retire | 제거 | 제거 | 제거 | 증가 |

무효화 component 하나가 실패해도 나머지를 시도하고 error metric을 남긴다. sample/chart cache 삭제 중 하나라도 실패하면 해당 datasource ID만 cache-blocked 상태로 유지한다. 차단된 sample cache는 DB cache를 우회해 live 결과를 반환하고 저장하지 않으며, chart snapshot은 읽거나 쓰지 않는다. 30초 기본 주기로 두 DELETE를 다시 실행하고 모두 성공한 뒤 차단을 해제한다. 다른 datasource cache는 계속 사용한다. L1 cache hit와 cache write는 datasource generation read fence 안에서 검사한다. `DatasourceChangedDuringQuery`가 보이면 최신 설정으로 한 번 재시도한다.

## 7. 배포 체크리스트

- [ ] `DATASOURCE_ENC_KEY`, embed secret 교체
- [ ] actuator를 외부에서 차단하고 health detail 기본 `never` 확인
- [ ] `ops/prometheus/chartsdk-alerts.yml` rule load 성공 확인
- [ ] `CHART_REQUIRE_UPDATE_VERSION=false`로 배포
- [ ] 15/30/100 테스트용 100만행 fixture와 최대 100개 ID 준비
- [ ] normal/peak/burst threshold 통과
- [ ] query queue/rejection/timeout, pool pending, heap/GC 확인
- [ ] `EXPECT_SAMPLE_METHOD=RESERVOIR_RANDOM`으로 reservoir 결과가 v9이고 N>K일 때 K행인지 확인
- [ ] 원본 탐색이 1,000행인지 확인
- [ ] 표본 OFF/manual/일반 차트가 기존 결과와 같은지 smoke 확인
- [ ] `chartsdk.chart.update.version_missing`이 충분한 관찰기간 0인지 확인
- [ ] 별도 배포에서만 `CHART_REQUIRE_UPDATE_VERSION=true` 전환

## 8. 부하 테스트 실행과 판정

실행법은 [load-tests README](../load-tests/README.md)를 따른다. 100개 소스 실험은 `REQUIRE_100_DATASOURCES=true`로 ID 수 자체를 검증한다. 테스트 중 서버와 고객 DB의 CPU, I/O, connection, heap, GC를 같은 시각축으로 수집한다.

결과 기록에는 다음을 포함한다.

- app version/commit, replica 수, JVM heap, CPU 제한
- 고객 DB별 pool max와 PostgreSQL `max_connections`
- fixture 실제 행 수와 `ANALYZE` 시각
- 15/30/100 단계별 성공률, 최종 `QUERY_BUSY`, p50/p95/p99
- timeout, pool pending, 최대 heap, GC pause ratio
- reservoir 활성 횟수와 `populationCount/retainedRows`

100 VU에서 일부 `QUERY_BUSY`는 overload 보호가 작동한 정상 결과일 수 있다. 다만 15 VU 정상 구간의 지속적인 거절이나 pool pending은 기본 예산/쿼리 성능 문제이므로 운영 전 해결한다.

## 9. 다음 확장 조건

다음 조건이 실제 metric으로 확인될 때만 후속 구조를 추가한다.

- replica 확장으로 전체 permit을 예측하기 어려움: 분산 `AdmissionController`
- 등록 datasource ID가 장기간 수천~수만으로 증가: generation-aware admission/catalog state eviction
- 표본 OFF/raw SQL exact 대형 결과가 필요: ResultSet streaming, spill, binary/columnar, HTTP streaming
- 자동 point K에서도 UI가 느림: scatter/map 전용 renderer strategy와 typed array
- datasource 변경이 여러 인스턴스의 in-flight cache write와 자주 경쟁: DB runtime version fence
- 차트 목록 EXPLAIN에서 기존 index가 실제 병목: `(owner_id, updated_at DESC, id DESC)` 또는 keyset pagination

가능성만으로 데이터 의미나 API를 바꾸지 않고, metric과 부하 재현으로 확인된 병목에만 다음 변경을 적용한다.
