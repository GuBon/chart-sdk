02

배포 차단 이슈 · Critical / High

배포 전 반드시 해소해야 하는 항목. 표시된 확인됨 배지는 감사 결과를 원문 코드로 직접 재검증했다는 뜻입니다.

Critical관리 API 전면 무인증 — 임의 SQL 실행 · 토큰 원문 유출확인됨

인증 인터셉터가 /api/v1/charts/data 한 경로에만 걸려 있고 Spring Security 의존성이 없습니다(WebMvcConfig.java:18, build.gradle.kts). 그 결과 GET /tokens가 모든 JWT 원문을 반환하고(TokenService.java:30,106), POST /query/run(임의 SELECT를 고객 DB에 직접 실행), 사용자 생성, 데이터소스 자격증명 등록이 전부 무인증입니다. 인터넷 노출 시 /tokens로 유효 토큰 확보 → 전 차트 열람 또는 /query/run으로 고객 DB 덤프가 가능합니다.

조치 관리 API 전역 인증(세션 또는 관리자 토큰) 도입, /tokens 응답에서 원문 제거(발급 시 1회만 노출·해시 저장), 관리·임베드 라우트 분리.

Critical임베드 토큰에 chartId 스코프 부재 → 크로스 테넌트 차트 노출확인됨

JWT 페이로드는 userId, jti, iat, exp, v뿐 chartId 스코프가 없습니다(JwtTokenProvider.java:32-37). 임베드 조회는 WHERE id=? AND (owner_id=? OR owner_id IS NULL)인데(EmbedChartService.java:64), 유일한 CurrentUserProvider 구현이 항상 empty를 반환해(DevelopmentCurrentUserProvider.java) 모든 차트가 owner_id NULL로 저장됩니다. 결과적으로 유효 토큰 하나로 chartId를 1,2,3…으로 열거해 타 테넌트의 매출·좌표·PII 차트 결과를 전량 수집할 수 있습니다.

조치 토큰에 허용 chartId(또는 도메인) 스코프를 넣어 발급·강제, 운영용 CurrentUserProvider 실구현으로 교체, owner_id IS NULL 광역 허용 제거.

Highdev 시크릿이 코드 기본값 + 운영 프로파일 부재 + fail-fast 없음확인됨

단일 application.yml만 존재하며 JWT 서명키(dev-chartsol-embed-secret-change-me), AES 키, 메타 DB 비밀번호(0218)가 모두 fallback 기본값입니다(:8,83,86). 환경변수 주입을 잊으면 운영이 dev 시크릿으로 조용히 기동합니다. 평문 비밀번호에는 startup guard가 있지만 시크릿에는 없습니다. (참고: 서명키 위조는 validateBearer의 DB 재확인이 막지만, 서명 무결성·enc-key 유출 복호화 관점에서 High.)

조치 prod 프로파일에서 fallback 제거·필수화 + 기동 시 dev 문자열 감지 fail-fast(기존 DatasourcePasswordStartupGuard 패턴 재사용).

High내부 예외(SQL 원문 · DB 오류) 4종이 클라이언트로 노출

SQL_ERROR(422)·FEDERATION_ERROR·SAMPLE_AGGREGATION_ERROR·DATASOURCE_QUERY_FAILED가 e.getMessage()를 envelope message에 그대로 실어 PostgreSQL 원문 오류(컬럼·제약·테이블명), DuckDB/libpq 접속 오류(호스트·DB명)를 노출합니다. 의도적 오류 SQL로 스키마를 열거하는 에러 기반 정보수집이 가능하며, "내부 예외 비노출" 설계 원칙과 상충합니다.

조치 이 4종도 일반화된 사용자 메시지 + requestId만 반환하고 상세는 서버 로그로만 남김.

HighSDK 로딩 상태·요청 타임아웃 부재 → 네트워크 hang 시 영구 빈 박스확인됨

fetch에 AbortSignal/타임아웃이 없고 렌더 전 placeholder도 없습니다(sdk/api.ts:22-25). 응답이 지연·행되면 방문자는 오류도 로딩도 아닌 "아무것도 아닌" 빈 div를 영구히 봅니다. 사용자가 강조한 "차트 실행/부재 시 내부 형식 안내" 관점에서 가장 취약한 지점.

조치 AbortSignal.timeout(15s) 부여 + 요청 시작 시 로딩 placeholder 표시, 타임아웃 시 renderError로 합류.

HighSDK 데이터 0행 empty state 부재 → 빈 축에 "정확한 결과" 캡션확인됨

응답의 rowCount를 받고도 사용하지 않아(sdk/api.ts:8), 0행이면 서버 option을 그대로 setOption해 빈 좌표축 + "전체 데이터 · 정확한 결과" 캡션이 표시됩니다(chart.ts:98-120). 오류는 아니지만 안내도 아니며, "정확한 결과" 문구는 오해를 부릅니다.

조치 rowCount 0 감지 시 "표시할 데이터가 없습니다" 디자인 placeholder(renderError와 동급의 인라인 스타일 잠금).

HighAdmin — IN 조건 값을 타이핑으로 입력할 수 없음 (콤마 즉시 삭제)확인됨

연산자 in 선택 후 값란에 "서울," 입력 → splitList가 빈 항목을 filter하고 join(', ')으로 되돌려 controlled input이 "서울"로 스냅백, 이어 "부산" 입력 시 "서울부산" 단일 값이 됩니다(NocodeBuilder.tsx:934-937). 다중 값은 붙여넣기로만 입력 가능한 실사용 기능 버그.

조치 입력 중 로컬 문자열 state 유지하고 blur/실행 시점에만 파싱, 또는 태그(칩) 입력 UI로 교체.

HighAdmin — 차트 목록 API 실패가 "차트 없음" 빈 상태로 위장확인됨

목록 로드 catch가 error state 없이 setCharts([])만 수행해(useChartPage.ts:31-36), 백엔드 중단 시 "아직 만든 차트가 없습니다 / 첫 차트 만들기" EmptyState가 표시됩니다. 운영자가 전체 차트 삭제로 오인할 수 있는 위장.

조치 catch에서 error state를 분리해 "목록을 불러오지 못했습니다 + 재시도" UI 표시.

HighAdmin — 새로고침·탭 닫기에 이탈 경고 없음 → 미저장 변경 유실

이탈확인 모달이 인앱 [목록]·[새 차트] 버튼에만 작동하고 beforeunload/popstate 핸들러가 없습니다(ChartEditor.tsx:1102-1105). 편집 중 F5·탭 닫기·브라우저 뒤로가기로 변경이 경고 없이 사라집니다.

조치 hasUnsavedChanges일 때 beforeunload 핸들러 등록/해제.

HighChartOptionConverter 2,173줄 God class + 차트타입 if-체인 분기

시리즈 조립·축·여백 수식·타이포그래피·레거시 마이그레이션·boxplot 통계·이동평균이 한 클래스에 공존하고, 타입 분기가 if-체인입니다(ChartOptionConverter.java:216-231). 상태 없는 순수 변환이라 동작 위험은 없으나 새 차트 타입 추가 시 파일 내 6~8곳을 동시에 고쳐야 하고 회귀 반경이 파일 전체입니다.

조치 타입별 SeriesAssembler 전략 맵 + OptionMigrations/레이아웃 협력 클래스 추출. 계약 테스트가 두꺼워 안전한 리팩터링 여건은 이미 갖춰짐.

High패키지 순환 의존 — web이 사실상 최하층

ApiException이 web 패키지에 있어 query·cache·datasource·chart·converter 전부가 하위→web 역방향 의존을 갖고, query↔cache·cache↔federation·datasource↔query 패키지 순환이 존재합니다. 빈 그래프는 비순환이라 부팅은 되지만 모듈 분리(Gradle 멀티모듈·ArchUnit 규칙)가 불가능합니다.

조치 ApiException을 common/error로, SamplingMetadata를 sampling 패키지로 이동. ArchUnit 의존 규칙 테스트 추가.

주요 Medium 발견 사항

배포 직후~단기에 처리할 항목. Low 12건은 개별 영역 보고에 상세.

Medium자원 경합 3종 — 서블릿 스레드/풀 생성 직렬화

① 풀 생성이 단일 전역 락 아래 실행돼 죽은 고객 DB 하나가 다른 모든 소스의 최초 풀 생성을 최대 10초씩 직렬 블록(DatasourcePoolRegistry.java:93-102). ② lease 대기가 100ms sleep-폴링으로 서블릿 스레드를 최대 35초 점유(대기 인원 무제한, ChartRefreshCoordinator.java:95-109). ③ /charts/previews가 live 카드 최대 60건을 각 30초 타임아웃으로 순차 재계산(ChartService.java:33,94).

조치 datasource별 스트라이프 락 + lazy 초기화, 대기 인원 상한(초과 시 REFRESH_IN_PROGRESS), live 재계산 개수 별도 상한.

Medium확장성 — "새 소스 = 포트 구현 하나"가 성립하지 않음 (kind 디스패처 부재)

SPI 이음매(CatalogPort·DuckDbBinding·QueryEngine)는 정확하나 종류별 라우팅 지점이 없고 단일 빈만 주입되며, jdbcUrl()·SamplingPlanner·BuilderSqlBuilder에 PG 방언(TABLESAMPLE·ILIKE·DATE_TRUNC·setseed)이 하드코딩됐습니다. MySQL 추가 시 최소 10파일 + 스키마 마이그레이션이 필요합니다.

조치 mc_datasource에 kind 컬럼 추가 → kind→(CatalogPort, DuckDbBinding, JDBC URL, dialect) 레지스트리. 포트 계약이 좋아 디스패처 계층만 추가하면 됨.

MediumAdmin — 주변 화면 catch 누락 4곳 (S5 연결테스트 · S7 토큰 · 임베드 모달)

조치 각 화면 catch 추가 + 로딩/오류/빈 상태 분리, 재발급 확인 모달 + 진행 중 disabled.

Medium공용 Modal 포커스 트랩·스크롤 락 부재 + 검색 디바운스 없음

공용 Modal.tsx에 포커스 트랩·초기 포커스·스크롤 락이 없어 Tab이 배경으로 새고, 오버레이 클릭 한 번에 폼 입력이 확인 없이 유실됩니다(완비된 ChartFocusDialog가 공용화 안 됨). 검색은 키마다 API 2건 + 목록 blank flash(SearchBox.tsx, useChartPage.ts:21).

조치 ChartFocusDialog 트랩 로직을 Modal로 이관, 250ms 디바운스 + placeholder data 유지.

Medium운영 환경 — CORS 하드코딩 · 보안 헤더 부재 · Spring Boot 3.3.5 EOL

CORS 출처가 localhost로 하드코딩돼 운영 배포 시 재빌드 강제(CorsConfig.java:16, "하드코딩 금지" 원칙 위반), 관리 콘솔 next.config.mjs에 CSP·X-Frame-Options 등 보안 헤더 전무, Spring Boot 3.3.x는 2025-06 OSS 지원 종료라 보안 패치 없음.

조치 CORS를 프로퍼티로 외부화, 콘솔 라우트 보안 헤더 세트, Boot 3.5.x 상향.

MediumSDK — 실패 후 재시도 불능 + 완전 무음 진단 + ECharts 인스턴스 누수

scan()이 렌더 전에 data-chart-rendered를 찍고 실패해도 지우지 않아 SPA 재스캔으로 복구 불가, 오류가 완전 무음이라 호스트 개발자가 401인지 CORS인지 진단 불가(index.ts:70 catch {}), setOption throw 시 init된 ECharts 인스턴스가 dispose되지 않아 detached DOM 고정.

Medium계약서-구현 불일치 4건 + 서드파티 고지 누락

계약서의 GET /users/{userId}/tokens 미구현, 토큰 발급/회수/사용자 생성 상태코드 3건(201/204/201 명세 vs 전부 200), 422 SQL_ERROR의 detail/position 필드 미구현. NOTICES에 번들되는 ECharts(Apache-2.0)·DuckDB(MIT) 고지 누락.

조치 @ResponseStatus 3줄로 상태코드 정합, 계약서 에러코드 표 개정, NOTICES에 ECharts·DuckDB 추가.

05

요청 항목별 직접 답변

처음 지정한 점검 축에 대한 결론.

Q1코드가 모듈화 잘 되어 있나?부분

백엔드 계층 분리(web·chart·query·converter·cache)는 명확하나 패키지 순환 의존과 ChartOptionConverter God class가 흠. 프론트는 계산 로직을 lib로 잘 뺐으나 ChartEditor 1,653줄은 훅 분리 여지.

Q2디자인 패턴이 잘 사용되었나?양호

SPI/Port(CatalogPort·QueryEngine·DuckDbBinding), Strategy(RefRenderer 방언 주입), 단일 정책 소유(SourceCompositionPolicy)가 모범적. 단 차트 타입 분기는 패턴 없이 거대 if-체인이라 확장 지점이 흩어짐.

Q3코드 규칙은 일관적인가?대체로

record·DTO 위치·엔드포인트 은닉·타입 집중은 일관적. 흠은 주석 언어(한/영) 혼용과 API 오류 메시지 한/영 혼용(예: "사용자를 찾을 수 없습니다" vs "Chart not found.").

Q4에러 처리기가 잘 되어 있나?혼재

envelope 단일 계약과 상태코드 정합은 성숙. 그러나 내부 예외 노출 4종과, 더 근본적으로 관리 API 무인증이 에러 처리 이전의 문제.

Q5UI가 오류를 친절히 설명하나?편차 큼

에디터(S2)·데이터 카탈로그(S7')는 요청 ID 동봉·필드 단위 안내로 양호. 반면 목록·토큰·모달·연결테스트는 무반응·빈 상태 위장·오표시가 다수라 화면 간 밀도 편차가 큼.

Q6차트 실행/부재 시 원시 오류 대신 내부 형식으로 안내하나?원칙 OK, 구멍 有

SDK는 원시 에러/스택을 방문자에게 절대 노출하지 않는 구조로 원칙은 잘 지킴. 단 로딩/타임아웃 부재(영구 빈 박스)와 0행 empty state 부재(빈 축 + "정확한 결과")가 정확히 이 관점의 구멍. Admin은 목록 실패를 빈 상태로 위장.

Q7확장성 좋은 인터페이스 설계인가?이음매 OK, 디스패처 미완

포트 계약은 정확하나 kind 디스패처가 없어 MySQL 추가 시 10파일, 새 차트 타입 추가 시 6~8곳 수정. 설계 의도는 옳고 디스패처 계층만 추가하면 되는 상태.

Q8프론트에서 의도와 다르게 동작하는 것은?있음

IN 조건 타이핑 입력 불가(콤마 스냅백), 목록 실패의 빈 상태 위장, 새로고침 이탈 경고 부재, 검색 blank flash, 재발급 더블클릭 중복 발급, 신규 사용자+토큰 부분 실패 시 재시도 중복 오류. 반면 미리보기 stale 덮어쓰기는 requestId 가드로 방어됨.

우선순위 조치 로드맵

요청 타임아웃 + 로딩 placeholder, 0행 empty state, 실패 재시도/진단 코드. "원시 오류 대신 내부 형식 안내" 완성.

Admin 동작 버그·에러 UX · High · 사용자 강조

SQL_ERROR·FEDERATION_ERROR 등 4종을 일반화 메시지 + requestId로 전환, 상세는 서버 로그로.

확장성 리팩터링 · High(구조)
