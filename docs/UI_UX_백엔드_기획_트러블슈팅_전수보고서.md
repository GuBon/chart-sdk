## 2. 결론

프로젝트의 반복 문제는 개별 버그보다 **경계가 불명확했던 것**에서 주로 발생했다.

- UI에서는 “무엇을 고르는가”와 “무엇을 꾸미는가”가 한 패널에 섞였다.
- UX에서는 정상 화면은 있었지만 신규·로딩·오류·저장 전 같은 중간 상태가 뒤늦게 채워졌다.
- 백엔드에서는 SQL, 캐시, preview, embed가 같은 데이터를 서로 다른 규칙으로 해석했다.
- 테스트에서는 MSW가 실제 Spring·CORS·암호화·PostGIS·JWT의 계약 차이를 가렸다.
- 기획 문서는 기능이 구현된 뒤에도 “2차/후속” 표기를 유지해 현재 상태와 어긋났다.

개선 방향은 일관된다. **권위 있는 원천을 하나 정하고, 상태를 명시하며, mock과 운영 경로를 별도 계층으로 검증한다.** 이 원칙으로 옵션 레지스트리, Java 변환기, 저장 스냅샷, sampling fixture, 실백엔드 E2E를 도입했다.

## 3. 현재 확정된 UI 정보 구조

### 3.1 테마·스타일·계열

| 개념 | 현재 정의 | 근거 | 효과 |
|---|---|---|---|
| 테마 | 이름을 그대로 유지한다. 여러 색의 조합과 배정 규칙을 선택하는 프리셋이다. | CARTOColors CC BY 4.0, `chart-options/palettes.ts`, `THIRD_PARTY_NOTICES.md` | 사용자가 “팔레트 데이터 구조”가 아니라 완성된 시각 인상을 선택한다. |
| 스타일 | 테마, 색상, 배경, 글꼴, 차트 고유 외형처럼 결과의 모양을 바꾸는 설정이다. | `optionEditorTabOf()`와 옵션 레지스트리 | 색상이 계열과 분리되어 단일 계열·지도에서도 같은 위치에 존재한다. |
| 계열 | 시리즈 종류, 라벨, 정렬, 범례처럼 실제 시리즈의 표현·식별에 관한 설정이다. | `seriesTypes`, label, legend 매핑 | 시리즈가 없는 포인트 지도에서는 빈 탭을 만들지 않는다. |

CARTOColors의 공식 분류를 그대로 사용한다.

- 범주를 구분하는 정성형 테마: 6개, 각 12색
- 값의 낮음→높음을 표현하는 순차형 테마: 19개, 각 7단계
- 영역 지도·행렬 히트맵은 순차형, 나머지 차트는 정성형을 기본으로 노출

따라서 지도에서 20개가 넘는 임의 테마를 보여주는 것이 아니라, **공식 순차형 19개를 노출하는 것**이 현재 계약이다.

### 3.2 지도 편집 탭 순서

지도는 다음 순서를 사용한다.

`기본 → 스타일 → 영역 → 계열(실제 계열 설정이 있을 때만) → 상호작용 → 데이터`

- `map`: 위 6개 탭
- `geoscatter`: `기본 → 스타일 → 영역 → 상호작용 → 데이터`

이 순서는 ArcGIS를 그대로 복제한 것이 아니라 작업 흐름을 참고해 ChartSDK 구조에 맞춘 것이다. 먼저 차트와 색을 정하고, 지도 범위를 정한 뒤, 실제로 존재하는 계열만 다루고, 상호작용과 데이터 갱신을 마지막에 둔다.

### 3.3 시도명·시군구명 데이터

`geometry_demo.korea_sigungu_statistics`는 다음 역할을 분리한다.

- `region_name`: 지도 경계 매칭용 결합 이름
- `sido_name`: 시·도 분석·필터용
- `sigungu_name`: 시·군·구 분석·필터용

컬럼이 사라진 원인은 UI가 삭제한 것이 아니라 **이미 초기화된 PostGIS tmpfs/볼륨이 최신 `03-korea-statistics-years.sql`을 다시 실행하지 않은 초기화 시점 드리프트**였다. 최신 초기화 SQL은 두 컬럼을 `NOT NULL`로 만들고 2024~2026년 3개년 행을 생성한다. 효과는 지도 매칭 이름을 훼손하지 않으면서 시도/시군구를 각각 축·필터·계열에 사용할 수 있다는 점이다.

## 7. 기획·제품 전수 분석

### 7.1 구현 단계 표기의 드리프트

과거 문서는 다음 기능을 2차/후속으로 남겼지만 현재 구현돼 있다.

- stale-while-revalidate와 single-flight
- 지금 갱신과 `computedAt` 캡션
- `seriesBy` 시리즈 분할과 서버 피벗
- 옵션 검색
- 상자수염·행렬 히트맵·영역 지도·포인트 지도를 포함한 8개 차트 대분류
- TABLE·VIEW·MATERIALIZED VIEW 카탈로그
- PostGIS Point/Polygon

로드맵은 “언젠가 만들 기능” 목록이 아니라 **현재/검증 완료/후속** 상태표여야 한다. 이번에 PRD·화면설계·API·테스트 문서를 현재 구현으로 맞췄다.

### 7.2 벤치마크의 역할

ArcGIS, Grafana, Metabase, Redash는 구조적 참고다.

- ArcGIS: 지도 스타일·영역·상호작용을 사용자의 작업 순서로 나누는 방식
- Grafana: 오른쪽 옵션 패널, 섹션 접기, 옵션 검색
- Redash: 스키마 브라우저와 SQL 작업 공간
- Metabase: 노코드→SQL의 단방향 전환과 임베드 개념

참고 서비스의 용어와 탭 순서를 그대로 복사하지 않는다. ChartSDK의 실제 데이터 모델과 시리즈 존재 여부를 우선한다.

## 8. 이번 갱신 기능의 최종 흐름

1. 신규 차트는 `지금 갱신`을 비활성화하고 저장을 안내한다.
2. 저장 차트에 미저장 변경이 있으면, 저장된 과거 정의를 갱신하지 않도록 비활성화한다.
3. 클릭하면 `POST /api/v1/charts/{id}/refresh`를 호출한다.
4. 성공 응답의 `computedAt`을 즉시 반영한다.
5. `GET /api/v1/charts/{id}/preview`를 다시 호출한다.
6. 새 columns/rows/option을 결과표와 미리보기에 반영하고 저장 preview snapshot도 교체한다.
7. refresh 실패는 버튼 아래 `role=alert`로 표시한다.
8. refresh는 성공했지만 preview 재조회가 실패하면 두 결과를 구분해 안내한다.

이 순서의 핵심은 “서버 계산 성공”과 “Admin 화면 최신화 성공”을 같은 것으로 간주하지 않는 것이다.

## 9. 우선순위 제안

### P0 — 배포 전

1. Admin 인증/SSO, current user 주입, owner NULL 탈출구 제거 — M10으로 갱신 API가 조회와 같은 범위 검사를 타게 됐지만, `owner_id NULL` 탈출구가 남아 있어 이 항목이 끝나기 전까지 실질 격리는 성립하지 않는다

## 10. 기대 효과

- 사용자는 저장·실행·갱신 상태를 구분할 수 있고, “버튼은 있는데 아무 일도 안 일어나는” 상태가 사라진다.
- 지도 사용자는 공식 19개 순차형 테마와 영역 설정을 혼동하지 않고, 계열이 없으면 빈 계열 탭을 보지 않는다.
- 운영자는 MSW 성공만으로 배포를 판단하지 않고 실제 Spring/PostGIS/JWT/CORS 경로의 회귀를 CI에서 확인한다.
- 개발자는 옵션·SQL·변환·테스트 수치의 권위를 찾을 수 있어 같은 규칙을 여러 파일에서 다르게 고칠 가능성이 줄어든다.
- 기획 문서는 완료 기능과 후속 기능을 구분해 다음 작업 우선순위를 실제 위험 기준으로 정할 수 있다.
