# 코드구조 안내

최종 갱신: 2026-08-11 (데이터소스 확장점 §6 추가).

이 문서는 기능 명세가 아니라 코드의 책임과 의존 방향을 설명한다. 새 파일을 만들 때는 “파일이 길다”보다 “서로 다른 이유로 바뀌는 코드인가”를 먼저 판단한다.

## 코드 구조 선택 근거

| 개선 목표 | 현재 선택 | 검토 대안 | 선택 이유와 현재 이점 | 한계·검증 |
|---|---|---|---|---|
| 변경 이유가 다른 코드의 연쇄 수정 방지 | HTTP adapter→service→repository/query/converter 책임 분리 | controller 중심, 파일 길이 기준 분할, 과도한 generic layer | 비즈니스·저장·외부 DB·표현 규칙을 독립 테스트하고 교체 가능 | 작은 기능까지 계층화하지 않도록 재사용·변경 이유로 판단 |
| Admin·SDK 옵션 정의 공유 | npm workspace `chart-options` | 복사, 별도 package repository, 서버를 원천으로 codegen | 한 repository에서 UI·SDK asset·fixture를 원자적으로 변경 | Java는 생성 JSON과 parity 검증 필요 |
| 실행 엔진 교체 가능성 | `QueryRows`, renderer, `AdmissionController` 인터페이스 경계 | 모든 구현을 하나의 service에 직접 결합 | PostgreSQL/DuckDB·로컬/분산 admission을 호출부 변경 없이 교체 | 추상화가 실제 두 구현/전환 조건을 가질 때만 유지 |
| 역사 기록과 현재 계약 분리 | 전문 문서 SSOT+이력 문서 | 한 거대 문서, 모든 문서에 계약 복사 | 현재 규칙과 변경 이유를 각각 적합한 형태로 유지 | 링크·coverage 자동 검사 필요 |

대표 구조 선택의 근거와 한계는 각 절에서 함께 설명한다.

## 1. 전체 의존 방향

```text
Admin 화면(app)
  └─ 도메인 컴포넌트(components/charts, components/data)
       ├─ 공통 UI(components/ui)
       ├─ 순수 규칙(lib)
       └─ API 클라이언트(lib/api)
                ↓ HTTP
Server Controller(web)
  └─ Service(chart, datasource, cache)
       ├─ Repository/JdbcTemplate
       └─ query · converter · federation 규칙 엔진
                ↓
        메타 DB / 고객 데이터소스
```

- 위 계층은 아래 계층을 호출할 수 있지만, 아래 계층이 화면 컴포넌트를 알면 안 된다.
- Admin은 DB에 직접 접근하지 않고 서버 API만 호출한다.
- ECharts option의 운영 권위는 Java 변환기다. Admin mock은 테스트용 미러이며 공용 계약 fixture로 드리프트를 막는다.
- `chart-options`는 옵션 정의·기본값·표시 조건의 SSOT다.

## 2. Admin 책임

### 라우트와 화면

`admin/app`의 page 파일은 URL 파라미터를 읽고 화면 컴포넌트에 전달하는 얇은 경계로 둔다. 데이터 카탈로그 URL은 다음 계층으로 고정한다.

| URL | 화면 의미 |
|---|---|
| `/charts/{datasourceName}` | 해당 데이터소스 범위의 차트 |
| `/charts/{datasourceName}/{schema}` | 해당 스키마 범위의 차트 |
| `/charts/{datasourceName}/{schema}/{relation}` | 해당 관계 기반 차트 |
| `/charts/{datasourceName}/{schema}/{relation}/{chartId}` | 해당 차트 편집 |

경로 조립은 `admin/lib/chartRoutes.ts`만 사용한다. URL은 사용자별 고유 `mc_datasource.name`을 인코딩해 사용하고, 내부 API·builderConfig·조인은 안정적인 숫자 ID를 유지한다. 차트 응답의 `mainTable.datasourceName`은 현재 이름을 붙인 읽기 모델이므로 저장 입력에 넣지 않는다. 모든 저장 차트는 기준 관계를 가져야 하며 정식 주소는 `/charts/{datasourceName}/{schema}/{relation}/{chartId}`, 신규 초안은 `/charts/new`다. `new`는 데이터소스 예약 이름이다. 메타데이터 탐색은 동일 범위 경로의 `view` 쿼리로만 연다.

### 공통화한 경계

- `lib/chartTypes.ts`: 차트 대분류의 사용자 표시명과 아이콘. 목록 카드·필터·옵션 패널이 공유한다.
- `lib/relations.ts`: TABLE·View·Materialized View 표시명과 선택 가능 여부. 데이터 탐색·스키마 선택기가 공유한다.
- `lib/tableSelection.ts`: 원본·기존 조인·새 조인 선택 대상을 구분하고 사용자 표시 문구를 만드는 순수 규칙이다.
- `components/ui/Pagination.tsx`, `EmptyState.tsx`: 도메인 의미가 없는 반복 UI.
- `components/charts/useChartPage.ts`: 차트 목록, 배치 미리보기, 페이지 보정, 재조회와 오래된 응답 무시를 한 수명주기로 묶는다.
- `OptionPanel.tsx`: 검색·존·섹션·접힘을 조정한다. `OptionControl.tsx`: 레지스트리의 각 입력 종류를 렌더링한다.
- `components/ui/Toast.tsx`: 하단 알림의 상태·자동 해제 타이머(`useToast`)와 표시(`Toast`)를 한 곳에서 관리한다. 접근성 고지(`role="status"`, `aria-live="polite"`)를 항상 포함하며, 편집기·차트 목록·토큰 화면이 공유한다. z-index만 화면별로 `className`으로 주입한다(편집기는 자체 모달 위 `z-[60]`).

**`'use client'` 선언 기준**: React 훅이나 브라우저 API(`window`·`document`·`navigator` 등)를 직접 사용하는 컴포넌트만 파일 최상단에 `'use client'`를 선언한다. props를 받아 렌더링만 하는 순수 프레젠테이션 컴포넌트는 선언하지 않으며(이벤트 핸들러를 prop으로 전달만 하는 것은 클라이언트 기능 사용이 아니다) 상위 클라이언트 트리에 포함되어 동작한다. 라우트 진입점(`app/**/page.tsx`, `layout.tsx`)은 상호작용 화면이므로 선언한다.

### 의도적으로 유지한 큰 컴포넌트

- `ChartEditor`: 편집기 전체 상태와 패널 간 전이를 조정하는 오케스트레이터다. 원본·조인 선택 대상도 여기서 소유해 중앙 `NocodeBuilder`의 요청과 좌측 `SchemaExplorer`의 선택 결과를 연결한다. 상태를 여러 훅으로 잘게 나누면 저장·실행·복원 순서를 추적하기 어려워지므로 독립된 변경 축이 생길 때만 분리한다.
- `NocodeBuilder`: 하나의 빌더 폼과 검증 흐름이다. 관계 선택 칸은 대상을 요청할 뿐 카탈로그를 다시 렌더링하지 않으며, 새 조인은 실제 관계 선택 뒤에만 `BuilderConfig`에 추가한다. 조인, 필터, 표본 중 하나가 다른 화면에서도 재사용되기 전에는 억지로 분리하지 않는다.
- `SchemaExplorer`: 관계 목록·검색·페이지·컬럼 펼침을 담당한다. 선택 모드의 대상 자체는 소유하지 않고 배너·비활성 키·선택 이벤트만 받아 표시하므로 원본과 조인이 같은 카탈로그 경로를 공유한다.

## 3. Server 책임

### HTTP 경계와 서비스

- `web/*Controller`: URL·요청 바인딩·응답 형태만 담당한다.
- `chart/*Service`, `datasource/*Service`: 유효성 검사와 작업 순서 같은 애플리케이션 규칙을 담당한다.
- Repository/JdbcTemplate 사용 코드는 영속화와 행 매핑을 담당한다.
- `query`, `converter`, `federation`: SQL 생성, ECharts 변환, 다중 소스 실행처럼 계산 규칙이 밀집된 엔진이다.

`DatasourceController`에 있던 JDBC·암호화·연결 시험은 `DatasourceService`로 이동했다. 컨트롤러는 변경·삭제 성공 뒤 기존 커넥션 풀을 폐기하는 HTTP 경계 동작만 조정한다. API 읽기 모델은 비밀번호가 없는 `DatasourceView`로 고정한다.

차트 목록의 검색 조건은 `ChartListQuery` 값 객체로 전달한다. 여러 계층에 8개의 위치 인자를 반복하지 않고, 페이지 크기·스키마 기본값 같은 해석도 이 객체가 한 번만 수행한다.

### 의도적으로 유지한 규칙 엔진

- `BuilderSqlBuilder`: builderConfig를 검증하고 SQL과 파라미터를 함께 만드는 한 규칙 엔진이다.
- `ChartOptionConverter`: QueryRows를 ECharts option으로 바꾸는 한 규칙 엔진이다.

두 파일은 길지만 규칙 순서와 공용 문맥을 함께 읽어야 한다. 차트 종류별 구현이 독립 배포되거나 독립 테스트 계약을 갖게 되기 전에는 파일 길이만으로 전략 클래스를 늘리지 않는다.

## 4. 분리 여부 판단 기준

다음 중 하나가 참이면 분리를 고려한다.

1. 서로 다른 기능 변경이 같은 파일에서 반복적으로 충돌한다.
2. 같은 규칙을 둘 이상의 화면이나 서비스가 복사한다.
3. 외부 자원 접근과 순수 계산이 섞여 단위 테스트가 어려워진다.
4. 입력·출력 계약을 독립적으로 이름 붙이고 테스트할 수 있다.

반대로 한 번만 쓰는 짧은 표현 컴포넌트, 같은 상태 전이에 강하게 결합된 로직, 단순히 줄 수가 많은 규칙표는 그대로 둔다. 공통화는 중복 제거보다 의미의 단일 권위를 만드는 데 목적이 있다.

## 5. 검증 기준

- 순수 규칙은 단위 테스트로 값과 경계를 고정한다.
- 컨트롤러/서비스 분리는 위임 순서와 DB 행 매핑을 단위 테스트한다.
- 실제 PostgreSQL 계약은 서버 통합 테스트가 담당한다.
- URL과 사용자 동선은 `chartRoutes.test.ts`와 Playwright E2E가 함께 검증한다.
- 전체 명령과 최신 테스트 수치는 `docs/테스트_전략.md`만 갱신한다.

## 6. 데이터소스 확장점(포트)

새 데이터소스 종류(파일·API·타 DBMS 등)를 위한 이음매는 다음 4개다. 배경·편차·검증은
[데이터소스 인터페이스 확장 설계](데이터소스_인터페이스_확장_설계.md)가 정본이다.

| 포트 | 위치 | 책임 | 현재 구현 |
|---|---|---|---|
| `CatalogPort` | `datasource/spi/` | 소스에서 카탈로그 메타데이터 로드 | `datasource/postgres/PostgresCatalogPort` |
| `DuckDbBinding` | `datasource/spi/` | 소스를 DuckDB 세션에 붙이는 SQL 조립 | `datasource/postgres/PostgresDuckDbBinding` |
| `QueryEngine` | `query/engine/` | 실행 엔진 공통 계약(차트·미리보기·표본·EXPLAIN) | `query/engine/PostgresQueryEngine` · `federation/DuckDbQueryEngine` |
| `SourceCompositionPolicy` | `query/engine/` | 엔진 선택·스냅샷 서빙·갱신 모드 정규화 판정 | `query/engine/DistinctCountCompositionPolicy`(distinct ≥ 2) |

- **종류 무관 조율자:** `query/CatalogService`(TTL 캐시·무효화), `federation/FederatedQueryRunner`(카탈로그→표본 계획→SQL 생성→실행 골격 한 벌).
- **새 소스 종류 추가 절차:** ① `CatalogPort` 구현 1개 ② DuckDB 로 실행되는 종류(파일 등)는 `DuckDbBinding` 구현 1개 — 기존 federated 엔진 슬롯 재사용 ③ `SourceCompositionPolicy` 규칙 갱신 1곳. `BuilderSqlBuilder`·변환기·캐시·임베드·SDK·프론트는 무변경이 목표이며, `QueryEngineSeamTest`가 생성자 이음매 계약을 실행 수준으로 가드한다. 단, **첫 번째** 새 종류 도입 시에는 1회성 승격 공사(kind 판별자, 포트 주입의 종류 키 디스패치화, 서빙 판정의 종류 인지화)가 선행되고, **독자 실행 엔진이 필요한 종류**라면 runner 의 single/federated 2슬롯 라우팅을 엔진 선택 디스패치로 승격하는 작업이 추가된다 — 모두 [설계 §8](데이터소스_인터페이스_확장_설계.md)이 목록으로 관리한다.
- **패키지 불변식(grep 검증):** `datasource/postgres/` 밖에서 `jdbc:postgresql`·`pg_catalog`·`libpq`·`TYPE postgres` 검색 0건. PostgreSQL 규약은 그 패키지에만 둔다.
- **위임 파사드:** `QueryExecutor.catalog()`·`DuckDbFederation.attachSql()` 등은 기존 호출부·테스트 호환용 파사드다. 권위는 각 포트 구현에 있으며, 새 코드는 `CatalogService`·포트를 직접 주입받는다.
