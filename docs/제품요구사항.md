## 1. 개요

웹페이지에 `<div>` 한 줄과 스크립트만 삽입하면 차트가 렌더링되는 사내 전용 임베드 차트 솔루션을 개발한다. 사용자가 노코드 빌더(기본) 또는 SQL(2차)로 차트를 정의하고 시각화 옵션을 지정하면, 토큰이 포함된 임베드 코드가 발급되어 사내 인원이 자신의 페이지에 차트를 끼워 넣어 사용한다. Metabase의 임베디드 분석 기능과 개념적으로 유사하나, 핵심 기능(네이티브 임베드, SSO)이 유료인 Metabase와 달리 사내 요구에 맞춰 자체 구축한다.

## 2. 배경 및 목적

상용 BI 도구(Metabase 등)는 차트 그리기는 무료지만, 본 프로젝트가 필요로 하는 두 핵심 기능이 유료 영역에 있다.

- 네이티브 임베드(iframe이 아닌 div 직접 렌더 + 토큰 인증): Metabase Pro 전용
- SSO 로그인 연동: Metabase Pro 전용

따라서 ECharts + Spring Boot 기반으로 동일한 임베드 방식을 자체 구축하여, 구독 비용 없이 사내 요구(임베드 + 향후 SSO + Type B 임베디드 배포)에 맞춘 솔루션을 확보하는 것을 목적으로 한다.

## 3. 대상 사용자

- 사내 직원 전용 도구다. 외부 고객 대상이 아니다.
- 개인 계정 단위로 사용한다. 인증은 사내 SSO(통합로그인)를 전제하며, 회사 차원에서 타 솔루션과의 통합로그인이 추진될 가능성이 높다.
- MVP 단계에서는 인증 없이 동작하며, SSO 로그인은 설계에 포함하되 구현은 최후순위로 둔다.
- 계정 생성/삭제/비밀번호는 IdP(SSO)가 관리하므로 멤버 관리 화면은 만들지 않는다. 로그인 시 사용자 레코드를 자동 생성(JIT)한다.
- 차트 가시성: 개인 사용자 소유 범위. 사용자는 본인이 등록한 데이터소스와 본인이 만든 차트를 보고 수정·삭제한다. 공유/팀 권한은 후속 기능이다.
- 인수인계서 원문은 "고객사 납품(B2B)"을 전제했으나, 본 프로젝트의 서비스 단위는 조직이 아니라 **개인 사용자**다. 실제 연결 대상 DB는 회사/조직의 업무 DB일 수 있지만, 데이터소스 등록·차트 정의·토큰 발급의 소유 범위는 개인 사용자(`owner_id`/`user_id`)로 잡는다.

## 4. 개발 조건 및 제약

- 개발 인원: 사실상 단독 개발
- 일정: 수 주 내 MVP
- 설계 주도권: 본 프로젝트 리드(인수인계서 명세 변경 권한 보유)
- MVP 범위 축소가 성공의 핵심이며, 화려한 기능보다 코어 파이프라인의 완결을 우선한다.

## 5. 시스템 아키텍처

### 5.1 3대 구성 요소

| 구성 요소 | 기술 스택 | 역할 |
|---|---|---|
| Chart SDK | Vanilla JS + Apache ECharts | div 자동 검출, 토큰으로 데이터 요청, ECharts 렌더 |
| Backend API | Spring Boot + JPA + Flyway | 메타 DB 소유, SQL 실행, ECharts JSON 생성, 토큰 검증 |
| Admin Console | Next.js | 차트 빌더 UI (DB 직접 접근 없음, API만 호출) |

### 5.2 DB 소유권 및 마이그레이션

- Backend(Spring Boot)가 메타 DB를 단독 소유한다.
- Admin Console(Next.js)은 DB에 직접 접근하지 않고 Backend API만 호출한다. 따라서 Prisma는 사용하지 않는다.
- 마이그레이션은 Flyway로 관리한다. Spring Boot 구동 시 자동 적용된다. (인수인계서 8페이지의 Prisma 자동화는 Flyway로 대체)

### 5.3 데이터 구조 (메타 DB + 다중 데이터 소스)

- 메타 DB 1개: 솔루션이 소유(`mc_` 객체). 사용자·토큰·개인별 데이터소스·차트 정의 저장. Spring + Flyway가 관리.
- 데이터 소스 N개: 차트가 데이터를 조회할 PostgreSQL DB들. Admin에서 등록(호스트/포트/계정)하며, 차트마다 하나를 지정한다.
- 동적 커넥션 풀: 데이터소스별 커넥션 풀(HikariCP)을 런타임에 생성·관리한다. 메타 DB 연결과 분리.
- 자격증명 보안: 데이터소스 접속 비밀번호는 암호화(AES-GCM)하여 저장한다. 암호화 키는 `.env`. 등록 계정은 읽기 전용을 권장(등록 화면에서 안내).
- 데이터소스 엔진은 PostgreSQL로 고정한다(JDBC 드라이버 단일, SQL 방언 단일).

### 5.4 배포 모드 (Type A / Type B 모두 지원)

| 모드 | 설명 | DATABASE_URL |
|---|---|---|
| Type A (독립 설치형) | docker-compose로 전용 PostgreSQL을 함께 패키징 | 전용 DB 가리킴 |
| Type B (임베디드) | 기존 운영 DB에 연결, `mc_` 메타 테이블만 추가 | 기존 DB 가리킴 |

- 애플리케이션 코드는 두 모드를 구분하지 않는다. `DATABASE_URL` 값만 다르며, docker-compose 구성과 `.env`만 달라진다.
- Type B에서는 기존 운영 DB의 업무 테이블을 절대 건드리지 않아야 한다. Flyway 마이그레이션은 솔루션 소유 `mc_` 객체만 생성/변경한다. 예외적으로 S1 검색 최적화를 위해 PostgreSQL 표준 contrib 확장 `pg_trgm`을 사용하므로, Type B 설치 전 `CREATE EXTENSION pg_trgm` 권한을 확인한다.

## 6. 데이터 렌더링 방식

서버가 ECharts 설정(option)을 완성된 형태로 생성하여 SDK에 전달하는 방식(방식 A)을 채택한다. (인수인계서 4페이지 "ECharts 전용 JSON 반환"과 일치)

```
PostgreSQL에서 SQL 실행
  → Backend가 결과를 ECharts option JSON으로 조립 (차트종류/색상/축/범례 반영)
  → SDK는 받은 JSON을 chart.setOption()으로 렌더만 수행
```

SDK는 차트 모양을 결정하지 않으며, 모든 시각화 설정은 Admin/서버에 집중된다.

### 6.1 데이터 형태 컨벤션 (서버 변환기 규칙)

- SQL 결과의 첫 번째 컬럼 = X축(카테고리), 나머지 숫자 컬럼 = 각각 하나의 시리즈.
- 시리즈가 2개 이상이면 다중 막대/다중 선이 되며, 시리즈별 색·범례가 자동 구성된다.
- ECharts option 조립의 운영 권위는 서버의 단일 Java 변환기에 둔다: (rows, chartType, options) → option JSON. Admin MSW 변환기는 프론트 테스트 전용 미러이며 공용 계약 fixture로 운영 변환기와 핵심 결과를 맞춘다.
- 시리즈 분할(breakout)은 `builderConfig.seriesBy`를 두 번째 그룹 축으로 사용하고 서버가 rows를 피벗해 다중 시리즈를 조립한다. "첫 컬럼=X, 이후 컬럼=시리즈" 컨벤션은 피벗 산출물에 그대로 유지된다.

## 7. 기능 요구사항

### 7.1 차트 렌더링 (코어, 최우선)

- SDK가 페이지 로드 시 `[data-embed-key]` 속성을 가진 div를 자동 검출한다 (DOM 스캐닝).
- 각 div에서 차트별 불투명 임베드 키를 읽어 Bearer 헤더로 Backend에 전달한다. chartId는 클라이언트가 보내지 않는다.
- Backend는 검증된 키의 서버측 chart 바인딩으로 SQL을 실행하고 ECharts option JSON을 반환한다.
- SDK는 `echarts.init()` 후 `setOption()`으로 div에 직접 렌더한다.
- SDK는 컨테이너 div의 크기 변화를 추종한다(ResizeObserver → `chart.resize()`). 실제 임베드 크기·반응형은 호스트 페이지의 CSS 책임이고, SDK는 따라가기만 한다.
- 저장된 `options.display`는 자동 글꼴과 Admin 검수 캔버스의 **논리 설계 크기**다. Admin 미리보기에서 가로·세로 프리셋을 고르거나 너비·높이를 직접 편집하며, 숫자를 직접 바꾸면 `custom`으로 저장한다. SDK가 호스트 DOM을 1920×1080처럼 강제하는 값은 아니며, 임베드에서는 동일 option을 현재 컨테이너에 반응형으로 렌더한다.
- 글자 크기 계약은 세 경우로 고정한다. 논리 설계 크기를 바꾸면 **자동(px 미지정)인 요소만** 다시 계산하고, 사용자가 px를 지정한 요소는 그 값을 유지하며, 호스트 CSS로 임베드 영역만 리사이즈할 때는 어느 요소든 fontSize를 다시 계산하지 않는다.

### 7.2 시각화 옵션 (핵심 기능, 지속 확장)

- 차트 분류 체계: **대분류 → 소분류(variant) 2단계** (v1.4).
  - 현재 대분류 8종: 막대(bar) / 선(line) / 원형(pie) / 산점도(scatter) / 박스 플롯(boxplot) / 행렬 히트맵(heatmap) / 영역 지도(map) / 포인트 지도(geoscatter). 모두 활성 상태다.
  - 소분류는 대분류에 종속된다 — 대분류 선택 시 소분류 목록이 교체된다: 막대[기본·누적·그룹·가로] / 선[기본·곡선·영역·누적영역·계단] / 원형[파이·도넛·로즈] / 산점도[산점도·버블]. 나머지 4종은 현재 기본 variant 하나를 사용한다.
  - 소분류는 별도 chart_type이 아니라 **`options.variant`로 저장**: 막대(기본·누적·그룹·가로) / 선(기본·곡선·영역·누적영역·계단) / 원형(파이·도넛·로즈) / 산점도(산점도·버블). chart_type 컬럼·CHECK는 대분류만 — 소분류 추가 시 마이그레이션 불필요. 서버 변환기가 variant를 ECharts 속성(stack, areaStyle, radius 등)으로 해석한다.
- MVP 옵션 (섹션별):
  - 기본: 대분류·소분류, 차트 제목(`title.text`), 제목 위치 — 가로(좌/중앙/우 `title.left`) × 세로(상/하 `title.top`) 2축, 설명(차트 메타 — S1 카드 표시용, option 미반영)
  - 크기: 작은 카드 360×240 / 표준 640×360 / 대형 960×540 / HD 1280×720 / FHD 1920×1080 / 사용자 지정 240~3840×180~2160. Admin은 이 논리 크기로 렌더한 뒤 화면에 맞게 축소한다
  - 글꼴: 자동(설계 크기별 기본값 + 80~150% 배율, custom 논리 크기는 가로·세로 면적을 함께 반영) 또는 직접 지정(제목·범례·축·데이터 라벨·툴팁의 고정 px). 제목·범례·visualMap 여백은 최종 글꼴 px에서 동적으로 계산한다
  - 색상: 색 모드(팔레트/개별 지정), 팔레트 프리셋, 항목별·시리즈별 개별 색 — 모든 대분류 공통(막대=항목/시리즈, 선=시리즈, 원형=조각)
  - 축(X·Y 그룹 구조): 그룹별 제목·단위 표기·범위(자동/수동 min·max)·스케일(선형/로그)과 X·Y 라벨 세로쓰기. 세로쓰기는 grapheme 단위 줄바꿈으로 위에서 아래로 쌓으며, 별도 라벨 회전값이 있으면 쌓인 라벨 전체에 함께 적용한다. X축의 범위·스케일은 X가 숫자일 때만 활성(산점도 — `appliesTo`로 제어), 카테고리 X축은 제목·라벨 회전도 제공
  - 계열: 데이터 라벨 표시, 정렬(원본/오름/내림)
  - 분석 표시: 기준선·기준 범위·목표값, 박스 플롯 1.5×IQR 이상치 표시·색상, 날짜·시간 X축 선 차트의 적용 계열별 단순 이동평균(SMA)·기간·범례 포함 여부
  - 범례: 표시 여부, 위치(상/하/좌/우). 상·하는 한 줄 scroll을 자동 적용하고, 좌·우는 scroll 토글을 제공
  - 데이터 갱신: 갱신 모드(수동/항상 최신 조회), [지금 갱신] — 7.7 참조
- 차트 종류 전환 규칙(비파괴): **데이터 구성(테이블·축·조건·정렬)은 어떤 전환에도 초기화하지 않는다.** 같은 대분류 내 소분류 전환은 옵션 전부 유지(완전 호환). 대분류 간 전환은 공통 옵션(제목·위치·색·범례)만 유지하고 이전 대분류 전용 옵션은 즉시 초기화 + 토스트 안내("막대 전용 설정이 초기화되었습니다" + 실행 취소). 비호환 데이터는 무시+안내로 처리(원형: 첫 시리즈만 사용 / 산점도: 숫자 X축 필요).
- 옵션 정의에 `appliesTo`(적용 대분류 목록) 메타를 두고 옵션 패널이 차트 종류별 노출을 필터링한다 — "옵션 추가 = 정의 한 줄" 원칙 유지.
- 확장 예약(후속): 0 기준 해제(`yAxis.scale`), 조건부 서식. 막대 너비·범례 좌/우·차트 여백 프리셋(`grid`)·툴팁 포맷은 구현됨. (곡선·영역·누적은 variant로 흡수됨)
- 저장: 시각화 옵션은 DB의 `options` JSONB 컬럼에 저장한다. 옵션 추가 시 스키마 마이그레이션이 불필요하다.
- 구현 원칙: 옵션 정의(키·타입·기본값·섹션)를 코드에서 데이터 목록으로 관리하고 옵션 패널이 이를 렌더한다. 옵션 추가 = 정의 한 줄 + 서버 변환기 한 줄. 옵션 패널 상단 검색은 옵션 이름·설명·섹션을 대상으로 동작하며, 결과가 없으면 빈 상태를 표시한다.

#### 개별 색 지정 (막대마다·선마다 다른 색)

- 팔레트 모드(기본): 색 배열을 순서대로 자동 적용. 데이터가 바뀌어도 깨지지 않는다.
- 개별 지정 모드: SQL 실행 성공 후 결과의 카테고리/시리즈 항목별로 색을 지정한다. 실행 전에는 비활성(동적 UI — 항목 수는 데이터에 의존).
- 저장 형태(JSONB): `colorMode`, `palette[]`, `colorMap{항목명: 색}`.
- 매핑 규칙: 항목이 `colorMap`에 있으면 지정 색, 없으면(SQL 변경으로 새 항목 등장) 팔레트 순서로 자동 적용. 차트가 깨지지 않게 한다.

### 7.3 차트 빌더 (Admin) — 노코드 + SQL 이중 모드

차트 정의는 두 모드를 제공한다. 노코드가 옵션 1(기본 경로), SQL이 옵션 2(고급 경로)다. MVP에서는 노코드만 구현하며, SQL 직접 작성 UI는 2차에서 추가한다. 새 차트는 항상 노코드에서 시작한다. 탭 자리는 화면에 미리 두되 SQL 탭은 2차까지 비활성("준비 중") 표시한다.

- 노코드 모드(옵션 1, 기본): 기존 DB의 TABLE·VIEW·MATERIALIZED VIEW 중 원본 선택 → X축 컬럼 [+ 날짜 타입이면 묶기(일/주/월, 기본 월) — DATE_TRUNC, MVP 포함] → Y축 컬럼 + 집계(합계/평균/표준편차/분산/개수/고유 개수/최소/최대/원본값) → 조건(WHERE: 컬럼·연산자·값 행 추가식) → 정렬. 원본·조인 관계는 중앙 드롭다운과 좌측 목록으로 이중 제공하지 않고, 중앙의 대상 칸을 누른 뒤 검색 가능한 좌측 카탈로그에서 고르는 단일 흐름으로 제공한다. 내부적으로 SQL을 생성하여 기존 실행 파이프라인을 그대로 사용한다(노코드 = SQL 생성기). 고객 DB의 관계를 생성·수정·갱신하지 않는다.
- `원본값(agg:"none")`은 모든 차트 타입에서 지원한다. 막대/선은 X/Y 튜플, 원형은 name/value 튜플, 산점도는 `[x,y]`, 기본 영역 지도는 region/value 행을 그대로 그린다. 원본값 모드는 집계와 섞을 수 없고 `GROUP BY`를 만들지 않는다. 표본 추출을 켜면 선택된 원본 행만 표시한다.
- 모든 실제 차트 실행은 고정 행 제한 없이 조건과 집계 결과 전체를 반환한다. 성능을 위해 결과를 줄일지는 사용자가 `sample`로 선택하며, 표본을 지정하지 않은 차트를 시스템이 임의로 자르지 않는다. [원본 데이터]와 관계 미리보기는 조회 도구이므로 최대 1,000행 제한을 유지한다.
- 포인트 지도(`geoscatter`)는 ① 숫자 경도·위도 컬럼과 ② SRID가 지정된 PostGIS `geometry/geography(Point, SRID)` 공간 컬럼을 모두 지원한다. 공간 컬럼은 서버가 `ST_Transform(...,4326)` 후 `ST_X/ST_Y`로 같은 `[경도,위도,(크기)]` 행 계약에 투영한다.
- 결과 영역은 **실행 결과**(집계)와 **원본 데이터**(조건 적용 raw, 최대 1,000행 스크롤) 탭으로 구성한다. 기준 관계를 선택한 직후에는 관계 preview를 표시한다. JOIN·WHERE 등 구성이 바뀐 원본 행은 [실행]과 함께 중복 요청하지 않고 [원본 데이터] 탭을 처음 열 때 지연 조회한다. 집계는 명시적 [실행]만 수행한다. 저장된 차트로 진입할 때는 쿼리를 자동 실행하지 않고 마지막 저장 캐시의 집계 rows와 option을 복원한다.
- 시리즈 나누기(breakout, `seriesBy`)는 선택적 두 번째 그룹 차원이다. 값이 없으면 계열 축/행을 노출하지 않고 단일 계열로 처리하며, 값이 있으면 서버가 `GROUP BY x, seriesBy` 결과를 피벗해 여러 계열로 조립한다(SQL 생성규칙 10장).
- SQL 모드(옵션 2, 고급, 2차 구현): SQL 직접 작성. 스키마 탐색기·자동 실행·에러 노출은 기존 설계대로.
- MVP: 노코드의 "생성된 SQL 보기"(읽기 전용)만 제공. 전환 규칙(노코드→SQL 단방향, SQL 수정 시 builder_config 폐기 경고)은 2차의 SQL 탭과 함께 활성화. Metabase와 동일한 모델.
- SQL 실행 엔진(검증·읽기전용 실행·타임아웃·미리보기 행 제한)은 백엔드 기반으로 MVP에 포함된다 — 노코드 생성 SQL이 이 엔진을 사용한다. 실제 차트 계산은 행 제한 없는 실행 경로를 사용한다. 2차에서 추가되는 것은 SQL 작성 UI뿐이다.
- 저장: `define_mode`('sql'|'builder') + `sql_query`(항상 저장) + `builder_config` JSONB(노코드 상태 복원용). builder 모드 저장 시 `sql_query`는 클라이언트 값을 신뢰하지 않고 서버가 `builder_config`에서 재생성·검증한 SQL로 저장한다.
- 저장 조건: 차트명 + 데이터소스·테이블·X축·Y축 1개 이상 + 검증 통과. 저장 시 서버가 SQL 재생성 후 1회 실행해 캐시를 시드하므로(7.7), 실행이 실패하면 저장도 실패로 처리한다(검증 400 동일 노출).
- 미저장 이탈 보호: 구성 변경 후 [←목록] 등으로 이탈 시 "저장되지 않은 변경이 있습니다" 확인 모달.
- 데이터소스 선택: 차트 생성의 첫 단계로 데이터소스를 선택한다. 이후 데이터소스 변경은 좌측 카탈로그의 탐색 범위를 바꾸며 기존 구성을 보존한다. 원본 또는 조인 선택 칸을 누르면 좌측 패널을 펼치고 검색에 포커스하며, 검색 위에 현재 대상(`원본 테이블 선택 중`/`N번째 조인 테이블 선택 중`)과 취소 동작을 표시한다. 새 조인은 관계를 임의로 선점하지 않고 사용자가 목록에서 고른 뒤 생성한다.
- 연결된 소스의 스키마 탐색 패널 제공(읽기 전용, `mc_` 관계·시스템 스키마 제외). 고객 DB의 `public` 외 사용자 스키마(예: `analytics`)에 있는 TABLE·VIEW·MATERIALIZED VIEW를 모두 노출하며, VIEW/물리화 뷰 배지와 물리화 뷰 갱신 상태를 표시한다. 식별자는 스키마 한정(`"schema"."name"`)으로 생성해 `search_path` 의존 없이 정확한 관계를 조회한다. 갱신되지 않은 물리화 뷰는 선택하지 못하게 한다. SQL 오류 응답에는 DB 원문·SQL·스키마 정보를 포함하지 않는다.
- 요청/응답 형식은 API 계약서를 따른다.
- 저장된 차트의 정식 편집 URL은 `/charts/{datasourceName}/{schema}/{relation}/{chartId}`다. 사람이 주소만 보고 소스를 알 수 있도록 사용자별 고유 데이터소스 이름을 사용하며 한글·공백은 URL 인코딩한다. 저장·실행은 계속 숫자 `datasourceId`를 사용한다. 모든 저장 차트는 기준 관계를 가지며 원시 SQL 차트도 URL 문맥용 `builder_config.table`을 저장한다. 신규 초안은 `/charts/new`를 사용하고 `new`는 데이터소스 예약 이름이다.
- 차트 범위의 각 계층은 같은 목록 UX를 쓴다. `/charts/{datasourceName}`은 해당 소스를, `/charts/{datasourceName}/{schema}`는 해당 스키마를, `/charts/{datasourceName}/{schema}/{relation}`은 해당 관계를 기준 또는 조인으로 참조하는 차트를 기본 화면에서 보여주며 검색·종류·정렬·페이지네이션을 공통 제공한다. 메타데이터 탐색은 각각 `?view=schema`(스키마), `?view=relations`(TABLE·View·Materialized View), `?view=columns`(컬럼)로 명시적으로 진입한다. 스키마 관계 목록은 대규모 카탈로그에서도 이름 검색을 제공한다. 이름 수정 후에는 새 이름이 정식 URL이 되며 구 이름 주소는 유지하지 않는다.

### 7.4 로그인 세션·임베드 키

- 임베드 키는 `(userId, chartId)`에 서버측으로 묶이며, 원문은 발급 성공 응답에서만 한 번 표시한다.
- 임베드 코드: `<div data-embed-key="cek1_...">` + `<script src=".../sdk.js" data-api-base="...">`. S3가 생성한 HTML은 별도 초기화 호출 없이 그대로 붙여 넣어 동작해야 한다.
- 검증: 키 구문·HMAC 서명 + 만료 + DB의 is_active(회수) + 사용자 활성 상태. 서빙 차트는 키 바인딩에서만 결정한다.
- 로그인은 PostgreSQL 저장 세션 + HttpOnly 쿠키를 사용한다. 공개 회원가입은 아이디·비밀번호·비밀번호 확인만 받으며 이메일은 받지 않는다.
- 레거시 사용자 JWT 발급·검증 API와 화면은 제거한다. `mc_user_token` 이력 테이블만 보존 기간 확정 전까지 유지한다.
- 일반 사용자는 자신의 차트에서만 임베드 키를 발급·재발급·회수한다. 관리자는 타 사용자의 키 원문이나 발급·회수 권한을 갖지 않는다.
- MVP에서 만료는 길게 설정하고 회수로 관리한다.

### 7.5 화면 목록

전체 화면 및 상태 정의는 화면설계서를 참조한다. 사용자 콘솔은 로그인·회원가입, S1 목록, S2 편집, S3 임베드 코드, S5 데이터소스 관리로 구성한다. 관리자에게만 사용자 관리와 전체 차트 읽기 전용 화면을 추가한다. 임베드 런타임은 S4 렌더다.

### 7.6 MVP 제외 항목 (명시적)

- SQL 직접 작성 UI (2차 — SQL 실행 엔진 자체는 MVP 포함)
- 조직 전환/조직 관리 UI, 외부 토큰 배포 보안. 본 서비스는 개인 사용자 단위로 스코프한다.
- DB 관리 기능 (테이블 생성/수정/데이터 편집). 본 솔루션은 조회 전용 뷰어이며 DB 편집은 하지 않는다.

### 7.7 결과 스냅샷·갱신 모드 (대용량 대응, 코어)

기업 데이터는 매우 크다. 집계는 DB 안에서 실행되지만(GROUP BY pushdown), 임베드 차트가 사내 페이지에 깔리면 **페이지뷰마다 무거운 집계가 운영 DB를 때린다.** 수동 모드는 저장 결과 스냅샷을 재사용하고, 최신성이 필요한 차트만 live를 선택한다.

- 차트별 갱신 모드 2종 (`mc_chart.refresh_mode`):

| 모드 | 동작 | 용도 |
|---|---|---|
| `manual` (기본) | 저장/[지금 갱신] 결과 유지. 단일 소스의 누락·손상 스냅샷은 self-heal | 일반 차트, 무거운 통계, 일·주 단위 리포트 |
| `live` | 매 요청 실행 | 소규모 테이블, 최신성 필수 |

- 캐시 저장소: 메타 DB `mc_chart_cache` (JSONB). 차트 결과 전체를 보존하므로 결과 크기는 차트 정의에 따라 커질 수 있다. 운영자가 큰 차트에 표본·조건·집계 뷰를 적용할 수 있도록 안내하되 시스템이 결과를 임의 절단하지 않는다.
- 동작 규칙: ① S2 저장 검증에서 얻은 실행 결과를 재조회 없이 스냅샷으로 시드(첫 임베드도 즉시 응답) ② manual은 호환 스냅샷을 계속 반환하고 [지금 갱신]에서 교체 ③ live는 별도 Spring 빈의 만료형 lease로 같은 차트의 동시 계산을 줄이며 새 결과만 반환한다. 현재는 예약 작업·백그라운드 큐가 아니다.
- 스냅샷 실패 상태: 성공 결과는 유지하면서 `last_error/last_error_at`만 갱신한다. 성공 결과가 한 번도 없는 최초 시드 실패는 `result/computed_at`이 NULL인 error-only 행으로 기록한다. 차트 정의 버전이 다른 결과는 절대 서빙하지 않는다.
- 임베드 응답에 `computedAt`을 포함한다. `manual`은 S4 차트 하단에 "데이터 기준 {시각}" 캡션(옵션, 기본 켬)으로 정적 데이터임을 표시하고, `live`는 항상 최신 조회이므로 캡션을 표시하지 않는다.
- 무거운 쿼리의 근본 해결은 고객 DB 측 집계 테이블/뷰(ETL)이며, S5 등록 화면 안내문으로 가이드한다.
- **표본추출(보완 수단, MVP 포함):** 자동 또는 1,000~50,000행 직접 지정 방식을 제공한다. 정확 결과와 표본 결과를 명확히 구분하고 집계별 의미·경고를 Admin·cache·API·SDK까지 보존한다. 알고리즘과 통계적 의미는 [표본추출 계약](표본추출_계약.md)이 정본이다.
- **통계적 표현 원칙:** 집계별 정확/추정 의미, 신뢰구간 적용 조건과 경고 문구는 [표본추출 계약](표본추출_계약.md)을 그대로 사용한다.
- 구현 단계: 현재는 갱신 모드 2종, 수동 저장 결과 재사용, live lease 기반 single-flight, 수동 갱신, 실패 상태와 `computedAt`, sampling v9을 제공한다. 후속은 명시적인 전체 추정값, SYSTEM 분산 추정·반복 표본, 비동기·스케줄 갱신이다. 표본 후속 조건은 [표본추출 계약](표본추출_계약.md)에서 관리한다.

## 8. 비기능 요구사항 / 보안

### 8.1 SQL 실행 통제 (최대 리스크)

관리자가 직접 작성한 SQL이 DB에서 실행되는 구조이므로 다음을 필수로 적용한다.

- 차트 쿼리는 읽기 전용(read-only) DB 계정으로만 실행한다.
- SELECT 외 구문 차단(파서 검증).
- 쿼리 실행 타임아웃 및 결과 행 수 제한.

### 8.2 인증·임베드 키 보안

- 로그인 자격은 JWT/localStorage가 아니라 서버 저장 세션과 HttpOnly 쿠키를 사용한다. 모든 변경 요청은 CSRF 토큰을 요구한다.
- 임베드 키는 `(사용자, 차트)`에 귀속되며 HMAC 서명·만료·회수·사용자 활성 상태를 모두 검증한다.
- `cek1_*` 원문은 DB에 저장하지 않고 행 ID에서 재파생하며, 발급 응답에서 한 번만 표시한다.
- SDK는 `credentials: 'omit'`으로 로그인 쿠키를 전송하지 않고 Bearer 임베드 키만 사용한다.

### 8.3 Type B 마이그레이션 안전성

- Flyway 마이그레이션은 `mc_` 접두사 테이블 범위 밖을 절대 변경하지 않는다.

## 9. 데이터 저장 요구사항

메타데이터는 `mc_` 접두사의 PostgreSQL 테이블에 저장하고, 고객 업무 데이터는 등록된 외부 데이터소스에 그대로 둔다. Backend와 Flyway는 고객 DB 객체를 생성·수정하지 않는다.

저장 전략은 다음과 같다.

- 조회·정렬·필터·관계·무결성 대상은 정규화 컬럼에 저장한다.
- 계속 확장되는 차트 옵션과 노코드 정의는 JSONB에 저장한다.
- 실행 결과와 오류 상태는 정의와 분리된 cache 계층에 저장한다.
- 다중 데이터소스 참조, 표시 이름, 표본 row cache와 lease는 독립 테이블로 관리한다.
- `updated_at`, 사용자·데이터소스 소유권, 정의 버전과 cache version은 DB 제약 및 트랜잭션으로 보호한다.

현재 전체 테이블·인덱스·화면 저장 위치는 [데이터모델·화면 저장 매핑](데이터모델_화면저장_매핑.md), 실제 DDL은 Flyway 마이그레이션이 정본이다. 옵션 JSON 계약은 [차트옵션 변환 규칙](차트옵션_변환_규칙.md), `builder_config`는 [노코드 질의생성 규칙](노코드_질의생성_규칙.md), 세션·임베드 키와 API 구조는 [인터페이스 계약서](인터페이스_계약서.md)를 따른다.
## 10. 개발 우선순위 (단독 개발 기준)

**MVP**
1. 코어 파이프라인: SQL 실행 엔진(검증·읽기전용·타임아웃·행제한) + 차트별 임베드 키 → ECharts JSON → SDK가 div 렌더
2. 공개 회원가입 + PostgreSQL 세션 로그인 + exact owner 격리 + 차트별 임베드 키 발급/검증/만료/회수
3. 시각화 옵션: 막대/선/원형/산점도/상자수염/행렬 히트맵/영역 지도/포인트 지도(8종), 색(테마 선택/선택 대상에 테마색 적용/직접 지정/차트 요소 선택 삭제·모두 삭제), 축, 정렬, 라벨, 범례, 논리 크기·글꼴 + 크기별 미리보기
4. 사용자 콘솔: 목록(S1) + 노코드 빌더(S2, SQL 생성기) + 임베드 코드(S3) + 데이터소스 관리(S5)
5. 다중 데이터소스: 동적 커넥션 풀 + 자격증명 암호화
6. 결과 스냅샷: 갱신 모드 2종(manual/live) + 저장 시 시드 + live single-flight + [지금 갱신] + 마지막 계산 시각 (7.7 — 대용량 대응 코어)
7. 관리자: 사용자 역할·상태 관리 + 전체 차트 읽기 전용 조회 + 감사 로그

**2차**
8. SQL 에디터 모드(S2 옵션 2): 에디터 UI + 스키마 탐색기 + DB 에러 노출 + 노코드→SQL 전환 규칙
9. 캐시 운영 고도화: 스케줄 갱신, 실행 이력·관측 지표, 장시간 갱신 queue

**후속**
10. SSO 교체, 쿼리 파라미터({{}}), 대시보드, 알림/스케줄, 캐시 스케줄 갱신 (시리즈 분할과 날짜 버킷팅은 구현 완료)

## 11. 화면 요구사항

관리 콘솔은 로그인·회원가입, 차트 목록(S1), 차트 편집(S2), 임베드 코드(S3), 임베드 런타임(S4), 데이터소스 관리(S5), 관리자 사용자·전체 차트 화면으로 구성한다.

제품 범위와 우선순위는 이 문서가 소유하고, 프레임·치수·컴포넌트·빈 상태·로딩·오류·저장 전 상태·화면 흐름은 [화면설계서](화면설계서.md)가 정본이다. 화면 변경은 PRD의 기능 범위를 먼저 확인한 뒤 화면설계서를 갱신한다.
## 12. 향후 과제 (Post-MVP)

- 개인 계정 SSO(SAML/OAuth) 로그인 — 현재 서버 세션 경계를 유지하면서 회사 통합로그인 IdP로 자격 확인만 교체
- 차트 종류 확장(레이더·캘린더·경로 지도 등) 및 시각화 옵션 심화
- 임베드 키 자동 회전·배포 파이프라인 — 현재 차트별 키 격리와 즉시 회수 불변식 유지
- SDK 명령형 API 병행: `ChartSDK.render(el, { embedKey })` — SPA(React/Next)처럼 DOM 스캔 타이밍이 어긋나는 환경 대응 (선언형 div 스캔과 공존)
- 차트 미리보기 썸네일 캐싱 고도화
- 대시보드(여러 차트 묶음) 기능
