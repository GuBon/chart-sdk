# 변경사항 개선 설계 — 임베드 키·에디터 안정성·오류 진단

**상태:** 구현 전 확정 설계  
**작성일:** 2026-08-14  
**대상:** V11 임베드 키 전환과 동시 변경된 Admin·SDK·Server 경로

## 1. 목적

이번 설계는 다음 문제를 한 번에 정리한다.

1. 임베드 키 관리 API가 서빙 API의 소유자 불변식을 공유하지 않고, 목록에서 재사용 가능한 Bearer 원문을 노출한다.
2. 키 회수 API의 실제 상태코드가 Admin 클라이언트·문서·MSW와 달라 성공 응답이 클라이언트 오류로 바뀐다.
3. 키 발급 성공 뒤 목록 재조회만 실패하면 이미 회수된 이전 키가 UI에 남는다.
4. 같은 `(user, chart)` 키를 동시에 발급하면 부분 유니크 인덱스 충돌이 500으로 노출된다.
5. `WHERE IN` 입력의 UI 정체성이 길이 기반 ref에 의존해 외부 draft 교체와 Concurrent Rendering에 안전하지 않다.
6. 미저장 이탈 가드가 취소할 수 없는 브라우저 history traverse까지 막을 수 있다고 가정한다.
7. SQL 오류를 임베드와 Admin에 똑같이 마스킹해 작성자 진단성이 사라지고, 로그도 wrapper throw 지점을 잃는다.
8. SDK·MSW·수동 호스트·레거시 토큰 화면·문서가 새 계약과 부분적으로 어긋난다.

이 문서는 단순한 리팩터링 제안이 아니라 구현 순서, API 계약, 상태 전이, 실패 처리, 테스트와 배포 게이트를 정의한다.

## 2. 설계 원칙과 비목표

### 2.1 확정 원칙

- **대상 사용자 ID와 호출자 권한을 분리한다.** 요청 본문의 `userId`는 키 바인딩 대상일 뿐 인증 주체가 아니다.
- **임베드 키는 발급 성공 응답에서 한 번만 노출한다.** 목록 API는 키 원문을 재생성하지 않는다.
- **도메인 스코프와 인증 스코프를 분리한다.** 차트·사용자 바인딩 검증은 서비스가 담당하고, 호출자 신원은 `CurrentUserProvider`가 담당한다.
- **DB 제약은 최종 방어선이며 정상 경쟁 제어 수단은 아니다.** 발급 경쟁은 명시적 잠금과 409로 처리한다.
- **UI 정체성은 저장 모델에 섞지 않는다.** `WhereCond`의 JSON 계약에는 UI ID를 추가하지 않는다.
- **브라우저가 금지한 traverse 취소에 데이터 안전을 의존하지 않는다.** 제어 가능한 이동은 확인 모달, 제어 불가능한 이동은 세션 초안 복원으로 보호한다.
- **임베드 오류는 최소 정보, Admin 오류는 정제된 진단 정보**를 제공한다. 어느 경로에도 JDBC 원문 전체를 그대로 내보내지 않는다.
- **Mock은 백엔드의 대체 구현이다.** 상태코드·만료·회수 의미까지 서버와 같아야 한다.

### 2.2 이번 범위의 비목표

- SSO·로그인 화면·세션 발급 자체를 이번 작업에서 구현하지 않는다.
- 저장된 논리 설계 크기로 SDK 호스트 DOM 크기를 강제하지 않는다.
- 사용자 토큰 JWT를 새 임베드 인증으로 되살리지 않는다.
- DB 예외 원문 전체를 브라우저에 복원하지 않는다.

## 3. 목표 구조

```text
Admin 관리 요청
  -> Admin 접근 경계
  -> CurrentUserProvider(호출자)
  -> EmbedKeyService(차트 소유/레거시 범위 + 대상 사용자 바인딩)
  -> mc_embed_key

SDK 임베드 요청
  -> EmbedKeyInterceptor
  -> cek1 서명 + 활성/만료 검증
  -> 키에 저장된 chart_id만 사용
  -> 일반화된 공개 오류
```

관리 경로와 서빙 경로는 자격 증명과 응답 정책을 공유하지 않는다. `EmbedKeyPrincipal`은 임베드 데이터 서빙에만, `CurrentUserProvider`는 관리 API에만 사용한다.

## 4. 임베드 키 관리 API

### 4.1 호출자 스코프

`EmbedKeyService`에 `CurrentUserProvider`를 주입하고 관리 메서드마다 다음 규칙을 적용한다.

| 호출자 상태 | 관리 가능한 차트 |
|---|---|
| 인증 사용자 ID 있음 | `owner_id = currentUserId OR owner_id IS NULL` |
| 인증 사용자 ID 없음 + 로컬/테스트 허용 플래그 | `owner_id IS NULL`만 |
| 인증 사용자 ID 없음 + 허용 플래그 꺼짐 | `401 ADMIN_AUTH_REQUIRED` |

새 설정은 다음과 같다.

```yaml
chartsdk:
  admin:
    allow-unauthenticated: ${CHARTSDK_ALLOW_UNAUTHENTICATED_ADMIN:false}
```

- 기본값은 `false`다.
- 로컬 개발과 E2E만 명시적으로 `true`를 사용한다.
- `true`는 권한 검사를 생략한다는 뜻이 아니라, `owner_id IS NULL`인 레거시/개발 차트만 관리하도록 허용한다.
- 운영에서 Spring API를 직접 외부에 노출한 채 이 값을 켜는 배포는 금지한다.

`AdminAccessInterceptor`를 추가해 임베드 데이터·정적 자산·actuator를 제외한 Admin API 전체에
이 설정을 적용한다. 현재 사용자 ID가 없고 플래그도 꺼져 있으면 서비스 메서드에 도달하기 전에
`401 ADMIN_AUTH_REQUIRED`로 종료한다. 이는 SSO 구현이 아니라, 인증이 연결되지 않은 운영 배포를
실수로 공개하지 못하게 하는 fail-closed 게이트다. 플래그를 켠 내부 개발 환경에서도 키 서비스의
도메인 스코프는 `owner_id IS NULL`로 제한한다.

`issue(chartId, targetUserId, days)`의 `targetUserId`는 계속 키 바인딩 대상을 의미한다.

- 소유자가 있는 차트: `targetUserId == chart.ownerId`여야 한다.
- `owner_id IS NULL` 레거시 차트: 활성 사용자 중 하나를 대상으로 지정할 수 있다.
- 호출자 스코프 검증은 위 조건보다 먼저 또는 같은 잠금 쿼리 안에서 수행한다.

### 4.2 응답 DTO 분리

현재의 `Map<String, Object>` 대신 명시적 DTO를 사용한다.

```java
enum EmbedKeyStatus { ACTIVE, EXPIRED, REVOKED }

record EmbedKeySummary(
    long id,
    long userId,
    long chartId,
    Instant expiresAt,
    EmbedKeyStatus status,
    Instant createdAt,
    Instant revokedAt,
    String revokedReason
) {}

record IssuedEmbedKey(
    long id,
    long userId,
    long chartId,
    Instant expiresAt,
    EmbedKeyStatus status,
    Instant createdAt,
    String embedKey
) {}
```

목록 응답에는 `embedKey` 필드가 존재하지 않는다. `isActive`는 전환 기간에만 호환 필드로 유지하고 Admin 전환이 끝나면 제거한다.

### 4.3 엔드포인트 계약

#### 목록

```http
GET /api/v1/charts/{chartId}/embed-keys
200 { "embedKeys": [EmbedKeySummary...] }
```

- 호출자가 관리할 수 없는 차트와 없는 차트는 모두 `404 CHART_NOT_FOUND`로 통일한다.
- 활성·만료·회수 이력은 반환하지만 Bearer 원문은 반환하지 않는다.
- 목록 조회는 차트 스코프를 통과한 뒤 `chart_id`로 조회한다.

#### 발급·재발급

```http
POST /api/v1/charts/{chartId}/embed-keys
Content-Type: application/json

{ "userId": 7, "expiresInDays": 365 }

200 IssuedEmbedKey
409 EMBED_KEY_ISSUE_IN_PROGRESS
```

- `embedKey` 원문은 이 응답에서만 한 번 노출한다.
- 재발급은 파괴적 회전이므로 Admin에서 확인 단계를 거친다.
- 응답 성공 뒤 별도 GET 성공 여부가 발급 성공 여부를 바꾸지 않는다.

#### 회수

```http
DELETE /api/v1/embed-keys/{keyId}
204 No Content
```

- `@ResponseStatus(HttpStatus.NO_CONTENT)`를 선언한다.
- 키를 차트와 조인해 호출자가 해당 차트를 관리할 수 있는지 검증한다.
- 없거나 이미 회수됐거나 관리 범위 밖이면 `404 EMBED_KEY_NOT_FOUND`다.
- 성공 본문은 절대 쓰지 않는다.

#### 빈 성공 응답 공통 규칙

이번 점검 범위에서 `EmbedKeyController`뿐 아니라 `UserTokenController.revoke`와
`DatasourceController.delete`도 `void`를 반환하면서 204를 선언하지 않는다는 것이 확인됐다.
본문 없는 성공 mutation은 모두 204로 통일한다.

- `DELETE /charts/{id}` → 204
- `DELETE /datasources/{id}` → 204
- `PUT /schema/display-name` → 204
- `DELETE /tokens/{tokenId}` → 204
- `DELETE /embed-keys/{keyId}` → 204

서버 계약을 바로잡는 것과 별개로 Admin `request()`도 빈 본문에 방어적으로 동작해야 한다.
성공 응답은 `res.text()`로 한 번만 읽고, 204·205 또는 빈 문자열이면 `undefined`를 반환하며,
내용이 있을 때만 JSON.parse를 수행한다. 이 백스톱은 서버 상태코드 회귀가 사용자 행동 실패로
증폭되는 것을 막지만, 서버가 잘못된 200을 반환해도 계약 테스트는 계속 실패해야 한다.

### 4.4 동시 발급

부분 유니크 인덱스 `uq_mc_embed_key_active`는 유지한다. 서비스는 다음 순서로 처리한다.

1. 활성 사용자 존재 확인.
2. 차트 소유자·호출자 범위를 검증하면서 차트 행을 `FOR UPDATE NOWAIT`로 잠근다.
3. 잠금 실패(SQLSTATE `55P03`)는 `409 EMBED_KEY_ISSUE_IN_PROGRESS`로 변환한다.
4. 기존 활성 키를 `ROTATED`로 회수한다.
5. 새 키를 삽입한다.
6. 발급 DTO와 원문을 반환하고 커밋한다.

두 요청을 모두 순차 성공시키면 첫 요청이 받은 키가 즉시 두 번째 요청에 의해 무효화될 수 있다. 따라서 기다렸다가 둘 다 성공시키지 않고, 경쟁 요청 하나를 409로 거절한다. Admin은 이 오류에서 자동 재발급하지 않고 목록만 다시 읽는다.

유니크 위반 `23505`도 최종 백스톱으로 같은 409에 매핑하되, 정상 경로에서는 발생하지 않아야 한다. 메트릭 `chartsdk.embed_key.issue_conflict`를 증가시켜 잠금 설계 누락을 감시한다.

### 4.5 사용자 비활성화

현재 검증 경로가 `mc_user.is_active=false`를 즉시 `TOKEN_REVOKED`로 처리하므로 기능상 안전하다. `USER_DISABLED`는 감사 이력 요구를 위해 예약한다.

- 사용자 비활성화 API가 생길 때 같은 트랜잭션에서 활성 임베드 키를 `USER_DISABLED`로 일괄 회수한다.
- 그 전까지 V11 CHECK의 `USER_DISABLED` 값은 예약값으로 문서화한다.
- 사용되지 않는다는 이유만으로 이번 마이그레이션에서 제거하지 않는다.

## 5. Admin 임베드 모달 상태 모델

### 5.1 상태 분리

```ts
type EmbedModalState = {
  summaries: EmbedKeySummary[];
  revealed: IssuedEmbedKey | null; // 현재 모달 수명에서만 보존
  selectedUserId: number | null;
  load: 'loading' | 'ready' | 'failed';
  mutation: 'idle' | 'issuing' | 'revoking';
  mutationError: string | null;
  refreshWarning: string | null;
};
```

`revealed.embedKey`는 React 메모리에만 있고 localStorage·sessionStorage·로그에 저장하지 않는다. 사용자 변경, 모달 닫기, 회수 성공 시 지운다.

### 5.2 발급 성공 경로

1. `POST issue` 응답을 받는다.
2. 즉시 `revealed`에 저장하고 스니펫을 표시한다.
3. `summaries`는 발급 응답으로 낙관 갱신한다. 같은 `(chart,user)`의 이전 ACTIVE는 REVOKED로 바꾸고 새 summary를 추가한다.
4. 선택적으로 목록을 백그라운드 재조회한다.
5. 재조회만 실패하면 스니펫을 유지하고 `refreshWarning`만 표시한다.

발급 성공과 후속 조회 실패를 같은 `catch`에서 처리하지 않는다.

### 5.3 재진입과 회수 UX

- 이미 ACTIVE 키가 있지만 이번 모달에서 발급한 원문이 없으면 “활성 키가 있습니다. 보안상 기존 원문은 다시 표시하지 않습니다.”를 표시한다.
- 코드를 다시 얻으려면 “키 재발급” 확인 모달을 거친다.
- 확인 문구는 기존 임베드가 즉시 중단된다는 사실을 명시한다.
- “회수”는 별도 확인 후 DELETE를 호출한다.
- 회수 성공 시 summary를 REVOKED로 바꾸고 같은 키의 `revealed`를 제거한다.
- 복사 성공 상태는 사용자 변경·재발급·회수 때 초기화한다.

### 5.4 레거시 사용자 토큰 화면

사용자 토큰은 더 이상 임베드에 사용되지 않으므로 현재 문구를 제거한다.

- 화면 제목: `사용자·레거시 토큰 관리`
- 설명: “사용자 토큰은 새 임베드 코드에서 사용되지 않습니다. 새 임베드는 차트별 임베드 키를 사용합니다.”
- 빈 상태에서 “토큰을 발급해 차트를 임베드하세요” 문구를 사용하지 않는다.
- 임베드 모달의 사용자 없음 링크 문구는 “사용자 관리로 이동”으로 바꾼다.
- 로그인 트랙 완료 후 사용자 관리와 레거시 토큰 관리를 분리하고 토큰 API 제거 여부를 결정한다.

## 6. `WHERE` 행 UI 정체성

### 6.1 저장 모델에 ID를 넣지 않는다

`WhereCond`는 API·저장 계약이므로 `uid`, `_id` 같은 필드를 추가하지 않는다. UI ID는 `NocodeBuilder` 수명 안에서만 관리한다.

```ts
type WhereRowUi = {
  id: string;
  condition: WhereCond;
};
```

다만 전체 `BuilderConfig`를 이 형태로 바꾸면 변환 함수 영향이 크므로, 실제 구현은 행 ID 배열과 외부 교체 revision을 조합한다.

### 6.2 확정 구현

- `ChartEditor`에 `builderRevision` 숫자 상태를 둔다.
- 서버 hydrate, 저장 상태 복원, 기준 테이블 교체, 차트 유형 draft 복원, 지도 variant draft 복원처럼 builder를 통째로 교체할 때 `builderRevision`을 증가시킨다.
- 일반 필드 편집인 `applyBuilderChange`에서는 revision을 유지한다.
- `NocodeBuilder`는 `builderRevision`을 prop으로 받고, revision 변경 시 reducer의 행 ID를 전부 다시 생성한다.
- 추가·삭제는 reducer action으로 `config.where` 변경과 같은 이벤트 안에서 ID를 갱신한다.
- ID는 `crypto.randomUUID()` 또는 컴포넌트 로컬 증가값으로 이벤트 핸들러에서 생성한다. 렌더 본문에서는 ref나 state를 변경하지 않는다.

```ts
type WhereIdentityAction =
  | { type: 'reset'; count: number; revision: number }
  | { type: 'append' }
  | { type: 'remove'; index: number };
```

키는 `${builderRevision}:${rowId}`를 사용한다.

### 6.3 외부 교체 단일 진입점

`ChartEditor`에 두 함수를 둔다.

```ts
setBuilderFromEdit(next);     // 행 ID 보존
replaceBuilderSnapshot(next); // revision 증가, 행 ID 재발급
```

기존 `setBuilder()` 직접 호출을 분류해 이 두 함수 중 하나만 사용한다. 필드명 snapshot 보강처럼 조건 의미를 바꾸지 않는 내부 정규화는 edit 경로로 처리한다.

### 6.4 회귀 테스트

- 두 IN 행 중 첫 행 삭제 후 두 번째 행의 미완성 `raw`가 유지된다.
- 길이가 같은 다른 snapshot으로 교체하면 모든 `WhereInInput`이 리마운트된다.
- 이전 raw가 `"서울,"`, 새 canonical이 `"서울"`이어도 새 snapshot에서는 `"서울"`로 표시된다.
- add/remove가 React Strict Mode 이중 렌더에서도 ID를 중복 생성하거나 다른 행에 전달하지 않는다.

## 7. 미저장 이탈 보호

### 7.1 보장 수준

Navigation API의 `traverse`는 `preventDefault()`로 취소할 수 없다. 따라서 다음처럼 보장을 나눈다.

| 이동 | UX 보장 | 데이터 보장 |
|---|---|---|
| 에디터 내부 버튼·GuardedLink | 커스텀 확인 모달 | 세션 초안 |
| 새로고침·탭 닫기·외부 URL | 브라우저 beforeunload | 세션 초안 |
| 브라우저 Back/Forward | 사전 모달을 보장하지 않음 | 세션 초안 복원 |
| Navigation API 미지원 브라우저 | 제어 이동은 requestLeave | 세션 초안 복원 |

취소 불가능한 이동을 억지로 history 조작해 가두는 sentinel 방식은 히스토리 오염·연속 Back·스크롤 복원 문제 때문에 이번 설계에서는 사용하지 않는다.

### 7.2 에디터 세션 초안

`sessionStorage`에 다음 구조를 300ms debounce로 저장한다.

```ts
type EditorSessionDraft = {
  schemaVersion: 1;
  chartKey: `chart:${number}` | 'chart:new';
  baseVersion: number | null;
  savedAt: string;
  definition: EditorDefinitionSnapshot;
};
```

- 비밀번호·임베드 키·토큰은 포함하지 않는다.
- 탭 단위 복구가 목적이므로 localStorage가 아니라 sessionStorage를 사용한다.
- 저장소 접근 실패는 편집을 막지 않고 로그 없는 로컬 경고 상태로만 처리한다.

복원 규칙:

1. 서버 정의와 저장 baseline을 먼저 로드한다.
2. 같은 `chartKey` 초안이 없으면 정상 진입한다.
3. `baseVersion`이 서버 version과 같으면 “이전 편집 복원/버리기”를 묻는다.
4. version이 다르면 자동 덮어쓰지 않고 “서버 버전이 변경됨”을 표시한 뒤 초안을 새 변경으로 복원할지 선택하게 한다.
5. 저장 성공·명시적 “저장 안 함”·초안 버리기에서 해당 키를 삭제한다.
6. 새 차트 저장 성공 시 `chart:new` 초안을 지우고 새 chart ID baseline으로 전환한다.

### 7.3 `useLeaveGuard` 단순화

- `beforeunload`는 유지한다.
- `requestLeave`와 `confirmLeave`는 제어 가능한 내부 이동만 담당한다.
- Navigation API listener는 지원 브라우저에서 우발적인 same-document `push`를 보조적으로 잡되 `traverse`를 막는다고 주장하지 않는다.
- 에디터 라우트에는 현재 AppBar가 없지만, 향후 링크 추가 시 `GuardedLink` 또는 leave context를 사용한다.
- “브라우저 뒤로가기를 막았다”는 주석과 `historyKey/traverseTo` 코드는 제거한다.

### 7.4 E2E

- 미저장 상태에서 목록 버튼 → 모달 → 취소/버리기/저장 후 이동.
- 미저장 상태에서 `page.goBack()` → 이전 화면 이동 → 에디터 재진입 → 초안 복원 안내.
- Navigation API를 `undefined`로 만든 브라우저 컨텍스트에서 내부 버튼 가드와 초안 복원.
- 저장 성공 뒤 재진입 시 오래된 초안이 나타나지 않음.
- 서버 version 변경 뒤 초안이 자동 적용되지 않음.

## 8. SQL 오류 진단과 로깅

### 8.1 응답 audience

요청을 두 audience로 구분한다.

- `EMBED`: `/api/v1/charts/data`
- `ADMIN`: 그 외 관리·편집 API

요청 필터가 `chartsdk.requestAudience` 속성을 설정한다. 이 값은 인증을 대신하지 않고 오류 노출 정책만 선택한다.

### 8.2 예외 구조

```java
record SqlDiagnostic(
    String sqlState,
    String category,
    Integer position,
    String safeMessage
) {}
```

`ApiException`은 공개 `message`, 내부 `cause`, 선택적 `SqlDiagnostic`을 분리해 가진다.

- `EMBED` 응답: code와 일반화된 message만 반환.
- `ADMIN` 응답: 위 필드 중 존재하는 값만 `error.diagnostic`에 추가.
- JDBC URL·호스트·DB 사용자·전체 SQL·전체 JDBC message·stack trace는 어느 응답에도 넣지 않는다.

우선 지원하는 SQLSTATE:

| SQLSTATE | category | Admin safeMessage |
|---|---|---|
| `42703` | `UNDEFINED_COLUMN` | 참조한 컬럼을 찾을 수 없습니다. |
| `42P01` | `UNDEFINED_RELATION` | 참조한 테이블 또는 뷰를 찾을 수 없습니다. |
| `42501` | `INSUFFICIENT_PRIVILEGE` | 데이터소스 계정에 조회 권한이 없습니다. |
| `42804`/`42883` | `TYPE_MISMATCH` | 컬럼 타입 또는 연산자 조합이 맞지 않습니다. |
| `57014` | `QUERY_CANCELLED` | 쿼리가 제한 시간 안에 완료되지 않았습니다. |
| 기타 | `QUERY_FAILED` | 쿼리 실행 중 오류가 발생했습니다. |

컬럼명 추출은 PostgreSQL의 구조화된 server error field가 있을 때만 사용한다. message 문자열 정규식 파싱으로 임의 원문을 복원하지 않는다. 구조화된 이름을 제공할 수 없으면 category와 position만 준다.

### 8.3 로그

[ApiExceptionHandler]의 cause 보유 예외는 wrapper 자체를 넘긴다.

```java
log.warn("Handled {} ({})", e.code(), e.status(), e);
```

이렇게 해야 `ApiException`을 던진 서비스 위치와 JDBC cause chain이 함께 남는다. 로그 메시지에는 토큰·임베드 키·전체 SQL을 별도 인자로 추가하지 않는다. requestId는 기존 MDC를 사용한다.

### 8.4 Admin UI

`ApiError`에 optional `diagnostic`을 추가하고 ChartEditor 실행 오류에서 다음 순서로 표시한다.

1. 사용자용 message
2. category별 행동 지침
3. SQLSTATE와 position
4. 5xx일 때 requestId

임베드 SDK는 diagnostic을 읽거나 표시하지 않는다.

### 8.5 계약서 정리

`SQL_ERROR (DB 에러 메시지 동봉)` 문구는 폐기한다. 대신 “Admin에는 정제된 diagnostic 선택 제공, 임베드에는 일반 문구”로 기록한다.

### 8.6 cause chain 순회

`DatasourceService.sqlState()`가 최상위 예외를 건너뛴다는 진단은 사실이 아니다. 현재 구현은
최상위부터 검사한다. 다만 `t.getCause() != t`는 Java의 정상적인 cause 설정에서는 실효가 없고,
두 객체 이상으로 만들어진 비정상 순환도 차단하지 못한다.

공통 `ThrowableCauseWalker`를 두고 identity 기반 방문 집합과 최대 깊이 32를 적용한다. SQLSTATE
추출기와 Admin diagnostic 변환기가 이 유틸리티를 함께 사용한다. 테스트는 최상위 SQLException,
중첩 SQLException, cause 없음, 인위적인 다중 객체 순환을 포함한다.

## 9. SDK 요청 시간 예산

현재 150초를 데이터와 지도에 각각 적용하면 최악의 로딩 시간이 데이터 150초 + 지도 150초 + 폰트 최대 10초가 된다. 계약을 단계별로 분리한다.

```ts
DATA_REQUEST_TIMEOUT_MS = 150_000;
MAP_ASSET_TIMEOUT_MS = 15_000;
FONT_LOAD_TIMEOUT_MS = 5_000; // 단계별 기존 값, 총 최대 10초
```

- 기존 `window.CHARTSDK_TIMEOUT_MS`와 `script[data-timeout-ms]`는 데이터 요청 timeout으로 유지해 하위 호환한다.
- 지도는 `CHARTSDK_MAP_TIMEOUT_MS`와 `data-map-timeout-ms`로 별도 재정의한다.
- 한 차트 전체 기본 대기 상한은 약 175초다.
- 지도 실패는 차트 전체 오류로 표시하되 다음 render에서 재시도한다.
- 폰트 실패·timeout은 기존처럼 시스템 폰트로 계속 렌더한다.

테스트는 데이터 150초 뒤 지도 15초만 추가되는지, 지도 in-flight 실패 캐시가 제거되는지, override 우선순위를 검증한다.

## 10. MSW·수동 호스트·문서 패리티

### 10.1 MSW

- 키 발급 상태를 서버와 같은 200으로 변경한다.
- 목록 응답에서 `embedKey`를 제거한다.
- 만료 여부를 응답 시각에 계산해 `status=EXPIRED`로 반환한다.
- 없는 키 또는 이미 회수된 키 DELETE는 404 `EMBED_KEY_NOT_FOUND`다.
- 발급 경쟁 테스트를 위해 동일 pair 요청 중 하나에 409를 주입할 수 있는 시나리오 핸들러를 둔다.
- `Math.random()` 키 대신 테스트별 결정적 sequence를 사용한다.

MSW API 계약 테스트를 추가해 상태코드와 envelope를 fixture로 고정한다. 실백엔드 E2E에서도 같은 fixture 기대값을 재사용한다.

### 10.2 `embed-host.html`

저장된 `options.display`는 논리 설계 기준이지 호스트 DOM 크기 명령이 아니다. 따라서 고정 640×360 동작은 유지하고, “저장 크기를 자동으로 읽는다”는 안내를 제거한다.

새 안내:

> 크기를 지정하지 않은 슬롯은 확인 편의를 위해 640×360으로 표시합니다. 실제 임베드 크기는 호스트 CSS 또는 인라인 스타일로 지정하세요.

설계 프리셋별 검수는 Admin의 `ChartDesignViewport`에서 담당한다. 수동 호스트가 내부 차트 정의 API를 다시 조회하도록 되돌리지 않는다.

## 11. 레거시 임베드 롤아웃

기존 `[data-chart-id][data-auth-token]` 코드가 이미 배포됐다면 새 서버를 즉시 올리는 순간 깨진다. 운영 데이터가 없다는 것이 확인되지 않는 한 다음 전환 절차를 따른다.

1. 서버에 제한된 레거시 검증 경로와 사용 메트릭을 유지한다.
2. 새 Admin을 먼저 배포해 신규 코드는 `data-embed-key`만 발급한다.
3. 기존 임베드 위치를 새 키로 교체한다.
4. `chartsdk.embed.legacy_request` 메트릭이 정해진 관찰 기간 동안 0인지 확인한다.
5. 레거시 JWT 검증과 `chartId` 요청을 비활성화한다.
6. 사용자 토큰 화면·API 제거 여부를 별도 승인한다.

레거시 경로를 유지할 수 없는 보안 정책이라면 호환 기간 대신 명시적 점검 시간과 전수 교체 목록을 배포 전 승인받는다. 조용한 호환 파괴는 허용하지 않는다.

## 13. 테스트 계획

### 13.1 Server 단위 테스트

- 목록이 활성 키에도 `embedKey`를 포함하지 않는다.
- 호출자 owner scope와 레거시 NULL scope.
- 무인증 허용 플래그 false에서 관리 API 차단.
- 회수 성공 204, 없는/회수/범위 밖 404.
- 모든 `request<void>` 대응 서버 endpoint가 204를 반환한다.
- SQLSTATE별 Admin diagnostic과 Embed 마스킹.
- handler 로그 인자가 cause가 아니라 wrapper 예외임을 검증.

### 13.2 DB 통합 테스트

- 두 트랜잭션 동시 발급: 하나 성공, 하나 409, 최종 ACTIVE 정확히 1개.
- 회전 시 이전 행 `ROTATED`, 새 행 ACTIVE.
- 사용자 비활성 상태의 키 검증은 TOKEN_REVOKED.
- 차트 삭제 cascade 후 키 검증은 TOKEN_REVOKED.

### 13.3 Admin 단위·컴포넌트 테스트

- POST 성공 + GET 실패에서도 새 스니펫 유지.
- 재진입 목록에는 원문이 없고 재발급 전 복사 버튼이 없음.
- 회수 204에서 JSON parse를 시도하지 않음.
- 잘못된 200 빈 본문도 클라이언트 백스톱에서 성공으로 종료하되 계약 테스트는 서버 204를 요구.
- 동일 길이 builder snapshot 교체 시 IN raw 초기화.
- 행 삭제 후 다음 행 raw 유지.
- session draft version 일치/충돌/삭제.

### 13.4 E2E

- 신규 키 발급 → 복사 → 실제 SDK 200 렌더.
- 재발급 후 이전 키 401, 새 키 200.
- 회수 후 401 및 Admin summary REVOKED.
- 브라우저 Back 뒤 복귀 시 초안 복원.
- Navigation API 미지원 모사 환경에서 내부 버튼 확인 모달.
- Admin SQL 오류에는 diagnostic, embed 슬롯에는 일반 문구만 표시.
- MSW와 실백엔드가 같은 상태코드·응답 필드를 반환.

## 14. 구현 순서와 커밋 경계

1. **계약 기반:** DTO·204·MSW 상태코드·문서 오류 정정.
2. **키 보안:** 목록 원문 제거·호출자/차트 스코프·회수 스코프.
3. **키 원자성:** NOWAIT 잠금·409·통합 테스트.
4. **모달 상태:** 일회성 reveal·부분 성공·재발급 확인·회수 UI.
5. **Builder 정체성:** revision+reducer·회귀 테스트.
6. **이탈 무손실:** session draft·leave guard 단순화·Back E2E.
7. **오류 진단:** audience·structured diagnostic·wrapper 로그.
8. **SDK 예산:** 지도 timeout 분리.
9. **문서/롤아웃:** README·호스트·레거시 메트릭과 제거 게이트.

각 단계는 독립 테스트가 통과해야 다음 단계로 넘어간다. 키 목록 원문 제거는 구 Admin과 호환되지 않으므로 새 Admin을 먼저 배포한 뒤 Server를 배포한다.

## 15. 완료 기준

- GET 키 목록에서 Bearer로 사용할 수 있는 문자열이 나오지 않는다.
- 모든 키 관리 작업이 동일한 호출자·차트 스코프를 사용한다.
- 회수 API는 실제 서버·MSW·문서 모두 204이며 Admin에서 성공 처리된다.
- 발급 성공 후 어떤 후속 GET 실패도 새 키를 “발급 실패”로 바꾸지 않는다.
- 동시 발급이 500이나 즉시 무효화된 성공 키를 만들지 않는다.
- 동일 길이 builder 교체에서도 IN 입력 로컬 상태가 새 조건으로 새지 않는다.
- 브라우저 Back으로 화면을 떠나도 편집 내용이 복구 가능하다.
- Embed에는 DB 상세가 없고 Admin에는 정제된 진단과 requestId가 있다.
- SDK 기본 로딩 상한이 단계별 계약과 일치한다.
- MSW·실서버·README·계약서가 같은 엔드포인트와 상태코드를 설명한다.
