## A. 보안

### A1. 데이터소스 DB 비밀번호 평문 저장 🔴
- **원인:** 컬럼명 `db_password_enc`, 스키마 주석(`AES-GCM: base64(IV‖ct‖tag)`), `.env`의 `DATASOURCE_ENC_KEY`가 모두 암호화를 전제했으나, 구현은 입력 비밀번호를 **그대로 저장**(`password()`가 원문 반환)하고 조회 시 **그대로 JDBC 비밀번호로 사용**했다. 코드 전체에 `Cipher`/암복호화가 전무했고 `DATASOURCE_ENC_KEY`는 `.env.example` 외 어디서도 참조되지 않았다.
- **결과(영향):** 메타 DB가 유출되면 연결된 **모든 운영 PostgreSQL 자격증명이 평문 노출**. `_enc` 접미사가 "암호화됨"이라는 착각까지 유발.
- **해결방안:** `crypto/DatasourcePasswordCodec`(AES-GCM) 신설. 저장 시 암호화, 조회 시 복호화. 레거시 평문은 복호화 실패 시 원문 폴백으로 호환.
- **코드:**
  ```java
  // DatasourcePasswordCodec — 키=SHA-256(DATASOURCE_ENC_KEY), 저장형식 base64(IV(12)‖ct+tag(16))
  public String encrypt(String plaintext) { /* GCMParameterSpec(128, iv) */ }
  public String decrypt(String stored) {
      try { /* AES/GCM/NoPadding 복호화 */ }
      catch (Exception e) { return stored; } // 레거시 평문 호환
  }
  // DatasourceController: 저장 시 passwordCodec.encrypt(...), 조회 시 passwordCodec.decrypt(...)
  ```
- **이유:** 키 길이/인코딩 의존을 없애려 env 문자열을 SHA-256으로 32바이트 AES 키로 파생. GCM은 인증 태그로 무결성까지 보장. 복호화 폴백은 이미 저장된 평문 행이 있어도 마이그레이션 없이 동작시키기 위함(기존 데이터 비파괴).

## B. 데이터/SQL (노코드 빌더)

### B1. `DATE_TRUNC` bucket 직접 문자열 결합 인젝션 🔴
- **원인:** `"DATE_TRUNC('" + bucket + "', " + col + ")"` 처럼 사용자 입력 `xAxisBucket`을 **따옴표 이스케이프 없이** SQL 리터럴에 직접 결합. 식별자에 적용되던 `qident`의 따옴표 방어조차 없었다.
- **결과:** 작은따옴표로 탈출하는 전형적 SQL 인젝션. `xAxisBucket`에 임의 식을 주입해 데이터 탈취 가능. 가장 직접적인 공격 벡터.
- **해결방안:** bucket을 `{day, week, month}` 화이트리스트로만 허용하고, 그 외는 `400 BUCKET_TYPE_MISMATCH`로 차단.
- **코드:**
  ```java
  if (!Set.of("day","week","month").contains(bucket))
      throw new ApiException(BAD_REQUEST, "BUCKET_TYPE_MISMATCH", "Unsupported bucket: " + bucket);
  if (!isDate(typeOf(x)))
      throw new ApiException(BAD_REQUEST, "BUCKET_TYPE_MISMATCH", "Bucket requires a date/timestamp column.");
  ```
- **이유:** 고정 enum 값은 화이트리스트가 가장 단순·확실. 추가로 X축 컬럼이 실제 날짜 타입인지 검증해 의미 오류도 함께 차단(노코드 SQL생성규칙 §3A).

### B2. 식별자 화이트리스트 부재 + `mc_` 테이블 미차단 🔴
- **원인:** `table`/`column`/`join` 식별자를 `information_schema` 검증 없이 `qident`로 따옴표만 씌워 사용. `validateTable`은 스키마 미리보기 경로에서만 쓰였고 빌더 경로에선 호출되지 않았다. 내부 메타 테이블(`mc_*`) 차단도 빌더 경로엔 없었다.
- **결과:** 따옴표 escape만으로는 "실재 컬럼인지"를 보장 못 함. 자격증명이 접근 가능한 **임의 테이블/컬럼 + 솔루션 내부 테이블(`mc_user_token` 등) 열람** 가능.
- **해결방안:** `SchemaCatalog`(information_schema 로딩, `mc_` 제외)로 모든 식별자를 검증한 뒤에만 따옴표 적용(이중 방어). 미존재 식별자는 `400 INVALID_IDENTIFIER`.
- **코드:**
  ```java
  // QueryExecutor.catalog(): WHERE table_schema='public' AND table_name NOT LIKE 'mc\_%' ESCAPE '\'
  private Ref resolveRef(String ref) {
      // "table.col" 또는 base 암묵 컬럼 → 카탈로그 존재 검증
      if (!catalog.hasColumn(table, column))
          throw new ApiException(BAD_REQUEST, "INVALID_IDENTIFIER", "Unknown column: " + ref);
      return new Ref(table, column);
  }
  ```
- **이유:** 식별자는 PreparedStatement로 바인딩할 수 없으므로(노코드 SQL생성규칙 §1.2) 화이트리스트가 정석. 카탈로그가 `mc_`를 애초에 제외해 로딩하므로, 존재성 검증이 곧 `mc_` 차단을 겸한다(한 번에 두 문제 해결).

### B3. scatter `none` 집계인데 `GROUP BY` 강제 → 실행 불가 🟠
- **원인:** 집계 분기가 항상 `GROUP BY`를 붙였다. scatter는 모든 yAxis가 `none`(집계 없음)이라 `SELECT x, col1, col2 … GROUP BY x`가 되어 PostgreSQL `must appear in GROUP BY` 에러.
- **결과:** scatter(분포) 차트 경로가 **사실상 실행 불가**.
- **해결방안:** 모든 agg가 `none`이면 `GROUP BY`를 생략.
- **코드:**
  ```java
  boolean allNone = yAxis.stream().allMatch(y -> "none".equals(str(y.get("agg"))));
  String groupBy = allNone ? "" : " GROUP BY " + (bucket == null ? x.quoted() : "1");
  ```
- **이유:** `none`은 분포 전용의 "원본 행 조회"라 집계가 없으니 GROUP BY 자체가 성립하지 않는다. chartType이 아니라 `allNone`으로 판정해 향후 다른 비집계 케이스에도 견고.

### B4. LIKE 와일드카드 escape 누락 🟠
- **원인:** `contains`/`starts_with`가 사용자 입력의 `%`, `_`를 escape하지 않고 패턴에 넣었다.
- **결과:** 사용자가 입력한 `%`가 와일드카드로 동작해 의도와 다른 패턴 매칭(노코드 SQL생성규칙 §4 위반).
- **해결방안:** `\`, `%`, `_`를 escape한 뒤 서버가 `%`를 부착해 단일 파라미터로 바인딩.
- **코드:**
  ```java
  String escaped = s.replace("\\","\\\\").replace("%","\\%").replace("_","\\_");
  String pattern = "contains".equals(op) ? "%"+escaped+"%" : escaped+"%";
  parts.add(col.quoted() + " ILIKE ?"); params.add(pattern);
  ```
- **이유:** 와일드카드 조립은 서버 책임이라는 규칙(§4 비고)에 맞춤. 패턴 전체를 한 파라미터로 바인딩해 SQL 문자열엔 값이 끼어들지 않음.

### B5. 빌더/스키마 경로가 가드레일을 우회 🟠
- **원인:** `QueryController.runBuilder`·`SchemaController.preview`가 각자 raw `DriverManager`로 접속해 `setReadOnly`/`setQueryTimeout`/`setMaxRows`가 제각각(또는 미설정)이었다. 미리보기는 12행 하드코딩, 절단 감지 없음.
- **결과:** 운영 DB에 **무제한 타임아웃·쓰기 가능** 쿼리가 나갈 수 있었고, 에러 코드·행 제한도 경로마다 불일치.
- **해결방안:** 모든 고객 DB 조회를 `QueryExecutor` 단일 경로로 통일.
- **코드:**
  ```java
  // QueryExecutor: 읽기전용 + 타임아웃 10s + 1000행 + 절단 표기 + 에러 매핑 일원화
  conn.setReadOnly(true);
  ps.setQueryTimeout(QUERY_TIMEOUT_SECONDS); ps.setMaxRows(MAX_ROWS);
  boolean truncated = rows.size() >= MAX_ROWS;
  // SQLTimeoutException → 408 QUERY_TIMEOUT, 그 외 → 422 SQL_ERROR
  ```
- **이유:** "노코드는 별도 실행 경로를 만들지 않는다"(노코드 SQL생성규칙 §1.1). 가드레일을 한 곳에 모으면 새 엔드포인트가 생겨도 보안·제한이 자동 적용된다(SSOT 원칙의 실행 계층 버전).

## C. 변환기·렌더 (서버 단일 변환기, 방식 A)

### C1. `withDefaults` 얕은 병합 → 중첩 옵션 기본값 유실 🟠
- **원인:** `merged.putAll(options)`가 최상위 키만 덮어써, 사용자가 `{"yAxis":{"unit":"원"}}`만 보내면 `yAxis` 전체가 교체되어 `format`/`scale`/`splitLine` 등 기본값이 사라졌다.
- **결과:** 중첩 옵션 일부만 바꿔도 같은 그룹의 다른 기본값이 통째로 유실 → 축·범례·시리즈 옵션 광범위 손상.
- **해결방안:** 재귀 deep merge.
- **코드:**
  ```java
  private Map<String,Object> deepMerge(Map base, Map override) {
      // 양쪽이 Map 이면 재귀 병합, 아니면 override 값으로 교체
  }
  ```
- **이유:** 매핑 스펙 §3 "누락 키 = 레지스트리 기본값"은 중첩 키 단위 보존을 의미. 얕은 병합으론 충족 불가.

### C2. scatter 데이터가 `[x,y]` 쌍이 아니라 카테고리축으로 깨짐 🟠
- **원인:** scatter도 cartesian과 동일하게 `xAxis.data = categories`로 두고 시리즈 data를 y 1차원 배열로 만들었다. 분포 차트는 `xAxis.type='value'`에 `[x,y]` 쌍 데이터여야 한다.
- **결과:** 산점도가 인덱스 기반 y만 그려져 좌표가 무의미해짐(축 타입과 데이터 형태 모순).
- **해결방안:** scatter는 X·Y 모두 수치축(data 없음) + 데이터 `[x,y]`(버블이면 `[x,y,size]`).
- **코드:**
  ```java
  if (scatter) { /* xAxis.type=value, data 없음 */ data.add(Arrays.asList(x, y)); }
  // 버블: bubbleField 컬럼을 3번째 차원으로 → [x, y, size]
  ```
- **이유:** 매핑 스펙 §7/§10의 분포 데이터 컨벤션. `Arrays.asList`를 쓴 건 `List.of`가 null을 거부하기 때문(빈/짧은 행 방어).

### C3. `@variant`·직접매핑 미구현 🟠
- **원인:** 기존 변환기가 데이터만 끼운 골격이라 `variant`·`sortOrder`·title·color·grid·축 등 직접매핑과 특수 핸들러를 거의 읽지 않았다.
- **결과:** 누적·곡선·영역·도넛·버블 등 **중분류가 전혀 동작하지 않고**, 사용자가 설정한 대부분의 옵션이 무시됨.
- **해결방안:** 매핑 스펙대로 재작성 — `@sort`, `@variant`(stack/smooth/area/step/donut/rose/bubble/가로/100%정규화), 직접매핑(title/axes/legend/grid/palette/series), `@colorMap`, 이중축.
- **코드:** `ChartOptionConverter`의 `applyVariantDelta`·`applyAxes`·`applyLegend`·`buildCartesianSeries`/`buildPieSeries` 등(파일 참조).
- **이유:** 변환기는 TS/Java 이중 구현 금지(방식 A) — 서버 하나가 임베드·미리보기·재조립을 모두 책임지므로 스펙을 온전히 구현해야 클라이언트가 `setOption`만으로 끝난다.

### C4. ECharts formatter 함수의 JSON 직렬화 불가 🟡
- **원인:** 매핑 스펙은 숫자 포맷(콤마 등)·툴팁 valueFormatter를 **JS 함수**로 정의하나, option은 JSON으로 SDK에 전송되므로 함수를 담을 수 없다.
- **결과:** 콤마/소수 포맷 같은 함수 기반 포맷은 서버 JSON으로 표현 불가.
- **해결방안:** 표현 가능한 것만 처리 — 단위 접미사는 ECharts 문자열 템플릿 `'{value}단위'`로. 함수 포맷은 한계로 명시(후속: SDK 측 후처리 또는 포맷 토큰 전달).
- **코드:**
  ```java
  if (!unit.isEmpty()) label.put("formatter", "{value}" + unit); // 문자열 템플릿(JSON 안전)
  ```
- **이유:** 전송 매체(JSON) 제약을 인정하고 구조적 정확성(축/시리즈/색)을 우선. 거짓으로 함수 문자열을 넣어 클라이언트에서 깨지게 두지 않음.

## D. API·캐시

### D1. raw SQL 실행·refresh·duplicate 엔드포인트 부재 🟠
- **원인:** API 계약서에 정의된 `POST /query/run`(raw SQL), `POST /charts/{id}/refresh`(수동 갱신), `POST /charts/{id}/duplicate`(복제)가 구현되지 않았다.
- **결과:** SQL 탭 실행 불가, manual 모드 차트의 갱신 수단 부재, 카드 복제 액션 불가.
- **해결방안:** 세 엔드포인트 구현. refresh/duplicate는 `ChartComputeService` 재사용.
- **코드:**
  ```java
  @PostMapping("/query/run")          // SELECT/WITH 검증(SQL_NOT_SELECT) 후 QueryExecutor 실행
  @PostMapping("/charts/{id}/refresh")  // recompute → {chartId, computedAt, rowCount, elapsedMs}
  @PostMapping("/charts/{id}/duplicate")// INSERT ... SELECT(이름 "(사본)") + 캐시 복사(재실행 없음)
  ```
- **이유:** raw SQL은 SELECT만 허용해 쓰기/다중문 차단(노코드와 사용자층 분리). 복제는 원본 캐시를 그대로 복사해 재실행 비용 0(계약서 §3.6).

### D2. 저장 시 캐시 시드 부재 🟠
- **원인:** 차트 생성/수정이 INSERT/UPDATE만 수행하고 결과 캐시를 시드하지 않았다.
- **결과:** 저장 직후 manual 차트는 캐시가 없어 첫 임베드 요청의 self-heal에 의존(계약서가 약속한 "저장 시 시드" 미이행).
- **해결방안:** 저장 성공 시 `seedQuietly`로 1회 실행·캐시.
- **코드:**
  ```java
  compute.seedQuietly(id); // 데이터소스 장애 시에도 저장 트랜잭션은 보존(베스트 에포트)
  ```
- **이유:** 시드는 성능 최적화일 뿐 정합성의 필수 조건이 아니므로, 실패해도 저장은 성공시키는 게 옳다(캐시 미스는 self-heal로 복구됨).

### D3. HTTP 상태코드(201/204) 불일치 🟡
- **원인:** 생성/삭제가 `@ResponseStatus` 없이 일괄 200을 반환(계약서는 생성 201·삭제 204).
- **결과:** 201/204로 분기하는 클라이언트와의 계약 위반.
- **해결방안:** `@ResponseStatus(CREATED)`/`(NO_CONTENT)` 명시.
- **이유:** 계약서 정합. 무해해 보여도 표준 상태코드는 외부 통합의 신뢰 계약.

## E. 프론트엔드 동작 (Admin · SDK)

### E1. S2 stale 저장 — 빌더 변경 후 이전 실행 SQL 저장 🟠 (`4f8489a`)
- **원인:** 노코드 빌더(테이블·축·조건·정렬)를 바꿔도 직전 실행 결과(`result`/`generatedSql`/`option`)가 남아 있어, 사용자가 재실행 없이 저장하면 **바뀐 폼과 다른 옛 SQL**이 저장됐다.
- **결과:** 화면의 빌더 상태와 저장된 SQL이 어긋남 → 임베드/미리보기가 의도와 불일치.
- **해결방안:** 빌더 변경 시 실행 산출물을 무효화하고, 저장 버튼은 `result`가 있어야 활성(저장=실행 선행, PRD 7.3).
- **코드(패턴):**
  ```ts
  // ChartEditor: 빌더 config 변경 → result/generatedSql/option = null, canSave = !!result
  ```
- **이유:** "저장은 실행을 선행한다"는 PRD 규칙을 상태 모델로 강제해 stale 데이터 저장을 구조적으로 차단.

### E2. 저장 후 중복 생성·임베드 버튼 비활성 🟠 (`4f8489a`)
- **원인:** 생성 저장 후에도 차트가 "신규" 상태로 남아 재저장 시 또 INSERT됐고, 임베드 버튼은 id가 없어 비활성.
- **결과:** 동일 차트 중복 생성, 저장 직후 임베드 불가.
- **해결방안:** 저장 응답의 id로 `savedId` 전환 → 이후 PUT(수정) 경로 + 임베드 버튼 활성 + 상단 임베드 → S3 모달 연결.
- **이유:** "신규→저장됨" 상태 전이를 명시해 멱등성(중복 방지)과 후속 동선(임베드)을 동시에 확보.

### E3. 원본 데이터 탭에 WHERE 조건 미반영 🟡 (`4f8489a`)
- **원인:** 집계 실행만 호출하고 원본 데이터 탭은 조건 없이 보여줬다.
- **결과:** [원본 데이터]가 WHERE 필터를 무시한 전체를 표시.
- **해결방안:** 실행 시 `run-builder` `mode:rows`를 동시 호출해 같은 조건 바인딩으로 원본을 조회.
- **이유:** 집계/원본이 같은 조건을 공유해야 사용자가 "이 조건의 세부 행"을 신뢰할 수 있음(노코드 SQL생성규칙 §3B).

### E4. 임베드 스니펫 SDK 경로 하드코딩 🟠 (`480e71c`)
- **원인:** 임베드 스니펫이 `cdn.example.com/sdk.js`를 하드코딩.
- **결과:** 실제 배포 환경에서 동작하지 않는 스니펫.
- **해결방안:** `NEXT_PUBLIC_SDK_SRC || window.location.origin + '/sdk.js'`로 환경 기반 해석.
- **코드:**
  ```ts
  const sdkSrc = () => process.env.NEXT_PUBLIC_SDK_SRC ?? `${window.location.origin}/sdk.js`;
  ```
- **이유:** 배포 출처가 환경마다 다르므로 빌드/런타임 env로 주입. 기본값을 현재 출처로 둬 단일 호스트 배포는 설정 0.

### F1. ECharts 번들 1.0MB(임베드 과대) 🟠 (`3ed9950`)

- **원인:** ESLint 9 + eslint-config-next 16 조합이 Next 15와 충돌(flat config 전환기 비호환).
- **결과:** `next lint` 실패로 CI lint 단계가 깨짐.
- **해결방안:** eslint 8 + eslint-config-next@15 + `.eslintrc(next/core-web-vitals)`로 다운그레이드.
- **이유:** 프레임워크가 공식 지원하는 lint 스택에 맞추는 게 신기능보다 우선(빌드 안정성). flat config는 Next가 따라온 뒤 올린다.

### F3. server gradle CLI/래퍼 부재로 컴파일 미검증 🟠 (해결: 이번 세션)

## J. 데이터 정합성 보강 (해결 진행 — 2026-06-25)

데이터 정합성 분석에서 도출한 갭(G1~G8)을 우선순위대로 해결한다. 각 항목은 분석 근거(원인/결과)와
실제 적용(해결/코드/이유)을 함께 기록한다. 강점(스키마 제약·FK·트리거·트랜잭션)은 양호했고,
부족분은 **캐시(파생 데이터)와 동시성**에 집중돼 있었다.

### J1. 동시 재계산 단일 비행 + SWR (G1·G4) ✅
- **원인:** 캐시 미스/`ttl` 만료 시, 동시에 들어온 임베드 요청들이 **모두 고객 DB를 재조회**하고 각자
  `upsert`로 덮어썼다. `V1__init.sql` 캐시 주석이 `pg_try_advisory_xact_lock(chart_id)` 단일 비행을
  명시적으로 권장했으나 미구현. 또 `ttl` 만료 시 `findUsable`이 empty → **동기 재계산(블로킹)** 이라
  만료 직후 요청이 운영 DB를 직격했다.
- **결과(영향):** 만료 순간 운영 DB 부하 스파이크(thundering herd), 표본(sample) 차트는 동시 재계산이
  서로 다른 근사값을 써 **결과가 깜빡임**. 임베드가 막으려던 "DB 직격"이 그대로 발생.
- **해결방안:** advisory 락으로 재계산을 한 요청(승자)으로 합치고, 경쟁에서 진 요청은 stale 캐시를
  즉시 반환(SWR). stale 이 없거나 `live` 모드면 승자 완료를 기다린 뒤 신선한 결과를 읽는다.
- **코드:**
  ```java
  // ChartComputeService.refreshSingleFlight (@Transactional — xact 락은 트랜잭션 종료 시 자동 해제)
  Boolean won = jdbc.queryForObject("SELECT pg_try_advisory_xact_lock(?)", Boolean.class, chartId);
  if (won) return cache.upsert(chartId, queries.execute(datasourceId, sql));   // 승자만 재계산
  if (allowStale) { var stale = cache.find(chartId); if (stale.isPresent()) return stale.get(); } // SWR
  jdbc.query("SELECT pg_advisory_xact_lock(?)", rs -> null, chartId);          // 승자 대기
  return cache.find(chartId).orElseGet(() -> cache.upsert(chartId, queries.execute(datasourceId, sql)));
  // EmbedChartService: findUsable(..).orElseGet(() -> compute.refreshSingleFlight(.., !"live".equals(mode)))
  // ChartCacheService.find(chartId): ttl 무시 raw 조회(stale 반환용) 추가
  ```
- **이유:** advisory **xact** 락은 `@Transactional` 종료 시 자동 해제돼 누수가 없다. 순수 백그라운드
  SWR(별도 스레드)은 `@Async`+새 트랜잭션이 필요해 복잡도가 큰데, "승자 동기 재계산 + 패자 stale 반환"은
  단일 비행과 비블로킹의 핵심 이득을 단순하게 얻는다(승자 1요청만 느리고 나머지는 즉시). `live`는 stale을
  내보내면 의미가 깨지므로 대기 후 신선 결과를 읽는다.

### J2. 정의-캐시 버전 일치로 stale 데이터 차단 (G2) ✅
- **원인:** 차트 `sql_query`/`builder_config`를 수정하면 `seedQuietly`로 재계산하지만, **데이터소스 장애로
  시드가 실패하면 옛 정의로 계산된 캐시가 그대로 남았다.** 캐시에 "어느 정의로 계산했는지" 식별자가 없었다.
- **결과(영향):** `manual` 모드면 임베드가 **새 정의 ≠ 옛 데이터**를 무기한 노출. 정의와 데이터가 어긋난 채 표시.
- **해결방안:** `mc_chart.version`(저장마다 +1)과 `mc_chart_cache.definition_version`을 둬, 임베드 조회 시
  **캐시 버전 ≠ 현재 정의 버전이면 stale 취급**(재계산). 캐시는 계산 시점의 정의 버전을 함께 스탬프.
- **코드:**
  ```sql
  -- V2__integrity.sql
  ALTER TABLE mc_chart ADD COLUMN version INTEGER NOT NULL DEFAULT 0;
  ALTER TABLE mc_chart_cache ADD COLUMN definition_version INTEGER;
  ```
  ```java
  // ChartCacheService.findUsable(.., int currentVersion)
  int cachedVersion = rs.getInt("definition_version");
  if (rs.wasNull() || cachedVersion != currentVersion) return Optional.empty(); // 정의 변경 → stale
  // upsert(.., definitionVersion): 계산 시점 정의 버전을 캐시에 스탬프
  // EmbedChartService: findUsable(.., chart.version()) + refreshSingleFlight(.., chart.version(), ..)
  ```
- **이유:** `version` 하나가 **낙관적 락(G3)과 캐시 무효화(G2)를 동시에** 해결한다 — 저장이 곧 버전 증가이고,
  캐시는 그 버전으로 태깅되므로 "정의가 바뀌면 캐시는 자동으로 stale"이 성립. 별도 해시 컬럼·트리거 불필요.
  마이그레이션은 `docs/V*__*.sql` 글로브로 복사하도록 빌드를 바꿔 V2 이후도 자동 반영.

### J3. 낙관적 동시성 제어로 갱신 유실 방지 (G3) ✅
- **원인:** 두 사람(또는 두 탭)이 같은 차트를 동시에 열어 저장하면 **마지막 PUT이 앞 변경을 덮어썼다**(lost update).
  버전 비교·`If-Match`가 없었다.
- **결과(영향):** 변경 유실. 개인 스코프라도 멀티탭에서 발생 가능.
- **해결방안:** `GET`이 `version`을 내려주고, `PUT`이 그 버전을 되돌려보내면 **`WHERE id=? AND version=?`로만 갱신
  + `version=version+1`**. 0행이면 차트 존재 여부로 갈라 **409 VERSION_CONFLICT**(존재) 또는 404(미존재).
- **코드:**
  ```java
  // ChartController.update — version 미전송 시 기존 동작(하위호환), 전송 시 낙관적 락
  if (expectedVersion != null) { sql.append(" AND version=?"); args.add(expectedVersion); }
  if (updated == 0) {
      boolean exists = count("mc_chart", id) > 0;
      throw exists ? conflict("VERSION_CONFLICT", "modified elsewhere; reload")
                   : notFound("CHART_NOT_FOUND");
  }
  ```
- **이유:** 낙관적 락은 비관적 락(행 잠금)보다 가볍고, 충돌이 드문 개인 툴에 적합. `version`을 보내지 않는 기존
  클라이언트는 종전대로 동작(점진 도입). 충돌은 **유실 대신 409로 드러내** 사용자가 새로고침 후 재시도하게 한다.

### J4. 암호문 버전 태그 + 명시적 복호화 실패 (G6) ✅
- **원인:** `decrypt()`가 복호화 실패 시 **입력을 그대로 반환**(레거시 평문 호환)했다. 그래서 *진짜 암호문이
  손상되거나 키가 바뀌어 복호화 실패*해도 **쓰레기 값을 비밀번호로 조용히 반환**했고, 키 회전 식별 수단도 없었다.
- **결과(영향):** 정합성 위반을 "조용한 접속 실패"로 흘려보냄. `DATASOURCE_ENC_KEY`를 바꾸면 기존 비밀번호
  전부 복호화 불가인데, 그조차 평문 폴백에 묻혀 진단이 어려움.
- **해결방안:** 암호문에 키 버전 마커 `"v1:"`를 붙인다. **마커가 있으면 우리 암호문 → 복호화 실패 시 평문 폴백
  금지하고 명시적 오류.** 마커가 없으면 레거시 평문으로 취급(마이그레이션 0). 회전 시 `v2:` 등으로 확장.
- **코드:**
  ```java
  private static final String PREFIX = "v1:";
  // encrypt: return PREFIX + base64(IV‖ct+tag);
  public String decrypt(String stored) {
      if (!stored.startsWith(PREFIX)) return stored;          // 레거시 평문 → 그대로
      try { /* base64 decode + AES-GCM 복호화 */ }
      catch (Exception e) { throw new IllegalStateException("decryption failed (key mismatch/corrupted)"); }
  }
  ```
- **이유:** "복호화 실패 = 명시적 오류"여야 키 불일치/손상을 **조용한 오접속이 아니라 즉시 가시화**한다.
  마커는 향후 키 회전(`v2:`)에서 "어느 키로 복호화할지"를 값 자체가 담게 해, 무중단 점진 회전의 토대가 된다.
  마커 없는 값만 평문 폴백이라 기존 시드(`'0218'`)·레거시 데이터와 호환된다.

### J5. 집계 절단(1000행) 노출 (G5) ✅
- **원인:** 모든 조회가 `LIMIT 1000`+`setMaxRows(1000)`. GROUP BY 결과 그룹이 1000개를 넘으면 일부가
  잘린 채 집계되는데, 절단 여부가 임베드 응답에 드러나지 않았다.
- **결과(영향):** 합계/카운트 차트가 **소리 없이 부분값**이 될 수 있어 "정확한 합계"로 오해.
- **해결방안:** `QueryExecutor`가 `rowCount >= MAX_ROWS`일 때 `truncated=true`로 표기하고(이미 적용),
  이를 **임베드 응답에도 동봉**(`rowCount`/`truncated`)해 SDK·페이지가 "상위 1000개" 안내를 띄울 수 있게 했다.
- **코드:**
  ```java
  // EmbedChartService.data
  response.put("rowCount", rows.rows().rowCount());
  response.put("truncated", rows.rows().truncated());
  ```
- **이유:** 정합성에는 "정확성"뿐 아니라 **"불완전함을 정직하게 드러내는 것"** 도 포함된다. 절단을 숨기면
  사용자가 부분값을 전체값으로 신뢰하는 더 큰 정합성 사고로 이어진다.

### J6. 깨진 캐시를 예외 대신 미스로 처리 (G7) ✅
- **원인:** `ChartCacheService.readRows`가 캐시 JSONB 역직렬화 실패 시 `IllegalStateException`을 던져,
  손상된 캐시 한 줄이 **임베드 요청 전체를 500으로 깨뜨렸다**. 구조 검증도 `jsonb_typeof='object'`뿐이었다.
- **결과(영향):** 캐시 손상이 self-heal 가능한 상황인데도 사용자에게 장애로 전파.
- **해결방안:** `readRows`가 `{columns, rows}` 구조를 검증하고, 깨졌으면 `null` 반환 → `findUsable`/`find`가
  **미스로 처리**해 단일 비행 재계산으로 자가 복구.
- **코드:**
  ```java
  if (!(result.get("columns") instanceof List) || !(result.get("rows") instanceof List)) return null;
  // 호출부: QueryRows rows = readRows(..); return rows == null ? Optional.empty() : Optional.of(..);
  ```
- **이유:** 파생 데이터(캐시)의 손상은 **복구 가능한 미스**로 다뤄야지, 원본이 멀쩡한데 장애로 키우면 안 된다.
  "캐시는 언제든 버리고 다시 만들 수 있다"는 캐시의 본질에 맞춘 처리.

### J7. 생성 멱등성 (G8) — 의도적 후순위 ⏸
- **원인:** `POST /charts`는 매번 INSERT라, 재시도/더블클릭 시 중복 생성 가능.
- **결과(영향):** 중복 차트. 단 admin은 저장 후 `savedId` 상태 전환으로 클라이언트 측 중복을 이미 차단(트러블슈팅 E2).
- **결정:** **후순위로 보류.** 완전한 멱등은 `Idempotency-Key` + 단기 키 저장 테이블이 필요한데, 사용자 측
  중복 방지가 이미 있고 개인용 내부 툴이라 비용 대비 이득이 낮다.
- **권장 해결방안(추후):** `POST`에 `Idempotency-Key` 헤더 + (key, 응답) 단기 캐시 테이블 → 동일 키 재요청은
  기존 결과 반환. 또는 (owner_id, name) 단기 유니크로 중복 생성 거부.
- **이유:** 정합성 보강도 **비용 대비 효과로 우선순위를 매겨야** 한다. 이미 1차 방어선(클라이언트)이 있는
  저빈도 위험은, 더 시급한 캐시·동시성·보안(G1~G6)을 끝낸 뒤로 미루는 것이 합리적이다.

## 횡단 교훈 (Cross-cutting)

1. **컬럼명/주석이 약속한 것을 코드가 이행하는지 검증** — `_enc`처럼 "이름이 보안을 약속"하면 반드시 구현을 확인(A1).
2. **식별자는 화이트리스트, 값은 바인딩** — SQL 안전의 2대 규칙. 식별자 escape만으론 부족(B1·B2).
3. **단일 경로(SSOT)로 가드레일 집약** — 실행은 `QueryExecutor`, 옵션 기본값은 `defaults.json`, 변환은 단일 Java 변환기. 경로가 갈라지면 보안·정합이 갈라진다(B5·C3).
4. **전송 매체 제약을 인정** — JSON으론 함수를 못 보낸다. 표현 가능한 범위에서 정직하게(C4).
5. **상태 전이를 모델로 강제** — "저장=실행 선행", "신규→저장됨"을 코드 상태로 못 박아 stale/중복을 구조적으로 차단(E1·E2).
6. **테스트 환경의 결정성** — stale 서버·콜드 컴파일·버퍼링은 "코드 버그"가 아니라 "관측 신뢰성" 문제. 환경을 통제해야 빨강/초록을 믿을 수 있다(G1–G4).
7. **프레임워크 지원 스택 우선** — 신버전(ESLint9)보다 프레임워크가 보증하는 조합이 빌드 안정성에 유리(F2).
8. **검증 게이트를 환경 제약 너머로** — 래퍼가 없어도 캐시 배포본으로 컴파일 게이트를 세운다(F3).
