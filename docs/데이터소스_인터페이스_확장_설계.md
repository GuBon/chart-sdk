## 0. 목적과 범위 선언

현재 계산 경로는 PostgreSQL 단일 종류를 전제로 카탈로그 로딩·접속 규약·엔진 선택이 구현 클래스에 직접 결합되어 있다. 본 설계는 **새 데이터소스 종류(파일 업로드, API, 타 DBMS 등)를 추가할 때 건드릴 파일이 정해진 소수가 되도록** 경계를 재배치한다.

**범위에 대한 명시적 선언:**

- **기능 증가 0.** 파일 업로드를 포함해 어떤 신규 소스 종류도 이번에 구현하지 않는다. 순수 구조 전환이다.
- 모든 단계의 완료 기준은 "기존 테스트가 **테스트 파일 수정 없이** 전부 통과"다. 테스트를 고쳐야 한다면 동작이 바뀐 것이고, 이 리팩터링의 실패 신호다.
- 프론트엔드(admin·sdk)·chart-options·DB 스키마·API 계약은 **변경 0**이다.

## 1. 현재 결합 실측 (2026-08-11 기준)

### 1.1 이미 인터페이스화되어 재사용하는 자산

| 이음매 | 위치 | 구현 |
|---|---|---|
| `Catalog` (식별자 화이트리스트) | `query/Catalog.java` | `SchemaCatalog` · `FederatedCatalog` |
| `RefRenderer` (참조 렌더링 전략) | `query/RefRenderer.java` | `SINGLE` · `FEDERATED` · `alias()` |
| `AdmissionController` (동시성 경계) | `query/AdmissionController.java` | JVM-local (분산 교체 전제 명시) |
| `QueryRows.from(rs, …)` (결과 계약) | `query/QueryRows.java` | PG·DuckDB 공유 |

`QueryRows` 이후 구간(변환기 → 캐시 → 임베드 → SDK)은 이미 데이터 출처와 무관하다. `EmbedChartService`는 `ChartComputeService.serve()` 캐시만 읽고, `ChartOptionConverter`는 rows만 받는다. **포트화가 필요한 것은 `QueryRows`를 만들기 이전 구간뿐이다.**

### 1.2 소스 구성 판정 3중복 (핵심 문제)

"이 차트의 소스 구성이 무엇인가"에 따른 판정이 3곳에 개수(`size >= 2`) 기반으로 중복되어 있다.

| # | 위치 | 판정 |
|---|---|---|
| 1 | `federation/FederatedQueryRunner.runBuilder()` (`refs.size() >= 2`) | 엔진 선택: DuckDB vs PG 직접 |
| 2 | `cache/ChartComputeService.isMultiSource()` (count 쿼리 `>= 2`) | 서빙 정책: 캐시-온리 여부 |
| 3 | `chart/ChartService.prepareForSave()` (`datasources.size() >= 2`) | 저장 정책: `refresh_mode` manual 강제 |

새 소스 종류 추가 시 3곳을 모두 고쳐야 하고, 하나라도 누락하면 임베드가 고객 데이터소스를 직격하는 **서빙 불변식 위반**이 된다(연합조회 설계 §8).

### 1.3 기타 결합 지점

| 결합 | 위치 | 내용 |
|---|---|---|
| 실행·카탈로그·캐시 3책임 동거 | `query/QueryExecutor.java` (313줄) | SQL 실행 + `pg_catalog` 로더 + TTL 캐시가 한 클래스. 호출부 7곳 중 `SchemaController`·`DatasourceRuntimeInvalidator`는 카탈로그만 필요한데 실행기를 통째로 주입받음 |

## 4. 도입 포트 명세

### 4.1 `CatalogPort` + `CatalogService` — 카탈로그 로딩 분리

```java
// datasource/spi/CatalogPort.java — 소스에서 메타데이터를 "어떻게 읽는가"
public interface CatalogPort {
    SchemaCatalog load(long datasourceId);
}

// query/CatalogService.java — TTL 캐시·무효화·행수 추정 (종류 무관, 현행 로직 이동)
@Service public class CatalogService {
    SchemaCatalog catalog(long datasourceId);
    void invalidate(long datasourceId);
    Map<SchemaCatalog.Key, Long> estimatedRowCounts(long datasourceId);
}
```

- `QueryExecutor`의 `pg_catalog` 질의(`loadCatalogAdmitted`)를 `PostgresCatalogPort`로 이동. TTL 캐시·`invalidateCatalog`는 `CatalogService`로 이동.
- 호출부 6곳 교체: `DuckDbFederation.catalog()` · `FederatedQueryRunner` 2곳 · `SchemaController` 2곳 · `DatasourceRuntimeInvalidator`.
- `SamplingPlanner`의 통계 프로브 쿼리도 이 포트 뒤로 격리한다.
- 즉시 이득: `SchemaController`·`DatasourceRuntimeInvalidator`에서 실행 엔진 의존 소멸, 관련 테스트가 실행기 없이 성립.

### 4.2 `DuckDbBinding` — 접속 규약 은닉

```java
// datasource/spi/DuckDbBinding.java — "이 소스를 DuckDB 세션에 붙이는 SQL"
public interface DuckDbBinding {
    String attachSql(long datasourceId);
    String maskedAttachSql(long datasourceId);  // 로깅용 — 비밀번호 마스킹(연합조회 설계 §10)
}
```

- `DuckDbFederation`의 `attachSql`/`connString`/`libpq`/`sqlLiteral`을 `datasource/postgres/PostgresDuckDbBinding`으로 이동. 엔진은 받은 SQL을 실행만 한다.
- `DatasourceCredentials`·`DatasourcePoolFactory`를 `datasource/postgres/`로 이동해 패키지 밖에서 PG 접속 규약이 보이지 않게 한다.
- 호출부 2곳(`DatasourcePoolFactory`, `DuckDbFederation.configure`)뿐이라 비용 최소.

### 4.3 `QueryEngine` — 실행 엔진 공통 포트

```java
// query/engine/QueryEngine.java
public interface QueryEngine {
    RefRenderer renderer();
    QueryRows execute(ExecutionTarget t, BuilderSqlBuilder.Sql sql, ExecutionSpec spec);
    long explainEstimatedRows(ExecutionTarget t, BuilderSqlBuilder.Sql sql);
    PointCollectionResult executeAutoPoints(ExecutionTarget t, BuilderSqlBuilder.Sql sql,
                                            int targetSize, long seed);
}
public record ExecutionTarget(Set<Long> datasourceIds) {}
public record ExecutionSpec(int maxRows, Long bernoulliSeed, AdmissionController.Kind kind) {}
```

- `QueryExecutor` → `PostgresQueryEngine`(4.1 분리 후 실행 전담), `DuckDbFederation` → `DuckDbQueryEngine`.
- `FederatedQueryRunner`의 `runSingle`/`runFederated` 골격을 엔진 주입 한 벌로 통합한다.
- `ExecutionSpec`이 현재 흩어진 실행 축(maxRows / bernoulliSeed / admission Kind)을 한 값으로 묶는다.

**통합 범위 제한 — L1 표본 캐시 경로는 통합하지 않는다.** 페더레이션 RESULT_RANDOM은 EXPLAIN 추정과 표본 실행이 같은 ATTACH 세션에서 일어나야 하고(`executePlannedResultSample` — per-op 무상태 + `threads=1` 재현성), 단일 PG는 `executeCachedSample`로 분리 실행한다. 이 차이는 우발적 중복이 아니라 엔진의 실제 실행 모델 차이다. 목표는 중복 0이 아니라 **"엔진이 갈리는 지점을 한 곳으로 모으는 것"**이며, 골격 통합률은 60~70% 수준을 예상치로 둔다.

### 4.4 `SourceCompositionPolicy` — 판정 단일화

```java
// query/engine/SourceCompositionPolicy.java — 소스 구성 판정의 단일 진실원
public interface SourceCompositionPolicy {
    QueryEngine engineFor(Set<Long> datasourceIds);
    boolean requiresSnapshot(Set<Long> datasourceIds);            // 서빙 시 재계산 금지?
    String normalizeRefreshMode(Set<Long> ids, String requested); // 저장 시 manual 강제?
}
```

- 현행 규칙(`size >= 2`)을 **그대로** 이동한다. 동작 변화 0.
- §1.2의 호출부 3곳이 위임으로 교체된다. `isMultiSource`는 `requiresSnapshot` 위임으로 개명한다 — 개념이 "다중 소스"에서 "서빙 시 재계산 불가"로 정확해진다.
- **현재의 소스 개수 임계 규칙**(라우팅·스냅샷 서빙·갱신 모드 고정)을 바꿀 때 손댈 파일이 이 하나가 된다.
  종류 인지 규칙(예: "파일 소스는 항상 스냅샷")은 §8 승격 공사(kind 판별자·서빙 판정 종류 인지화)와 함께 온다.

## 5. 단계 계획

각 단계는 독립 커밋이며 단독 revert 가능하다. 순서는 의존 순(P2가 P3의 전제 — 엔진이 접속 SQL을 주입받으려면 바인딩이 먼저 존재해야 한다).

| Phase | 내용 | 규모 | 위험 |
|---|---|---|---|
| **P1** | `CatalogPort`+`CatalogService`+`PostgresCatalogPort`. 호출부 6곳 교체 | 이동 ~110줄, 신규 ~40줄 | 낮음 (순수 이동) |
| **P2** | `DuckDbBinding`+`PostgresDuckDbBinding`. `DatasourceCredentials`·`DatasourcePoolFactory` postgres 패키지 은닉 | 이동 ~50줄 | 낮음 (호출부 2곳) |
| **P3** | `QueryEngine`·`ExecutionTarget`·`ExecutionSpec`. `FederatedQueryRunner` 골격 재구성 | 재구성 ~300줄 | **중간** — 표본 캐시 세션 결합(§4.3) |
| **P4** | `SourceCompositionPolicy`. 판정 3곳 위임 교체, `isMultiSource`→`requiresSnapshot` 개명 | ~60줄 | 낮음 (규칙 이동만) |
| **P5** | 테스트 fake: `FakeCatalogPort`·`FakeQueryEngine` (src/test 전용) | 테스트만 | 없음 |
| **P6** | 문서: [코드구조 안내](코드구조_안내.md)에 "확장점" 절 추가, 본 문서 상태 갱신 | 문서만 | 없음 |

P5의 fake는 프로덕션 기능 0으로 "두 번째 구현이 실제로 꽂히는가"를 컴파일·테스트로 증명하는 장치다. 각 Phase에 해당 fake를 함께 넣는 방식을 권장한다(이음매가 진짜인지 그 자리에서 증명).

### 6.2 최종 판정 — 확장 리허설 체크리스트

완료 후 "가상의 새 소스 종류 X를 추가한다면 건드릴 파일"을 **코드를 쓰지 않고 문서상으로** 리허설한다.

**(2026-08-11 정정)** 아래 "후" 열은 **§8의 1회성 승격 공사가 끝난 뒤의 정상 상태**다. 엔진·정책 축은 지금도 성립하며(`QueryEngineSeamTest`가 생성자 이음매를 실행 수준으로 증명), 카탈로그·바인딩 축은 첫 새 종류 도입 시 §8-2의 종류 키 디스패치 승격을 함께 요구한다 — "구현 1개 추가"만으로 끝나지 않는다. 이 비용을 숨기지 않기 위해 §8에 목록으로 고정한다.

| 필요한 것 | 리팩터링 전 | 리팩터링 후 (목표) |
|---|---|---|
| 카탈로그 | `QueryExecutor` 내부 수술 | `CatalogPort` 구현 **신규 1개** |
| 접속 | `DatasourceCredentials`·`DatasourcePoolFactory`·`DuckDbFederation` 3곳 수정 | 바인딩 구현 **신규 1개** |

이 표가 성립하지 않으면 경계를 잘못 그은 것이므로 P4 완료 시점에 재점검하고 필요 시 경계를 조정한다.

## 8. 후속 (본 설계 범위 밖) — 첫 새 종류 도입 시의 1회성 승격 공사

두 번째 소스 종류의 실제 요구가 확정되면 아래를 **한 배치로** 수행한다. 이 목록은 §6.2 체크리스트가
"구현 1개 추가"로 끝나기 위한 전제 공사이며, 종류가 1개인 오늘 만들면 죽은 코드가 되므로 의도적으로 보류한다(§2).

1. **판별자**: `mc_datasource.kind`(+필요시 `config` JSONB) 마이그레이션. PG 전용 컬럼 NOT NULL 완화는 kind 조건부 CHECK로.
2. **종류 키 디스패치 승격**: `CatalogService`·`DuckDbFederation`의 단일 포트 주입을 `kind → CatalogPort` / `kind → DuckDbBinding` 레지스트리로 승격. Spring 다중 빈은 이 레지스트리가 수집한다(현재의 단일 주입은 종류 1개 전제의 의도적 단순형). **세 번째 실행 엔진**(PG 직접도 DuckDB도 아닌 독자 엔진)이 필요한 종류라면 `FederatedQueryRunner`의 single/federated 2슬롯·boolean 라우팅도 엔진 선택 디스패치로 함께 승격한다 — DuckDB로 실행되는 종류(파일 등)는 이 승격 없이 기존 federated 슬롯을 재사용한다.
3. **서빙 판정의 종류 인지화**: `ChartComputeService.isMultiSource`의 count 판정을 소스 집합(또는 종류 집합) 판정으로 전환. 이 시점은 기능 변경이므로 해당 테스트 갱신을 수반한다. `requiresFederation`·`normalizeRefreshMode`는 이미 `Set<Long>`을 받으므로 정책 구현체에 kind 조회만 주입하면 된다(인터페이스 무변경).
4. **바인딩 다문장화**: `DuckDbBinding.AttachStatement` 단문 계약을 다문장 계획(예: `ATTACH ':memory:'` + `CREATE VIEW ... read_parquet(...)`)으로 확장. 파일 포맷 요구가 확정된 뒤 계약을 정한다.
5. **잔존 PG 직결 경로 정리(해당 종류가 요구할 때만)**: raw SQL 경로(`QueryController`·`ChartService` raw 저장·`SchemaController` preview)는 제품상 PG 전용 고급 경로다 — 새 종류에 raw SQL을 열 때만 포트화한다. `SamplingPlanner`의 PG 프로브 실행 경로·`DatasourceService`의 연결 시험/CRUD 형태도 이 배치에서 종류 분기한다.

그 외 판단 보류 항목: 상위 파사드(`DataSourceProvider`) 필요성, capability 플래그, 방언 추상화.
파일 소스의 경우 DuckDB가 CSV·Parquet를 네이티브로 읽으므로 위 승격 공사 + `CatalogPort`·`DuckDbBinding` 구현 각 1개로 수용 가능하다는 사전 조사 결과만 기록해 둔다(별도 실행 엔진 불요).
